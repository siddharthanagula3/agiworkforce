# AGI Workforce Web Public Release Audit

Status: Current
Owner: Founder + web lead
Last updated: 2026-09-14

The canonical public-release audit of the website, `apps/web`, and the shared
packages it renders. It covers the application shell, the new-chat screen, the
composer, streaming, navigation and escape, errors, responsive layout,
accessibility, themes, the design system, the public marketing routes and
support. Desktop, mobile, CLI and the extensions are out of scope except where
a shared package changes what the website renders.

This file holds the audit's findings, the state of each, and the order in which
the remaining work should happen. Root causes that need engineering beyond this
pass are also pointed to from `ACTIVE_ISSUES.md`, which remains the entry point
for all unresolved work; this file does not duplicate the registers named there.
A finding closed here is deleted from this file in the commit that closes it,
the same rule `ACTIVE_ISSUES.md` follows.

The new-chat empty state is an intentional product decision: greeting, composer,
sidebar, nothing else. Nothing in this audit treats its emptiness as a gap, and
nothing in this pass added a suggestion, card, chip, tile or template to it.

## Executive summary

**Release status: NOT READY for a public launch tomorrow. Frontend:
CONDITIONALLY READY once this pass is deployed and the P2 items below are
either fixed or accepted.**

The frontend condition is narrow. The website is coherent, honest about what it
does not have, and free of the generic look the design rules forbid. What kept
it from being finished was a small number of shared root causes with wide blast
radius: a root loading boundary that turned every marketing navigation into a
blank spinner and every deep-link redirect into a one-second meta-refresh with
the wrong status code; a providers file that shipped the whole chat runtime to
every legal page; a handful of public claims the product does not honour; and
several shared primitives (send button, sheet close, toaster, focus ring, offline
bar) each producing the same defect on every screen that used them. Most of
those are fixed in this pass and verified below.

The overall NOT READY is about what this audit cannot fix from a checkout, and
what sits outside the frontend. `ACTIVE_ISSUES.md` records that no durable chat
turn has yet completed on the production deployment (`LIVE-8`), that migrations
`0183` to `0190` are unapplied in production, that Stripe is in test mode, and
that the four Claude chat models answer 400 for lack of credit. A public launch
with those open is not a frontend question, and this file does not restate them.

**Top launch blockers (frontend, after this pass):** none at P1. The items
that would most make the site feel unfinished to a first-time visitor are
`WEB-010` (public pages now ship about half the script they did, and the
remaining half is the shared UI barrel, Sentry and Clerk), `WEB-020` (no client-side latency measurement, so the fast-model
promise cannot be proven), `WEB-030` (support is mailto-only and the page that
states the commitment was unlinked until this pass), `WEB-040` (hand-rolled
dialogs without focus management) and `WEB-050` (the shell clips between 769px
and about 899px and at 1024px with two panels open).

**Strongest areas:** the new-chat state is genuinely minimal and its
minimalism is recorded in code; the streaming markdown pipeline (settled and
tail split, lazy Shiki, gated mermaid and KaTeX, one cursor, no typewriter); menu
keyboard handling and portalled menus, written from real browser evidence;
send-failure recovery with nine test cases; the colour token contract in
`chat.css` with a 270-case contrast suite; every public claim about prices,
plans, model and provider counts reading from one owner; zero broken internal
links across 466 route references; `/customers`, `/partners` and `/press`
stating what does not exist rather than inventing it; no raw error message,
stack or digest printed by any `error.tsx`.

**Weakest areas:** the pre-provider request path (14 to 18 database round trips
and no early byte on the wire before the model's first token); the shared UI barrel, Sentry and the
Clerk script that still ride on public pages; a marketing layer that ships six section
systems and two 3,000-line stylesheets defining the same rules; a ratchet of
1,241 grandfathered raw colour and type literals; a support product that is built
but dark; and a chat shell with two fixed minimum widths that do not fit a tablet.

## Method and evidence

What was measured, observed or hypothesised, and where the instrument had limits.

- **Static analysis** over `apps/web`, `packages/ui/*`, `packages/client/*` and
  the guards in `scripts/`, by seven bounded review passes (routes; design
  system; shell and composer; streaming and latency; marketing; escape, states
  and support; accessibility, theme and responsive), each re-verified by the
  lead before a finding was accepted. Findings the reviewers could not verify
  are marked Hypothesis.
- **Runtime, signed out.** A production build (`next build`, then `next start`)
  against a local Postgres with all 190 migrations applied, the CI Clerk fixture
  key and `AGI_ALLOW_INVALID_ENV=1`, exactly as the `Web E2E and accessibility
audit` CI job runs. 101 public routes were driven in Chromium at 320, 360,
  375, 390, 430, 768, 820, 1024, 1280, 1440, 1728 and 1920 wide in dark, and at
  390 and 1440 in light: 1,187 page loads before the fixes and a second sweep
  after. Measured per load: HTTP status and final URL, horizontal overflow,
  interactive targets under 24px, `h1` count, `main` and `nav` landmark counts,
  unnamed buttons, images without `alt`, console and page errors, navigation
  timing, script count and transfer size, document height.
- **Accessibility scan.** axe-core (`@axe-core/playwright`, WCAG 2.0 and 2.1
  A and AA tags) on twelve public routes at 390 and 1440 in dark and light, 48
  page loads, after the fixes were built. Results are in the accessibility
  section below; the two rules it raised were fixed in this pass and the scan
  repeated.
- **Runtime, signed in: not possible.** The identity provider has exactly one
  production implementation (`packages/platform/identity/src/factory.ts`:
  `clerk`), the fake provider lives in the test harness only, and no Clerk
  secret exists in this environment. Every finding on `/chat`, `/settings`,
  `/code` and the other 55 protected routes therefore rests on code reading and
  the unit and component suites (`vitest`), which were run for every file this
  pass changed. Each such finding names the browser check that would confirm it.
- **Competitor reference.** The repository's own dated, signed-in observations of
  chatgpt.com and claude.ai (2026-08-30 to 2026-09-13) plus official help-centre
  and release-note pages for all three products fetched on 2026-09-14. Gemini has
  no signed-in observation in the repository; its rows are labelled accordingly.
- **Latency.** No provider credential exists here, so T0 to T10 could not be
  measured end to end. The server already carries 30 named phases on the
  `chat.turn` span; the client carries no marks at all. The instrumentation plan
  in the performance section is the prerequisite for the next measurement.

Environment artefacts that are not product defects and were excluded: the CI
Clerk key resolves to `clerk-ci.invalid`, so every page logs a failed script
load and `/pricing` waits 13 seconds for a blocked `js.stripe.com`; Node 22 ran
where the repository standardises on 24; the `@modelcontextprotocol/ext-tasks`
GitHub tarball is blocked by the proxy and was linked from a local clone for the
install only. None of those changed a file in this tree.

## AI-slop findings

Judged against the confirmed public design system (Newsreader display, Geist
body, JetBrains Mono receipts and eyebrows, warm black and cream with one amber
accent, italic amber hero fragment, mono fact ribbon, CSS device mockups, one
closing section) and the product-UI target (the ChatGPT and Claude conventions
with model and provider choice as the only additions). A deliberate signature is
not slop. What follows is what does not belong to either system.

### Public pages

- **Location:** `apps/web/features/marketing/components/DeviceMockups.tsx`, the
  hero device on `/`, `/web` and the surface pages.
  **Evidence:** the mockup drew "Served by AGI Cloud · Auto route · 612 in ·
  240 out · $0.004 · 6.2 s", a "3,740 / 128,000" token counter and an "Enter to
  send" hint. The product prints a receipt only when Auto moved the model, meters
  in credits, and has no token counter.
  **Why it feels generated:** a fabricated dollar figure and a counter that
  exists nowhere in the product are the two things a mockup template adds to
  look like a finished dashboard.
  **Root cause:** the mockup was drawn from a wished-for composer, not from the
  shipped one, and no claim test read it.
  **Smallest correction:** done this pass. The receipt says "metered in
  credits", the counter is gone, the keyboard hint stays because it is true.
- **Location:** `MarketingLanding.tsx:351`, `app/features/page.tsx:202`.
  **Evidence:** "A served-by receipt under every reply", already banned on
  `/web` by `surface-page-claims.test.ts` but still shipped on the homepage and
  `/features`.
  **Root cause:** the guard read one file.
  **Smallest correction:** done this pass; the sentence now says what the
  product does ("Every reply names the model that answered it") and the guard
  reads all three files.
- **Location:** `MarketingLanding.tsx:66-80`, the proof row.
  **Evidence:** `approximateCount` rounded 4 to "3+" and 6 to "5+", so the band
  read "3+ local runtimes" and "5+ surfaces" twelve lines above an `<h2>` that
  says "Six surfaces."
  **Why it feels generated:** a "+"-suffixed stat band that understates its own
  product is what a generic stat helper does to numbers it was not written for.
  **Smallest correction:** done this pass; counts below ten print exactly.
- **Location:** `legacy-pages.css:1168`, `:2359`; `system.css:1323`;
  `legacy-landing.css`.
  **Evidence:** one eyebrow motif rendered with three different dashes (the U+2014 escape,
  `\2013`, a literal en dash), and the em dash escaped the CI guard because it
  was written as a CSS escape.
  **Smallest correction:** done this pass; one glyph, and the guard reads the
  escape.
- **Location:** `apps/web/app/docs/page.tsx` and its `agi-docs` classes.
  **Evidence:** the only public page with no footer, a sixth section system, and
  an icon-plus-title-plus-sentence card wall.
  **Why it feels templated:** the card wall is the exact shape the design rule
  forbids ("three equal feature cards, cards around prose").
  **Root cause:** `/docs` was built before the `agi-ds` system and never moved.
  **Smallest correction:** WEB-084, not done here: rebuild `/docs` on
  `PageHero` and `Section`, drop the cards for a link list, restore the footer.
- **Location:** five public pages that hand-roll `grid-cols-3`
  (`/get-started`, `/security`, `/business`, `/teams`, `/enterprise` sections).
  **Evidence:** the system's `Bento` already handles three children with the
  responsive collapse; the hand-rolled grids have no phone fallback below `sm`.
  **Smallest correction:** WEB-085.
- **Location:** `/get-started`.
  **Evidence:** every section heading is written twice, once as the eyebrow and

  **Smallest correction:** WEB-086, drop the eyebrow where it repeats the
  heading.

  **Evidence:** "build the future of AI-powered work", three times in one

  **Smallest correction:** WEB-088, say what the job is.
- **Location:** `/connectors/mcp-directory`.
  **Evidence:** 407 vendor descriptions written for another product, with the

  **Smallest correction:** WEB-087, render the directory's own one-line summary

### Chat request path (OBSERVED from code; no provider credential here)

For a tool-free "hi" on the inline path the server awaits, in order: identity
verification (Clerk, twice on some paths), plan and entitlement gates,
organisation policy, credit reservation, the connector permission set and tool
catalogue (even when no tool is in play), context assembly, routing, then the
provider call. About 48 ordered steps, 14 to 18 Postgres round trips (two writes),
7 to 9 Redis calls, no Stripe in the hot path. Already skipped for a trivial
turn: attachment hydration, MCP context, past-chat recall, memory enrichment,
compaction and the secret-policy read. Deadlines from `deadline-policy.ts`: 40 s
turn first-token budget, 25 s provider first token, 240 s stream, 300 s function,
10 s per durable world call, 2 s durable first-event budget charged ahead of the
inline fallback.

The server sends no byte before the provider's first token. The adapter factory
awaits the first stream chunk so a provider error can become a real HTTP status
and failover can rotate before anything is committed; the `Response` is built
after that peek. T7 therefore equals T6 and the heartbeat cannot say
"connected". Changing that is a protocol decision (WEB-053), not a bug fix.

### Streaming render path (OBSERVED, with MEASURED tests read, none run against a provider)

- Token deltas are coalesced per animation frame with a catch-up window; a whole
  turn of deltas becomes one store write (`useChatStream.frame-batching.test.tsx`).

  after paint and never on the tail; mermaid and KaTeX are gated; one streaming
  cursor; no typewriter or artificial delay anywhere (grep for `setTimeout`,
  `charDelay`, `tokenDelay` in the streaming path returns nothing of the kind).

## The final question

If AGI Workforce opened to thousands of public users tomorrow, what would make
the website feel unfinished, unreliable, generated, confusing, slow or hard to
navigate?

Before this pass: every click between marketing pages blanked the screen to a
spinner; typing `/register` or `/sign-in` showed a loading shell for a second
before landing; a missing page said "not found" with a 200; every legal page
downloaded the chat runtime; the homepage promised a receipt the product does
not print and drew a price it does not charge; three pages said VS Code runs
BYOK today; the mobile drawer closed from a 16px target; toasts were light in
dark mode; the send button ignored the user's accent; a fullscreen artifact could
trap a keyboard user; footer links were too small to hit; the sitemap, the beta
programme and the support page were unreachable; a short answer from a fast
model showed nothing until it finished.

Those are fixed here and verified as far as a signed-out build allows. What is
left that a user would still feel: public pages are heavier than they should be
(WEB-010); the composer's own code disagrees with the target it names (WEB-052);
between 769 and 899 pixels the chat shell clips (WEB-050); nine dialogs do not
manage focus (WEB-040); support is an email address (WEB-031); the first token's
arrival is not measured, so the fast-model promise is an assertion (WEB-020);
and `/docs` looks like a different product (WEB-062). None of them adds anything
to the new-chat screen, which stays a greeting and a composer.
