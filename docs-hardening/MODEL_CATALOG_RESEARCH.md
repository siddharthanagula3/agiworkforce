# Model Catalog: Single-Source-of-Truth — Research Report

Generated 2026-05-29 via deep-research harness (100 agents, adversarially verified). Branch: hardening/execution-2026-05-28.

## Summary

The best multi-provider tools converge on a HYBRID model-catalog architecture: a single schema-validated, hand-curated DATA catalog (TOML or JSON) is the canonical source for the metadata that provider /models endpoints omit (pricing, context window, capabilities/modalities), and it is distributed as one generated JSON file fetchable at runtime/build — optionally layered over live provider/gateway discovery. The two de-facto community sources are models.dev (per-provider TOML compiled to a single hosted api.json; the source opencode/AI-SDK consume) and LiteLLM's single model_prices_and_context_window.json (one flat object keyed by model ID, ~41k lines, runtime-syncable from GitHub for "day-0" zero-downtime updates). Capability/modality flags in these catalogs (supports_vision, tool_call, reasoning, etc.) enable capability-based selection instead of hardcoded named-model literals. For a polyglot TS+Rust monorepo, the proven pattern is JSON-as-canonical-single-source plus build-time embed/codegen (e.g. Rust include_str!+serde, or quicktype generating both a TS type and a Rust struct from one JSON/JSON Schema input committed to the repo). CRUCIAL repo-specific finding: this monorepo has ALREADY built that bridge — apps/cli/src/model_catalog.rs already consumes packages/types/src/models.json via include_str! + serde_json in a 4-tier design (bundled JSON -> disk cache -> models.dev/api.json -> user config) that mirrors industry best practice, and a CI lint already exists — so the remaining work is duplication cleanup and widening enforcement, NOT building the bridge.

## Findings (verified)

### [high] The industry best practice is a HYBRID: a hand-curated, schema-validated static DATA catalog is canonical for pricing/context/capability metadata (which provider /models endpoints omit), distributed as one generated JSON file, optionally layered over live discovery. models.dev and LiteLLM's JSON are the two de-facto community sources.

**Evidence:** models.dev stores per-provider TOML files (providers/{id}/provider.toml + models/{model-id}.toml), validated by a GitHub Action against a Zod schema, then a generate() function compiles them into a single static api.json served at https://models.dev/api.json (static-source + generated-distribution hybrid). models.dev README: 'The data is stored in the repo as TOML files; organized by provider and model.' LiteLLM keeps ONE file, model_prices_and_context_window.json (~41,346 lines, 1.41MB) at the BerriAI/litellm repo root, and pulls 'the latest model data from GitHub at runtime' so admins can 'add day-0 support for new models without restarting your service' (zero downtime), with a bundled \*\_backup.json offline fallback and LITELLM_MODEL_COST_MAP_URL to override the source. Both deliberately hold the pricing/context/capability metadata that provider /models APIs usually do not return.

**Sources:** <https://github.com/sst/models.dev>, <https://github.com/anomalyco/models.dev>, <https://github.com/BerriAI/litellm/blob/main/model_prices_and_context_window.json>, <https://docs.litellm.ai/docs/proxy/sync_models_github>

### [high] These catalogs encode the full per-model metadata set needed to eliminate hardcoding: identity (id/provider/mode), capacity (context window, max input/output tokens), pricing (input/output/reasoning/cache-read/cache-write/audio per-token costs), capability flags, input/output modalities, lifecycle dates (knowledge cutoff, release, deprecation), and open-weights status.

**Evidence:** models.dev schema defines cost.{input,output,reasoning,cache_read,cache_write,input_audio,output_audio}, limit.{context,input,output}, modalities.input/output (text/image/audio/video), capabilities {attachment,reasoning,tool_call,structured_output,temperature}, knowledge cutoff, release_date, last_updated, status (active/deprecated/experimental/archived), open_weights. LiteLLM's file is one flat JSON object keyed by model-ID string (e.g. 'anthropic.claude-3-5-sonnet-20241022-v2:0'), each value bundling litellm_provider, mode, input_cost_per_token, output_cost_per_token, cache_read_input_token_cost, cache_creation_input_token_cost, max_input_tokens, max_output_tokens, and a deprecation_date. Both carry per-million-token pricing, not per-1k (the models.dev README is explicit).

**Sources:** <https://models.dev/model-schema.json>, <https://models.dev/api.json>, <https://github.com/BerriAI/litellm/blob/main/model_prices_and_context_window.json>, <https://docs.litellm.ai/docs/provider_registration/add_model_pricing>

### [high] Capabilities and modalities are stored as explicit per-model boolean flags, which enables capability-based selection instead of hardcoded named-model selection — and the tools actually USE these flags for selection.

**Evidence:** LiteLLM's file carries 26 distinct supports\_\* boolean keys including supports_vision, supports_function_calling, supports_prompt_caching, supports_reasoning, supports_audio_input, supports_pdf_input, supports_response_schema, supports_tool_choice, supports_computer_use, supports_web_search. It ships matching helper functions litellm.supports_vision(model), supports_function_calling(model), supports_computer_use() and a /model_group/info endpoint exposing the flags — i.e. capability lookup, not name matching. This is the concrete pattern for 'capability-based selection instead of named-model literals' the question asks about.

**Sources:** <https://github.com/BerriAI/litellm/blob/main/model_prices_and_context_window.json>

### [high] Vendors increasingly expose hosted catalog APIs and dynamic-discovery endpoints so the catalog can be fetched at runtime/build rather than hardcoded — but these hosted catalogs measurably LAG for brand-new models, which is the central tension with the 'models ship weekly' requirement.

**Evidence:** LiteLLM now offers a free hosted Model Catalog API at api.litellm.ai serving pricing/context/capabilities for 2,500+ models, queryable via GET /model_catalog (filters like ?provider=openai&supports_vision=true) and /model_catalog/{model_id}; live-verified returning per-model id/provider/pricing/context/flags. BUT a commenter (maxrabin, April 14 2026) reported the hosted catalog was 'out of date' — missing pricing for Opus 4.6 and not differentiating AWS Global vs Regional inference profiles — with no in-thread maintainer reply on update frequency. Staleness of hosted/community catalogs for week-old models is the recurring weak point.

**Sources:** <https://github.com/BerriAI/litellm/discussions/21029>, <https://api.litellm.ai/model_catalog>

### [high] Where /models endpoints DO return rich metadata, OpenRouter is the strongest example: GET /api/v1/models returns id, canonical_slug, context_length, a full pricing object, an architecture object with input/output modalities, and a supported_parameters array — so for OpenRouter the gateway itself is the catalog.

**Evidence:** Live curl (2026-05-29) returned 357 models; each carries id, name, canonical_slug, context_length, created, knowledge_cutoff, expiration_date; a pricing object with prompt/completion (per-token) plus input_cache_read, input_cache_write, image, audio, web_search, internal_reasoning; an architecture object with input_modalities/output_modalities (text/image/file/audio/video) and tokenizer; and a supported_parameters array listing tools, reasoning_effort, web_search_options, etc. This contrasts with OpenAI /v1/models (no pricing/context/limits) and is why aggregator catalogs exist for most providers.

**Sources:** <https://openrouter.ai/docs/api/api-reference/models/get-models>, <https://openrouter.ai/api/v1/models>

### [high] Vercel AI Gateway is the cleanest dynamic-fetch model: a no-auth public REST endpoint serves the whole catalog in one payload, and the AI SDK exposes getAvailableModels() for programmatic type/capability-based selection rather than named-model literals.

**Evidence:** Live curl (no auth, even with a bogus bearer token) returned HTTP 200 and 276 models; each carries id, context_window, max_tokens, a type enum (language/embedding/reranking/image/video), capability tags (reasoning/tool-use/vision/file-input), and detailed pricing (input/output/input_cache_read/input_cache_write/image/web_search plus tiered arrays). The AI SDK's gateway.getAvailableModels() returns id/name/description/pricing/modelType and the docs demonstrate model: availableModels.models[0].id and models.filter(m => m.modelType==='language') — concrete indirection away from hardcoded IDs.

**Sources:** <https://vercel.com/docs/ai-gateway/models-and-providers>, <https://ai-gateway.vercel.sh/v1/models>

### [high] For a polyglot TS+Rust monorepo, the proven single-source pattern is JSON/JSON-Schema-as-canonical committed to the repo, with build-time codegen into both a TS type and a Rust struct (quicktype) and/or a Rust build-time embed (include_str! + serde).

**Evidence:** quicktype 'generates strongly-typed models AND serializers' (not just type shells) from JSON/JSON Schema/TypeScript/GraphQL into 19+ targets that include BOTH Rust and TypeScript, so one canonical input emits a TS type and a Rust struct that serialize to the same JSON. Its documented recommended workflow is exactly the SSOT pattern: 'generate a JSON schema from sample data... commit the schema to your project repo, then generate code from the schema as part of your build process.' This is the polyglot answer; the lighter-weight alternative (used by this repo) is to skip codegen and have Rust embed the JSON directly via include_str! + serde_json::from_str.

**Sources:** <https://github.com/glideapps/quicktype>, <https://quicktype.io/rust>
