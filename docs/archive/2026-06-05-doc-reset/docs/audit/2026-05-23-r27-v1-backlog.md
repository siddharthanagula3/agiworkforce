## Section 2 — InviteCodeModal Prerequisite Spec

### 2.1 Critical schema gap (Stage 0 blocker discovered during synthesis)

`apps/desktop/src/services/waitlistService.ts:114-158` reads `beta_invites` table. `waitlistService.ts:160-206` reads `beta_redemptions`. **Neither table is created in any migration** — the only reference is in `supabase/migrations/20260509000007_drop_authrole_compound_policies.sql:21,63` (a policy-drop comment, not a CREATE TABLE). Result: every call to `validateInviteCode()` and `redeemInviteCode()` will fail with `relation "beta_invites" does not exist`. **Stage 0 must add the schema migration before any modal can function.**

### 2.2 Reconciliation with existing `CloudWaitlistSheet`

Mobile already ships `apps/mobile/src/features/waitlist/CloudWaitlistSheet.tsx` (waitlist-only sheet, 3-state machine, `useThemeColors()`-compliant). The v1-cloud-bridge lock copy ("Cloud features are gated for v1. Join the waitlist, or enter your invitation code below.") implies **one modal with two actions**, not two separate components.

**Recommended stance (Option A — Unified Component):**

- Build new `InviteCodeModal` as a **two-tab unified component** ("Join Waitlist" tab + "Enter Code" tab).
- Mobile's `CloudWaitlistSheet` becomes the "Join Waitlist" tab content — extracted to a sub-component and reused.
- Other surfaces (desktop, web, chrome-ext, vscode-ext) port the unified modal from desktop canonical.
- Rationale: lock copy is unambiguous about one modal; deprecation cost on mobile is low (1 component already abstracted via `onSubmit` prop).

**Alternative stance (Option B — extend `CloudWaitlistSheet`):** rename mobile component → canonical; other surfaces port from mobile. Lower duplication but goes against team-lead's stated preference for desktop canonical.

**Decision:** Option A unless user overrides. The component lives at:

```
apps/desktop/src/features/cloud-bridge/InviteCodeModal.tsx
```

(creating a new `cloud-bridge/` feature dir; sibling to existing `cloud/CloudStoragePanel.tsx`).

### 2.3 Modal copy (verbatim per lock)

Per `memory/locks/v1-cloud-bridge-strategy-2026-05-23.md` §"Implementation pattern":

> Title: **"Cloud features"**
>
> Body line 1: **"Cloud features are gated for v1. Join the waitlist, or enter your invitation code below."**

### 2.4 Props + events contract

```ts
interface InviteCodeModalProps {
  /** controlled visibility */
  open: boolean;
  /** caller closes after successful redeem or user cancel */
  onClose: () => void;
  /** which entry point opened the modal — used for waitlist `source` analytics + post-redeem routing */
  source:
    | 'connectors'
    | 'shared-links'
    | 'team-plan'
    | 'cloud-history'
    | 'research-panel'
    | 'cloud-sync'
    | 'web-search'
    | 'computer-use'
    | 'quick-mode'
    | 'other';
  /** default open tab; entry points like "Team plan" land on invite-code, others on waitlist */
  defaultTab?: 'waitlist' | 'invite-code';
  /** callback after successful redeem so caller can refetch features */
  onRedeemed?: (planTier: 'free' | 'pro' | 'enterprise') => void;
  /** callback after successful waitlist signup */
  onWaitlisted?: (rank: number) => void;
}
```

Tab-internal events emit to caller via the two callbacks. No internal navigation router — modal is a leaf.

### 2.5 Validation flow

**Client-side (basic):**

- Email regex `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` (mirrors `CloudWaitlistSheet.tsx:71`)
- Invite-code: trim, uppercase, length check (>= 6 chars).

**Server-side (enforced):**

- `waitlistService.validateInviteCode(code)` queries `beta_invites` on `code` + `is_active = true`; checks `expires_at` + `current_uses < max_uses`.
- `waitlistService.redeemInviteCode(code, userId)` inserts into `beta_redemptions` (unique constraint prevents reuse) and updates `subscriptions.plan_tier` + `status = 'trialing'`.
- **Anonymous redeem path:** for v1 local-only users without a `userId`, redemption requires Supabase anonymous sign-in first — this is a Stage 0 sub-dependency.

### 2.7 Dependencies (Supabase)

New migration `supabase/migrations/2026MMDD_beta_invites.sql`:

```sql
CREATE TABLE public.beta_invites (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    code text NOT NULL UNIQUE,
    plan_tier text NOT NULL DEFAULT 'free' CHECK (plan_tier IN ('free','pro','enterprise')),
    trial_days int NOT NULL DEFAULT 0,
    discount_percent int NOT NULL DEFAULT 0,
    stripe_coupon_id text,
    max_uses int NOT NULL DEFAULT 1,
    current_uses int NOT NULL DEFAULT 0,
    expires_at timestamptz,
    is_active boolean NOT NULL DEFAULT true,
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE public.beta_redemptions (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    invite_id uuid NOT NULL REFERENCES public.beta_invites(id),
    user_id uuid NOT NULL REFERENCES auth.users(id),
    redeemed_at timestamptz NOT NULL DEFAULT now(),
    UNIQUE (invite_id, user_id)
);
```

RLS: `beta_invites` anon `SELECT` by `code` only; `beta_redemptions` authenticated `INSERT WITH CHECK (auth.uid() = user_id)`; service-role full manage. Trigger to bump `beta_invites.current_uses` on each `INSERT` into `beta_redemptions`.
