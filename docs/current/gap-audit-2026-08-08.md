**Repository:** `siddharthanagula3/agiworkforce`  
**Audit snapshot:** opened 2026-08-08, every item revalidated against the working tree on 2026-08-16. Items proven fixed are deleted rather than annotated; partially-fixed items describe only what is still wrong.  
**Primary baseline:** the supplied full-stack AI terminology/architecture map, the repository's current source, current GitHub Actions state, `audit/capability-gaps.csv`, `docs/current/parity-implementation-matrix.md`, and current implementation files.

> This is an evidence-led gap plan. It distinguishes:
>
> - **CONFIRMED** — visible in current source or current GitHub Actions.
> - **TRACKED** — recorded by the repository's own gap ledger but not independently revalidated on the current head.
> - **CONFIGURATION / LIVE-PROOF REQUIRED** — code exists, but production configuration or a live end-to-end proof cannot be established from the repository.
> - **DEFERRED / NOT PLANNED** — an explicit product decision, not an accidental omission.
> - **STALE** — an older audit entry contradicted by newer code or newer repository documentation.

## 1. Executive Verdict

AGI Workforce is not primarily suffering from missing breadth. It already contains six client surfaces, extensive provider/model infrastructure, local and cloud runtimes, tools, MCP, agent execution, billing, database migrations, release workflows, and a large test suite.

The main gaps are:

1. **Production closure is not reliable.** The latest `main` CI is red, downstream E2E jobs are skipped, and production promotion for the same SHA is skipped.
2. **The CI graph hides independent evidence.** Every expensive E2E lane depends on one large `check` job, so a native-test failure prevents web, mobile, desktop, Chrome, VS Code, and cross-platform lanes from running.
3. **Security gates are not fully blocking.** Semgrep is advisory with a documented pre-existing backlog; some Rust advisory policy is also nonblocking.
4. **Durable automation is below the product promise.** User schedules run only daily and claim at most ten due tasks across the whole deployment per invocation.
5. **The connector framework is more complete than the connector product.** The OAuth broker deliberately ships with zero configured providers; most catalog entries are unavailable until an operator supplies endpoints, credentials, and MCP mappings.
6. **Security-sensitive AI artifacts are correctly blocked, but not redesigned.** CAP-052 has a repository-authored NO-GO review covering anonymous wallet DoS, origin/auth contradictions, capability copying, idempotency abuse, and a fail-open concurrency limiter.
7. **Policy storage and policy enforcement are not consistently the same thing.** Browse-domain rules, tenant restrictions, extension access, plugin governance, and reasoning-effort access are tracked as incomplete.
8. **The repository's source-of-truth system is not trustworthy enough for autonomous agents.** Current files contradict one another; several open gap rows are already cut or shipped, while README claims and root links remain stale.
9. **The runtime is broad but fragmented.** Desktop, CLI, web, extensions, and hosted runtime paths still contain duplicate orchestration/provider/MCP behavior and independently evolving semantics.
10. **Several customer-facing capabilities remain partial across surfaces.** Files, connected sources, memory scope, artifacts, research, voice, remote control, reauthentication recovery, and workspace/navigation primitives do not yet have consistent end-to-end behavior.
11. **Enterprise sale blockers remain intentionally deferred.** SAML/SCIM, residency, CMEK, IP allowlists, compliance export, tenant governance, organization analytics, and organization switching are not current-alpha blockers, but they are enterprise blockers.

The correct next move is not another breadth pass. It is a **truth reset followed by production-gate closure, core-runtime closure, and only then surface parity/expansion**.

4. Make the step exit nonzero for unsuppressed findings once the backlog is zero.

**Acceptance**

### GAP-P0-007 — Scheduled tasks are degraded to one daily batch of ten runs

### GAP-P0-007 — Scheduled tasks are capped at fifty runs per day for the whole deployment

**Status:** CONFIRMED  
**Evidence paths:** `vercel.json`, `apps/web/app/api/cron/run-schedules/route.ts`, `packages/contracts/types/src/billing-catalog.ts`

Current behavior:

- `run-schedules` fires once per day.
- One invocation drains at most `PLATFORM_SCHEDULE_RUNS_PER_SWEEP` (50) due runs, in waves of ten — a ceiling shared across every user on the deployment, so the platform executes at most fifty scheduled runs per day.
- The handler has a 60-second limit and a 55-second sweep budget; when the budget runs out it logs that schedules are still due and returns.
- `expire-support-handoffs` also runs once per day, so expired support handoffs may remain visible for up to a day.

Durable claims with leases, attempt counts, and idempotency-keyed replay exist in the schedule service. What is missing is cadence: a single daily sweep with a fifty-run platform ceiling cannot support a serious scheduled-task product.

**Required work**

Choose one production architecture:

1. Move recurring scheduling to a durable queue/workflow system; or
2. Upgrade hosting and restore appropriate cadence while keeping the existing claim/lease semantics.

Then add:

- retry with exponential backoff,
- dead-letter handling,
- per-tenant fairness,
- missed-run policy,
- concurrency control,
- schedule time-zone/DST tests,
- latency SLO and backlog alerting.

**Acceptance**

- A user schedule runs within the documented tolerance.
- A backlog larger than one sweep cannot starve indefinitely.
- Failed tasks retry and eventually enter a visible dead-letter state.
- Users can inspect last run, next run, failure, and retry state.

**Required work**

**Acceptance**

### GAP-P1-002 — Durable job execution lacks a complete retry/DLQ model

There is no canonical durable task model. Several per-domain durable executors exist, each with its own table and status set:

- Schedules — `apps/web/db/neon/0057_durable_scheduling.sql` adds `scheduled_for`, a unique `idempotency_key` per task, `lease_expires_at`, and `attempt_count`; `apps/web/lib/services/schedule-service.ts` claims runs, reclaims expired leases, and finalizes to `running|success|failed|timeout|cancelled`.
- Video generation — `apps/web/db/neon/0105_durable_video_generation_jobs.sql` and `apps/web/lib/server/video-generation-jobs.ts` carry idempotency keys, reconcile claim leases, `reconcile_failures`, `next_attempt_at` backoff, and cancellation.
- Cloud agent execution operations — `apps/web/db/neon/0063_cloud_agent_execution_operations.sql` carries lease token/expiry invariants and `running|completed|failed|outcome_unknown`.

What is still missing:

- No dead-letter path anywhere. No `dead_letter` or `blocked` state exists in any table, and no DLQ inspection or replay control exists in any surface.
- Schedule runs never retry. A failed or timed-out run is finalized terminally with no retry schedule and no backoff, despite `attempt_count` being persisted.
- No shared model. Exports, connector refresh jobs, and long-running research/artifact work are not covered by any of the durable tables above, so compensation state, cancellation tokens, and correlated trace/usage/audit IDs are per-domain at best.

**Required work**

Define a canonical durable task model with `queued`, `leased`, `running`, `blocked`, `succeeded`, `failed`, `dead_letter`, `canceled`, plus attempt count, lease owner and expiry, idempotency key, retry schedule, last error, cancellation token, compensation state, tenant and user context, and trace and audit IDs. Use it for cloud agent runs, schedules, triggered tasks, refresh jobs, exports, and long-running artifact/research work.

**Acceptance**

- Poison jobs enter DLQ with inspection/replay controls.
- A failed schedule run retries on a backoff schedule before becoming terminal.
- Every task is correlated to trace, usage, and audit records.

### GAP-P1-005 — Memory lacks complete project scoping and source suppression

**Status:** TRACKED (partial)
**Evidence paths:** `apps/web/lib/services/managed-memory-context-service.ts`, `apps/web/app/api/llm/v1/chat/completions/lib/request-processor.ts`, `apps/web/db/neon/0010_memory.sql`, `apps/web/db/neon/0006_projects.sql`

Account memory has global/profile scope, provenance columns, a read/write policy, soft deletion, and a user-visible exclusion list. Three things remain wrong.

**Exclusions do not apply to retrieval.** `isMemoryExcluded` runs only inside `persistManagedAutoMemoryFacts`, which suppresses _new_ auto-extracted facts. `loadManagedMemoryContext` selects on `user_id` and `is_deleted` alone, and `enrichManagedMemoryContext` injects the result into the system prompt unfiltered. Any memory stored before the user added the term still reaches the model.

**Suppression is term-based, not source-based.** `user_memories.source` is written but never used as a filter, so a user cannot suppress an entire source.

**There is no project/workspace memory scope.** `user_memories` has no `project_id` and `user_projects` has no memory-scope setting, so a project cannot exclude global memory or hold memory of its own. The only project-scoped memory in the repo is the desktop-local Tauri store keyed by `project_folder`, which is disconnected from cloud memory.

**Required work**

- Apply the exclusion list at retrieval, not only at write.
- Add source-level suppression keyed on the stored `source`.
- Add a project/workspace memory scope, with an explicit per-project switch to exclude global memory, enforced in the retrieval query.
- Add cross-tenant and cross-project leakage tests.

**Acceptance**

- A project can exclude global memory.
- A user can suppress a source and prove it is absent from retrieval, including for memories stored before the suppression.
- Every inserted memory has provenance and scope.
- Deletion propagates to indexes and caches.

The repository contains separate implementations for desktop, CLI, web, extension, and hosted paths. The VS Code surface primarily uses the CLI app-server while retaining another provider-stream path. Desktop and CLI own substantial Rust runtime/MCP/provider logic independently.

### GAP-P1-010 — Production sandbox isolation depends on deployment configuration

**Status:** CONFIGURATION / LIVE-PROOF REQUIRED  
**Evidence path:** `apps/web/lib/artifact-sandbox.ts`

The code supports a dedicated cross-origin renderer when `NEXT_PUBLIC_SANDBOX_ORIGIN` is configured and a safer `srcDoc` fallback without `allow-same-origin` when it is not. Parent and renderer already authenticate `postMessage` by exact origin (`isFromSandbox`, `postRenderToSandbox`, and `isAllowedParent` plus the `event.source !== window.parent` check in `infrastructure/sandbox/index.html`), and the published renderer exposes no privileged bridge.

The remaining gap is proof:

- correct production origin — `NEXT_PUBLIC_SANDBOX_ORIGIN` appears in `scripts/env-doctor.mjs` only under `urlKeys`, which validates format when the key is present; it is on no required list, so a production deploy without it silently degrades to the same-origin `srcDoc` fallback,
- CSP — `apps/web/proxy.ts` appends the sandbox origin to `frame-src` and the renderer ships its own CSP meta, but no browser test asserts either, and `apps/web/e2e/` contains no sandbox spec,
- deployment smoke — nothing fails or warns when the origin is absent.

**Acceptance**

- Production uses the dedicated sandbox origin for executable artifacts.
- CSP and connect-src are verified in a browser test.
- A deployment check fails when the required origin is absent.

### GAP-P1-011 — Moderation remains below a scored, auditable policy system

**Status:** TRACKED  
**Evidence path:** `audit/capability-gaps.csv`, CAP-024

Text moderation is weight-scored rather than toggle- or match-only: `apps/web/lib/moderation/text-classifier.ts` accumulates per-rule weights against module-level block and flag thresholds after normalizing zero-width characters, combining marks, letter separators and confusables, and `moderateManagedPrompt` hard-blocks pre-flight with a 422 before any provider call.

**Required work**

The scored classifier still lacks the policy system around it:

- versioned policy — no policy version exists anywhere in the repo, so no decision records one,
- category scores in the record — `ModerationEvent` carries categories and rule IDs but not the score, and the classifier emits one aggregate score rather than per-category scores,
- tenant/user policy thresholds — the block and flag thresholds are module constants and `moderateManagedPrompt` performs no policy lookup,
- appeal/review state,
- durable audit events — `recordModerationEvent` only writes a logger line; nothing is persisted, so threshold and policy changes are not auditable,
- offline/online evaluations and false-positive / false-negative monitoring — no evaluation sets exist for prompt injection, exfiltration, harmful actions or benign edge cases,
- tool/action moderation distinct from content moderation — the only call sites score prompt text and upload hashes; no tool-call or action path is evaluated.

**Acceptance**

- Every moderation decision records policy version and category scores.
- Tool/action moderation is distinct from content moderation.
- Threshold changes are auditable.
- Evaluation sets cover prompt injection, exfiltration, harmful actions, and benign edge cases.
