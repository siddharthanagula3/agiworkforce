# Public-Alpha Cutover Runbook (private beta → public alpha)

Status: Active · founder decision 2026-06-28
Owner: Founder
Decision: **Web + Mobile managed cloud go public alpha now. Desktop cloud is a fast-follow** — wire it to the same shared backend as web (DESK-CLOUD below), then flip its copy. Until DESK-CLOUD verifies, desktop shows honest interim copy (PA-3), never "available." Desktop keeps Local + BYOK throughout. Resolves DESK-CLOUD-COPY-01.

Why desktop is a fast-follow, not "never": the Rust `ERR_CLOUD_NOT_IMPLEMENTED` in `cloud.rs:42` is an orphaned placeholder (no caller); cloud was always meant to go through the web API boundary. Streaming is already shared (`packages/llm-runtime`) and desktop already has Cloud-mode plumbing + auth + egress guard, so desktop cloud ≈ web cloud. The only missing piece is the persistence client (web-only today).
Companion: `docs/spec/AGI_CODE_MASTER_SPEC.md` (invariants), `11-execution-playbook.md` (loop), `03` (risks).

Guardrail (non-negotiable): never claim a surface's managed cloud is "available" where its runtime doesn't serve. Copy ≤ shipped scope. The kill-switch `AGI_MANAGED_COMPUTE_PRIVATE_BETA` stays as the instant rollback.

## DESK-CLOUD — fast-follow: desktop cloud on the shared backend (then flip desktop copy)

Goal: desktop Cloud mode uses the **same backend as web** (the "one logical cloud" invariant), so desktop managed cloud is genuinely public alpha. Local + BYOK stay on the Rust runtime untouched.

Grounded scope (verified 2026-06-28):

- Cloud **streaming** already shared — `packages/llm-runtime` (gateway/retry/history). Reuse as-is.
- Cloud **persistence** is web-only — `apps/web/features/chat/hooks/use-chat-persistence.ts` → relative `/api/chat/conversations*`. This is the piece to share.
- Rust `apps/desktop/src-tauri/src/sys/commands/chat/cloud.rs:42` is an orphaned placeholder — cloud goes via the web API boundary, not Rust.
- Desktop already has Cloud-mode plumbing + Clerk auth (`features/auth`) + `lib/egressGuard.ts`.

**DCL-1 realignment — DONE (2026-07-03, desktop-engineer):** the 2026-07-03 correction note above understated the gap — the shared client (`packages/unified-chat/src/lib/cloud-chat-persistence-client.ts`) had conversation CRUD (create/get/update/delete/list, extracted from the dead `use-chat-persistence.ts` hook) but **no message-persistence method at all** (that hook's `saveMessages()` is a no-op, so nothing to extract). Added `saveMessage(conversationId, message, options?)` mirroring `useChatStream.ts`'s `saveMessageToDb()` exactly: same route (`POST /api/chat/conversations/:id/messages`), same body shape (`id, role, content, model, metadata, skipLlm: true`), same retry policy (3 attempts, `350ms * attempt` backoff on network errors and 5xx only), same non-retry on 429/other 4xx, same id-extraction fallback (`data.message ?? data.userMessage ?? {id: clientId ?? randomUUID()}`), same error strings (`Failed to save message to DB: <status>`). Conversation CRUD methods were left as-is — not part of the gap. 34 new/updated unit tests added (`packages/unified-chat/src/lib/__tests__/cloud-chat-persistence-client.test.ts`), full package suite green (505/505). Scope decision: web's live `useChatStream.ts` was NOT migrated to the shared client in this pass — `saveMessageToDb` is a private, unexported-by-default function in a hook file touching the live, working web chat path; migrating it is a separate, riskier task than fixing the shared client's own correctness. Tracked as a follow-up, not attempted here. Minor unfixed divergence noted, not blocking: `createConversation`'s body includes a `mode: 'mission'|'chat'` field carried over from the dead hook's mission-store concept; the REAL `/api/chat/conversations` route's `CreateConversationSchema` has no `mode` field (zod strips unknown keys, so this is inert, not broken) and its response never echoes `mode` either (`mapRawConversation` always falls back to the `'chat'` default in practice). Low-risk, left alone to avoid scope creep on an interface used by both surfaces.

**DCL-3 — status correction (2026-07-03, desktop-engineer): both bullets were already substantially done, not "NOT done."** Re-verified against the current tree: (1) `apps/desktop/src/lib/egressGuard.ts`'s `guardedFetch` already blocks Local/BYOK (`isLocalMode()` → `isPrivateTrustBoundary()`) and allows Cloud/managed through to `OUR_CLOUD_HOSTS` (`agiworkforce.com`, `vercel.app`, `neon.tech`, `clerk.com`, `clerk.accounts.dev`); the egress contract test (`apps/desktop/src/__tests__/lib/cloudPersistenceEgress.contract.test.ts`) already existed and already covered createConversation/listConversations/deleteConversation for local/byok (blocked) and managed (allowed, host-scoped) — both landed in `9c8634f9b` ("dcl-2/dcl-3"). Extended it this pass to also cover the new `saveMessage` verb (blocked in local/byok, reaches only the cloud host in managed) so the newest verb isn't a coverage gap. (2) The Rust placeholder (`apps/desktop/src-tauri/src/sys/commands/chat/cloud.rs`) already carries a clear "DCL-3 — INTENTIONAL ABSENCE" doc comment (also from `9c8634f9b`) explaining cloud persistence goes through the TS/HTTP seam, not Rust. Verified it should NOT be removed: `apps/desktop/src/services/cloudChat.ts` still calls all six `cloud_*` commands, and `apps/desktop/src/stores/chat/chatStore.ts`'s `isCloudMode()` branches (create/load/rename/delete conversation, load messages) still call into `services/cloudChat.ts` — so it has live TS callers today (legacy/unreachable from the primary `TauriRuntime.ts` send/receive path, per `DESKTOP-CLOUD-MODE-SPEC-VS-REALITY-01`, but not zero callers); deleting it would break that legacy call chain at runtime (IPC "command not found" instead of the controlled `ERR_CLOUD_NOT_IMPLEMENTED`). Left in place with its existing doc comment. **DCL-3 is now complete** per the plan's acceptance criteria (egress test green for all persistence verbs incl. `saveMessage`; placeholder documented).

**CORRECTION (2026-07-03), load-bearing for DCL-1/DCL-2 as currently implemented:** `apps/web/features/chat/hooks/use-chat-persistence.ts` — the file DCL-1 (`b89ded8fe`) extracted from — is itself dead/unrouted code. It is consumed only by `apps/web/features/chat/pages/UnifiedChatPage.tsx` (mounted behind a `?unified=1` flag, commit `e599872cb`), which no `app/**/page.tsx` route renders; its own test (`chat-route.test.tsx`) asserts the real `/chat` routes render `WebChatPage.tsx` instead. `use-chat-persistence.ts`'s `saveMessages()` is in fact a hardcoded no-op. The REAL, live, shipping message-persistence path is `apps/web/lib/hooks/useChatStream.ts`'s `saveMessageToDb()` (`POST /api/chat/conversations/{id}/messages`, retry/backoff on 5xx/network errors, verified via a passing 10/10 vitest suite). DCL-1's shared persistence client was therefore built by extracting the wrong, non-shipping reference. DCL-2's desktop seam (built on top of DCL-1) inherits this — it is real, unit-tested, and architecturally sound, but does not actually mirror what web's live chat does today. Before DCL-3/DCL-4 proceed, DCL-1's extracted client needs realigning to `useChatStream.ts`'s actual request/retry shape, or DCL-4's cross-surface proof will fail (or worse, silently diverge from web's real behavior) the first time it's run against a real backend.
