## 2. Cloud runtime architecture

**One backend, three independent clients.** All three apps ultimately hit the same server endpoint, `POST /api/llm/v1/chat/completions` (Next.js route in `apps/web`), over SSE, but each app has its own client implementation — there is no shared "chat client" package across all three:

- **Web**: `apps/web/lib/hooks/useChatStream.ts` (1950 lines) — the actual production web chat hook. Calls the route directly, same-origin, cookie/CSRF auth.
- **Desktop**: `apps/desktop/src/api/cloudApi.ts` — HTTP client wrapping the same endpoint (`sendCloudMessage`), Bearer-token auth via `cloudAccountAuth` when Tauri (`cloudApi.ts:16,84-90`). Two `ChatRuntime` implementations consume it:
  - `apps/desktop/src/runtime/TauriRuntime.ts` — the runtime actually selected in production (`apps/desktop/src/App.tsx:29-30`, `isTauri ? TauriRuntime : WebRuntime`).
  - `apps/desktop/src/runtime/WebRuntime.ts` — despite the name, this is **desktop's own fallback runtime** for non-Tauri (browser-embedded) builds of the desktop codebase, NOT the real apps/web app. It imports the same `cloudApi.ts` (`WebRuntime.ts:29-33`).
  - `apps/desktop/src/runtime/CloudRuntime.ts` — a third, more complete `ChatRuntime` for desktop's future Managed-Cloud mode. **Confirmed dead code today**: its own header comment states "NOT WIRED INTO THE LIVE APP YET... the runtime-selection switch in App.tsx is a static `isTauri ? TauriRuntime : WebRuntime` with no cloud branch" (`CloudRuntime.ts:34-43`). This matches `docs/current/parity-implementation-matrix.md:199` ("Cloud mode onboarding... Coming soon (desktop)").
  - Desktop's actual Cloud-mode gate: `apps/desktop/src/stores/appModeStore.ts:189-217` `selectPrivacyMode()` can resolve to `'managed'`, but `apps/desktop/src/constants/cloudAvailability.ts:1-20` documents the Rust backend fails closed with `ERR_CLOUD_NOT_IMPLEMENTED` and "the desktop runtime must NEVER enter Cloud mode."
- **Mobile**: `apps/mobile/services/streaming.ts` — `streamChat()` (line 542) is the SSE consumer for the same `/api/llm/v1/chat/completions` endpoint (comment at line 535). Independent fetch/SSE-parsing implementation (`attemptStream`, `processSseLine`, lines 145-203) sharing no code with web or desktop's clients.

**Wire protocol** (shared shape, independently parsed by 3 clients — no shared parser package): delta types are `tool_calls` / `tool_status` / `tool_result` / `x_search_results` / `x_generated_files` / `x_tool_approval_request` / a `<thinking>` inline tag. Desktop's parser lives at `apps/desktop/src/runtime/cloudStreamDeltas.ts` (used by both TauriRuntime-adjacent and WebRuntime/CloudRuntime); mobile's equivalent types are `StreamDelta`/`StreamToolCallFragment`/`StreamToolStatus`/`StreamToolResult`/`StreamToolApprovalRequest`/`StreamGeneratedFile` (`apps/mobile/services/streaming.ts:33-104`). Server-side, these SSE events are emitted from `apps/web/app/api/llm/v1/chat/completions/lib/tool-loop.ts` (`toolStatusEvent:233`, `toolApprovalRequestEvent:269`, `generatedFilesEvent:297`, `toolResultEvent:316`, `fetchSourcesEvent:360`).

**Server-side tool loop** — `runToolLoop` (async generator, `tool-loop.ts:686`) is the single agent loop all providers route through. Per-call dispatch order (`runMcpTool`, `tool-loop.ts:520`):

1. Per-user **connector executor** (`ConnectorToolExecutor`, `tool-loop.ts:106`) — first-party GitHub built-in + operator-mapped remote MCP connectors, from `lib/user-connector-tools.ts`.
2. Fallback to the **operator MCP dispatcher** — `getWebMcpCatalog`/`executeWebMcpTool` from `apps/web/lib/mcp-tool-executor.ts` (`tool-loop.ts:49-55`).
3. **E2B code-execution tools** intercepted separately — `isExecutionTool`/`routeExecutionTool` (`lib/e2b/execution-tools.ts`), `getE2BExecutor`/`pauseE2BSession` (`lib/e2b/runtime.ts`) — never treated as a generic MCP tool (`tool-loop.ts:548-556`).

**Connectors/MCP routes**: `apps/web/app/api/mcp/route.ts` (connect-and-list a remote MCP server, SSRF-defended: stdio transports rejected outright, `route.ts:1-19`) and `apps/web/app/api/connectors/route.ts` (list/save/delete `user_connectors`; GitHub is backed by GitHub App installs, not `user_connectors`, `route.ts:9-17`). Both are gated by kill-switches, open by default (§5).

**E2B / code-execution gate** (`apps/web/lib/e2b/gate.ts`): `AGI_E2B_EXECUTION` env var, default OFF. When off, `resolveCodeExecutionTools()` is "native-always" (dormant path); when on, E2B tools are offered only on "streaming non-free-trial requests" per `tool-loop.ts:548-556`, and `getE2BExecutor()` explicitly fails "unavailable" if `E2B_API_KEY` is absent. Client-visible flag: `/api/me` → `feature_flags.code_execution = e2bCutoverEnabled()` (`apps/web/app/api/me/route.ts:89-97`), consumed by the composer's "Run code" toggle (`apps/web/features/chat/components/Composer/ChatComposerNew.tsx:365`) and mirrored into `apps/mobile/src/features/billing/store.ts:34`. **E2B/code-execution is explicitly excluded from the free-trial path** — this is a real, current free-vs-paid capability gap, distinct from the model-picker gaps in §4.

## 3. Model catalog semantics

`packages/types/src/models.json` (3641 lines) top-level: `providers` (20 provider configs), `models` (59 model entries, includes 4 `auto*` virtual models + chat + image + video + audio), `tierAllowedModels` (`{economy, pro_additions, flagship_additions}`), `modelPresets` (per-provider `{value,label}` lists used to build UI pickers), `providersInOrder`.

`tierAllowedModels.economy` = 10 models: `gpt-5-nano`, `gpt-4.1-nano`, `gemini-3.1-flash-lite`, `gpt-5.4-mini`, `deepseek-v4-flash`, `claude-haiku-4.5`, `qwen-3.5-plus`, `kimi-k2.6`, `glm-5.2`, `sonar`. `pro_additions` = 7 (`claude-sonnet-4.6`, `gemini-3.5-flash`, `gemini-3.1-pro-preview`, `deepseek-v4-pro`, `qwen-max`, `sonar-deep-research`, `gpt-5.5`). `flagship_additions` = 2 (`claude-opus-4.8`, `grok-4.3`). Every model in `economy` also carries a per-model `tierPolicy.minTier: "free"` field in `models.json` itself (e.g. `gpt-5-nano` at the top of the entry), but `model-catalog.ts:192-198` documents this per-model field as **INERT** — "Nothing derives `tierAllowedModels` from this yet — it is future GA-wave data. `tierAllowedModels` remains the SSOT."

**Two parallel, non-overlapping gating systems live in `model-catalog.ts` — both real, gating different features, easy to conflate:**

1. **`TIER_POLICIES`** (`model-catalog.ts:1078-1263`, keyed by `ProductTier = free|pro|max|enterprise`) — an auto-routing/slot system (`RoutingSlot`, `SLOT_REGISTRY`) referencing `tasks/auto-routing-spec.md` and a `parallel-spinning-hedgehog` plan. `free.manualModelSelection = false`, `free.surfacedUx = 'auto_only'`, `free.allowedSlots = ['workhorse_general']` only. `getTierPolicy()` / `canAccessManualModelSelection()` (`model-catalog.ts:1481-1487`) read this. **Verified consumer**: this powers ONLY the "Advanced mode" toggle — `apps/web/features/settings/components/AdvancedModeToggle.tsx:211-213` renders nothing at all (`return null`) unless `getTierPolicy(tier).manualModelSelection` is true, i.e. it is invisible to Free/Basic users and only appears for Pro/Max/Enterprise as a power-user override that bypasses auto-routing and lets the user pick directly from `SLOT_REGISTRY` entries. Exposed to the client as `/api/me` → `feature_flags.advanced_model_access` (`apps/web/app/api/me/route.ts:91`). **This is not the everyday chat model picker.**
2. **`tierAllowedModels` / `getAllowedModelsForTier()` / `isModelAllowedForTier()` / `canAccessModelForSubscriptionTier()`** (`model-catalog.ts:1578-1648`) — the economy/pro_additions/flagship_additions catalog groups. This is what every app's actual composer/chat model picker reads (directly or via a per-app wrapper), and it is where the founder's free-tier spec must be validated (§4). Note `canAccessModelForSubscriptionTier(modelId, 'free')` **unconditionally returns `false`** (`model-catalog.ts:1636`) — free-tier access to any named model is granted only through app-specific overlay logic layered on top (mobile's `FREE_TIER_ECONOMY_MODEL_IDS` mirror, web's `FREE_TRIAL_MODELS`), not through this function directly. Both apps' comments explicitly call out this mirroring requirement (e.g. `apps/mobile/src/features/model-picker/service.ts:88-96`).

Per-app resolution of catalog → user-facing picker (verified in each app's actual chat composer, not Settings pages — see §4 for why that distinction mattered during this audit):

- **Mobile**: `apps/mobile/src/features/model-picker/service.ts` — `CAPABILITY_PRESET_NAMES` (line 423-434) relabels model IDs to marketing capability names ("Thinking", "Super Fast", "Fast", "Coder", "Balanced", "Search") for Free/Basic; Pro+ sees real provider names (`tierShowsRealModelNames`, line 445-448).
- **Web**: `apps/web/features/chat/components/Composer/ComposerFooter.tsx` — always shows real model names (`AVAILABLE_MODELS` built from `MODEL_PRESETS` in `apps/web/shared/stores/model-store.ts:117-182`, no relabeling), gates selectability via `isModelSelectableForTier()` (`ComposerFooter.tsx:183-192`).
- **Desktop**: `apps/desktop/src/features/v3/ModelPopover.tsx` — the real composer picker (NOT `apps/desktop/src/features/settings/ModelSelector.tsx`, which is the separate Models & Keys/BYOK settings grid, also tier-gated via `isModelAllowedForTier` but a different UI surface entirely). ModelPopover has **no tier gating of any kind** — see §4.

That commit is confirmed present in the current HEAD (`git merge-base --is-ancestor 80567f06b HEAD` succeeds). **IDENTIFIED, NEEDS CONFIRMATION WITH PROD ENV ACCESS (not verified — I cannot read Vercel values)**: independent of the above, `apps/web/app/api/checkout/route.ts:23` does `new Stripe(requireEnv('STRIPE_SECRET_KEY'), ...)`, and `requireEnv` throws if the var is absent (based on reading its use elsewhere in the codebase, not independently re-reading its full implementation this pass). **`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` do not appear in the Vercel name list the founder pasted**, despite all three being the app's own declared `criticalVars` (`apps/web/lib/validate-env.ts:29-36`). _If_ that list is complete and current, checkout would throw the moment any signed-in user clicks "Get Pro"/"Get Max" (client sees `"Failed to create PRO subscription"`, `stripe-payments.ts:166-169`), and any successful payment wouldn't sync back to Neon (`stripe-webhook/route.ts:25-27` logs the same missing-config warning). ## Executive summary (for the orchestrator)

1. **The founder's free-tier model spec is met on Mobile, diverges on Web (by design or drift, undetermined), and is untested on Desktop because Desktop Cloud mode is confirmed-dead code today** (`CloudRuntime.ts` explicitly says so; `App.tsx` has no cloud branch). See §4 table.
2. **Two separate, non-overlapping tier-gating systems exist under confusingly similar names** — `TIER_POLICIES`/`manualModelSelection`/`getTierPolicy` gates only the Pro+ "Advanced mode" power-user toggle; `tierAllowedModels`/`getAllowedModelsForTier` gates the everyday model picker every app actually uses. This is resolved (not a bug) but is a real trap for future agents reading `model-catalog.ts` — the file's own comment at line 189-191 already flags the per-model `tierPolicy.minTier` field as inert/unused.
3. **Mobile shows two rows with an identical "Super Fast" label** (gpt-4.1-nano and gemini-3.1-flash-lite) for free users — confirmed via `ModelRow.tsx:151` rendering raw `model.name`. Allowed by the spec's "and/or" wording but worth a product decision on whether that's intended.
4. **Media generation has three independent, mutually-inconsistent tier gates** (web hardcoded set, desktop hardcoded substring match, and the correct `assertQuota`/`TIER_POLICIES` path used only by the chat tool-loop) — two of the three currently let Pro-tier users generate video despite `pro.allowVideoGeneration:false` in the canonical policy. (A suspected "GPT Image 2 sends Google's model ID to OpenAI" bug was investigated and found already fixed as of commit `fc75e11af`; the same stale pattern survives only in an unused parallel service with no live call sites — see §6.)
5. **Video generation is fully built server-side but has no UI trigger on web, a partial UI on desktop (no Runway option), and doesn't exist on mobile at all.**
6. **E2B/code-execution is explicitly excluded from the free-trial path** and off by default platform-wide (`AGI_E2B_EXECUTION`), consistent across all docs and code checked.
7. **Both "public alpha" kill-switches** (`AGI_MANAGED_COMPUTE_PRIVATE_BETA`, `AGI_WEB_MCP_PRIVATE_BETA`) are correctly open-by-default and consistent with `docs/current/source-of-truth.md`.
8. **Provider leaf packages are web-only in practice** — desktop and mobile never import `packages/providers/*` directly; the real multi-provider registry for anything server-side is `services/api-gateway`, a separate deployable.
9. **The "no Pro/Max plans on prod" hypothesis: live-checked and not reproduced today, but git history explains the likely timing.** `https://agiworkforce.com/pricing` signed out on 2026-07-11 renders Pro/Max/Team correctly with working CTAs (verified, not inferred). Commit `80567f06b` (2026-07-04) explicitly says it "opens stripe checkout for all tiers... superseding the old pro/max waitlist-only rule" — strong evidence the founder's report predates that fix. Separately (identified, **not** verified — I cannot read Vercel values or sign in to test checkout): `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` do not appear in the pasted Vercel list despite being the app's own declared `criticalVars` (`validate-env.ts:29-36`), and `instrumentation.ts` deliberately never throws on that failure at startup — if genuinely absent, checkout would silently break with no startup-level signal. This needs confirmation with actual prod env access; the pasted list may also be partial. The one fully-verified, unrelated production risk from this check: `agiworkforce.com` is currently running Clerk **development-mode** keys — flag this to the founder with equal or higher priority.
10. **Mobile's missing Pro/Max plans have a separate, fully-explained root cause**: `apps/mobile/lib/v1FeatureFlags.ts:60` deliberately hardcodes `billing: false` for v1 (by design, not a bug), and even if flipped on, the IAP product SKUs are explicitly documented as placeholders never created in App Store Connect/Google Play Console (`apps/mobile/src/features/billing/iapProducts.ts:4-7`). No Stripe or Vercel env var explains the mobile symptom.
11. **"Team" is a live, real, correctly-configured pricing tier** ($30/seat/mo on the current site), not a suspicious leftover — correcting the initial concern about `STRIPE_PRICE_TEAM_*`. Genuine env cleanup candidates instead: `AGI_DATABASE_PROVIDER`, `AGI_AUTH_PROVIDER`, `CLERK_AUTHORIZED_PARTIES`, and `NEXT_PUBLIC_SITE_URL` all trace to dead or effectively-inert code paths (§7.2).
