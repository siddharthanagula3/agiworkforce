# AGI Workforce Web — Live Audit (localhost:3000)

## RANKED FINDINGS (top issues first)

1. **[Demo-blocker] Search-toggle + immediate-send race condition freezes the UI and silently loses the conversation.** Toggling "Search" in the composer and sending in quick succession (e.g. via Cmd+Return) leaves the app stuck on the loading/greeting screen indefinitely with stale composer text and response text bleeding through behind it. Network logs show the backend actually created the conversation (even duplicated it — two `POST /api/chat/conversations` both 201'd) but the frontend never navigates to it, and after a reload the conversation is gone entirely with zero error shown to the user. Reproduced and isolated: a plain send without touching Search works fine every time. See section 6, Bug A.
2. **[Demo-blocker] Web search does not work at all.** Even when the Search toggle is clicked deliberately (with a pause, not combined with send) and the prompt explicitly asks to search the web, the model answers "I can't directly browse the live web" and zero network requests matching "search" fire. The plus-menu's own "Web search" entry is permanently greyed out too — consistent, not a fluke. If the founder plans to demo live web search, it currently does not work in this build. See section 6, Bug B.
3. **[Demo-blocker] Duplicate/ghost code-block rendering.** Any assistant response containing a code block renders it twice, stacked: a faded skeleton version with an uppercase "PYTHON" label sits directly above the final fully-rendered version. Confirmed persistent after streaming completes and after scrolling away and back — not a transient frame. Visibly broken-looking to anyone watching a live demo. See section 3.
4. **[Demo-blocker] "Delete project" shows a false success toast — no DELETE request is ever sent.** Confirmed twice: click Project settings > Delete project > confirm "Delete" in the modal, a green "Project deleted" toast appears, but the project remains in both the sidebar and the Projects list after a full page reload. Checked the complete network log across both attempts (filtered by project ID and by `/api/projects` broadly) — zero DELETE requests fired, only GETs. This is a data-integrity trust issue, not cosmetic: a user could believe they deleted a project (possibly containing sensitive instructions/files) when it's still fully present. Could not clean up my own test project ("QA Test Project (delete me)") because of this bug — left behind, needs manual DB cleanup. See section 9.
5. **[Demo-blocker] "Monthly credit allowance: $1,000,000.00" placeholder value on the real Usage settings page**, plus the Today/Week/Month usage bars permanently reading "0% used" against that fake allowance even when real spend and 159 real sessions exist. Usage data also doesn't auto-load on opening Settings (shows "0 sessions," "Last updated: Not loaded" until a manual Refresh). If a founder opens Usage to show real account activity, it looks broken/fake. See section 2.
6. **[Demo-blocker] Moonshot (Kimi K2.6) provider fails with a 401 authentication error** — "Moonshot authentication error (401): 401 Invalid Authentication" — despite being told the API key is live. Error is surfaced cleanly to the user (banner + inline message + retry hint), but the provider itself doesn't work. DeepSeek (V4 Flash), by contrast, works correctly and returns real DeepSeek responses. See section 9.
7. **[Noticeable] Backend "popular searches" endpoint throws a 500.** Opening the global Search Conversations modal triggers `[GlobalSearch] get_popular_searches failed: "Internal Server Error"` at `features/chat/services/global-search-service.ts:201` (caught via the Next.js dev error overlay, not shown to the user). Search itself still works once you type a query (tested: 5 real results returned correctly, clicking one navigates to the right chat), but the "popular/suggested searches" pre-fill silently fails every time. See section 9.
8. **[Noticeable] Invalid HTML / React hydration error on the Projects page.** `packages/unified-chat/src/components/ProjectCard.tsx` renders a `<button>` (line 95-98, the whole clickable card) containing a nested `<button>` (line 123, the star toggle) — `<button>` cannot be a descendant of `<button>` in HTML, and React logs a hydration-error console warning every time the Projects list renders. See section 9.
9. **[Noticeable] Local dev server returned persistent HTTP 503 after visiting `/projects`** (later resolved — team lead confirmed it was an external SIGTERM, not a code crash, and restarted it manually). Not a code bug, but flagging that the dev environment is fragile enough to need a manual restart mid-session.
10. **[Noticeable] Wrong upgrade nag for a Pro-plan account.** General/Profile settings shows "Upgrade for photo upload" and "Hosted cloud upgrade" gating badges on an account that is already Pro and active — should be unlocked. See section 2.
11. **[Noticeable] "Switch model mid-conversation?" dialog fires on a brand-new, empty chat** with zero message history, warning about re-processing "your conversation so far" at full price — nonsensical copy/timing for an empty chat. Reproduced 3 times (Claude, DeepSeek, Moonshot switches), consistent every time. See section 7 and 9.
12. **[Minor] Skills feature is a dead end.** Both the sidebar's top-level "Customize" entry and Settings > Customize > Skills route to a page that just says "No skills loaded in this environment" with no way to add any, despite billing itself as "Quick-access prompts and specialist AI agents for every domain." 13. **[Minor] No conversation branching feature found anywhere** (checked every message hover menu) despite being a common comparable-product pattern; may be intentional scope, flagging in case it's expected. See section 4.
14. **[Minor] `/artifacts` silently redirects to `/chat` instead of a clean 404** (unlike `/scheduled`, `/library`, `/agents`, which all correctly show a proper "404 Page Not Found" page). Minor inconsistency in how unbuilt routes fail. See section 9.

## 6. REAL CHAT TEST 3 — Web search prompt — DEMO-BLOCKER (two separate bugs)

**Bug A — Search toggle + immediate send causes a UI freeze and silent data loss.** Sequence: typed a prompt on the home/new-chat screen, clicked the "Search" toolbar toggle, then pressed Cmd+Return to send in the same batch of actions. Result: the UI never left the home/greeting screen. The loading spinner (top-left) spun indefinitely, the composer still showed the original typed text, and the assistant's response text rendered bled-through/overlapping behind the composer box instead of the conversation view taking over. Network logs showed the message was actually POSTed successfully server-side (two `POST /api/chat/conversations` both returned 201 — i.e., two conversations were created, likely a double-submit) but the frontend never navigated to the new chat URL and stayed stuck rendering the empty-state screen. After manually reloading `/chat`, the conversation was gone entirely from the sidebar (chat count did not increase) — the message and any response were silently lost with no error shown to the user. This is fully reproducible evidence, not a one-off: confirmed via network log + before/after sidebar chat counts. **This is a severe demo-blocker**: a founder toggling Search and hitting send while narrating to an investor would watch the app appear to hang and then lose the conversation.

- Isolated the cause by retrying without touching the Search toggle: a plain send worked perfectly (chat saved, real chat URL, correct response, chat count incremented as expected) — confirming the freeze is specifically triggered by the Search-toggle-then-immediate-send sequence, not chat sending in general.

**Bug B — the Search / web-search tool does not appear to be functionally wired up at all.** Retried cleanly: clicked the "Search" toggle by itself first (no visible active/highlighted state change after clicking — itself a minor UX bug, there's no clear on/off affordance), waited, then sent "Search the web: what is the current weather in San Francisco right now?" The assistant replied "I can't directly browse the live web or fetch real-time weather data from here" and suggested the user manually Google it — i.e., it behaved exactly as if Search were off. Checked network requests during this exchange: zero requests matching "search" fired. So either (a) the Search toggle doesn't actually flip any server-side flag, or (b) the flag is sent but the backend never invokes a real search tool. Consistent with the plus-menu's "Web search" entry being permanently greyed out (see Home/composer section above) — this points to a real, not-yet-wired-up feature rather than a fluke. **This alone is a demo-blocker** if the founder plans to show live web search to investors — the feature currently does not work at all in this build.
