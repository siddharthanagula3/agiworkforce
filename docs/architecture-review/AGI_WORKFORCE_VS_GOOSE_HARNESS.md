# AGI Workforce vs. Goose: Agent Harness Comparison

Status: Draft for team review
Scope: the _harness_ layer — tool loop, MCP, provider routing, retry/stopping conditions, permission gating — not chat UI
Compared: `/Users/siddhartha/Desktop/oss-references/goose` (Rust workspace, `crates/goose` core) vs `/Users/siddhartha/Desktop/agiworkforce` (`apps/desktop/src-tauri/src/core/{agi,llm,mcp}` + `apps/cli/src/{agent,mcp,provider.rs}`)

Goose is the right comparison, not Jan/LibreChat/Cherry Studio: it has an explicit first-class harness (`crates/goose`) consumed identically by a CLI (`goose-cli`), an HTTP server (`goose-server`, binary name `goosed`), and an Electron desktop client (`ui/desktop`) that talks to `goosed` over `http://127.0.0.1:$GOOSE_PORT` (`ui/desktop/src/main.ts:890`). AGI Workforce's closest analog is the harness code living inside `apps/desktop/src-tauri/src/core/{agi,llm,mcp}`, plus a second, independent harness inside `apps/cli/src/{agent,mcp,provider.rs}`.

## 1. Executive Summary

**AGI Workforce's harness is less mature than Goose's on code-sharing and MCP-client consolidation, roughly comparable on core loop mechanics (both have iteration caps, retry, and permission modes), and arguably ahead on two specific points: provider breadth via a single generic client, and defense-in-depth stopping conditions (wall-clock timeout in addition to iteration cap).**

Top 3 findings:

1. **Goose has one harness crate reused by two clients; AGI Workforce has at least three independently-written harness subsystems (agent loop, MCP client, provider client) duplicated across `apps/cli` and `apps/desktop`.** The only Cargo path dependency shared between `apps/cli` and `apps/desktop/src-tauri` is `agiworkforce-sandbox-policy`. Everything else — the tool-call loop, the MCP transport/protocol code, and the LLM provider clients — is written twice. `docs/agent-context/known-flaws.md` already tracks the identical pattern once (`EXEC-POLICY-DUP-01`, CLI vs. `crates/agiworkforce-execpolicy`), confirming this is a recurring architectural gap, not a one-off.
2. **A composer-UI flag/harness-mode confusion caused every plain chat message in Desktop's Local mode to be silently routed through the full computer-use `AgentOrchestrator`** (`apps/desktop/src-tauri/src/core/agi::AgentOrchestrator`, gated behind Accessibility/Screen Recording/Input Monitoring OS permissions) instead of a normal completion — because a permission-style enum (`'ask'|'auto'|'plan'|'bypass'`) was truthy-coerced into a boolean `enable_agent_mode` flag. This is now fixed, but it is direct evidence that AGI Workforce's harness lacks a type-level boundary between "tool-confirmation posture" and "which execution engine handles this turn" — a distinction Goose enforces structurally (one `Agent::reply()` loop; `GooseMode` only ever changes _approval behavior inside_ that loop, never which engine runs).
3. **`llm_router.rs` has two ~90-line, near-duplicate implementations of candidate filtering, availability checks, rate-limit skipping, and provider fallback** (`route_with_retry` at line 1333, `send_message_streaming_with_retry` at line 2091). `known-flaws.md`'s `LOCAL-CHAT-NOINVOKE-01` entry shows both had to be patched together for the same local-mode error-message fix — concrete proof the duplication already imposes double-maintenance cost, the exact failure mode Goose avoids by having provider retry live once in `goose-provider-types::retry`.

Where AGI Workforce is genuinely stronger: `AGICore::achieve_goal` enforces _both_ an iteration cap (`goal_iteration_limit`, capped at 1000) _and_ an absolute 5-minute wall-clock timeout (`core/agi/core.rs:721-722`) — Goose's core loop (`agent.rs:1901`) only has a turn cap (`DEFAULT_MAX_TURNS = 1000`, `GOOSE_MAX_TURNS`) and a cancellation token, no built-in wall-clock ceiling on the loop itself. And AGI Workforce's `DirectApiProvider` reaches 22+ OpenAI-compatible providers (OpenAI, Anthropic, DeepSeek, xAI, Mistral, Perplexity, Groq, Together, Fireworks, Cerebras, DeepInfra, Cohere, AI21, Sambanova, Azure — `providers/direct_api_provider.rs:4-6`) through one generic client + endpoint table, a broader reach than Goose's per-provider file set (`openai.rs`, `anthropic.rs`, `databricks*.rs`, `ollama.rs`, plus a generic `openai_compatible.rs`/`declarative.rs`).

Both AGI Workforce loops are legitimate, working ReAct/plan-execute implementations with real stopping conditions — this is not a "toy loop" gap. The meaningful difference is that Goose's loop-with-caps-and-retry pattern exists **once**; AGI Workforce's exists **three times** (Desktop plan-executor, CLI ReAct loop, CLI retry helper), each with independently chosen constants and independently written cancellation/timeout logic.

## 3. MCP Integration Comparison

Goose: `crates/goose/src/agents/extension_manager.rs::add_extension` (`:899`) supports `ExtensionConfig` variants `Stdio`, `Sse`, `StreamableHttp`, `InlinePython`, `Frontend`, `Builtin`, `Platform` — one manager, one transport abstraction, used by both `goose-cli` and `goose-server`. Goose additionally ships first-party MCP servers in the separate `crates/goose-mcp` crate (`computercontroller`, `memory`, `tutorial`, `autovisualiser`, `peekaboo`) which `goosed` itself can run via `goosed mcp <server>` (`goose-server/src/main.rs`), and tool-confirmation for MCP tool calls is routed through the same `GooseMode`/`ToolConfirmationRouter` as native tools.

AGI Workforce: MCP is implemented **twice**, independently:

- Desktop: `apps/desktop/src-tauri/src/core/mcp/` — `transport.rs` (`StdioTransport`, `HttpSseTransport`, `Transport::{Stdio,HttpSse}` enum at `:1843`), `protocol.rs` (JSON-RPC types), `manager.rs`, `connectors.rs`, `oauth.rs`, plus a full `mcp/server/` (Desktop can itself act as an MCP server: `auth.rs`, `http_server.rs`, `handlers.rs`, `tools.rs`). ~11,460 lines across the module.
- CLI: `apps/cli/src/mcp/` — `connection_pool.rs`, `http.rs`, `sse.rs`, `oauth_flow.rs`, `oauth_store.rs`, `resources.rs`, `status.rs`, `tui_handler.rs`. ~5,695 lines. Plus a separate `apps/cli/src/features/mcp` layer on top.

Both implementations cover the same protocol surface (stdio + HTTP/SSE transports, OAuth) but were clearly written independently — different file organization, different OAuth-store designs, no shared types. Unlike the agent-loop split (where CLI vs. Desktop domain differences arguably justify separate execution engines), **JSON-RPC/stdio/SSE transport mechanics do not vary by domain** — this is the clearest pure-duplication finding in the whole comparison. Desktop's ability to also _run_ as an MCP server (`core/mcp/server/`) has no Goose equivalent inside `crates/goose` itself (Goose's server-hosting role is the separate `goose-mcp` crate, not the core agent crate) — a reasonable design choice either way, but it means "MCP server" and "MCP client" are two more things now living twice in AGI Workforce vs. cleanly separated once in Goose.

| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Where            | `crates/goose-providers` (per-provider files) + `crates/goose-provider-types` (shared `Provider` trait, retry, model config)                                                                                                            | `apps/desktop/src-tauri/src/core/llm/` (`llm_router.rs`, `providers/`) **and independently** `apps/cli/src/provider.rs` + `features/providers` + `models/provider_dispatch.rs`                                                                                                                                           |
| Provider files   | `anthropic.rs`, `openai.rs`, `databricks.rs`/`databricks_v2.rs`, `ollama.rs`, `openai_compatible.rs` (generic), `declarative.rs` (config-driven providers)                                                                              | `azure.rs`, `bedrock.rs`, `ollama.rs`, `managed_cloud_provider.rs`, `direct_api_provider.rs` (generic client covering 22+ OpenAI-compatible providers via an endpoint table)                                                                                                                                             |
| Routing strategy | Model/provider chosen by session config; `Provider` trait blanket-implements retry via `retry_operation`                                                                                                                                | `LlmRouter::candidates()` builds an ordered candidate list per `RoutingStrategy` (e.g. `LocalFirst`: Ollama → ManagedCloud fallback, `strategy_order` at `llm_router.rs:1456`), then `route_with_retry`/`send_message_streaming_with_retry` walk candidates with per-candidate availability + rate-limit-cooldown checks |
| Fallback         | Provider-level retry with exponential backoff; no explicit multi-provider candidate-fallback list observed in `crates/goose` core (recipe-level `on_failure` command is closer, but that's a shell command hook, not a provider switch) | Explicit ordered fallback across providers/models with 429-cooldown tracking (`rate_limit_tracker`) and a Local-mode-specific diagnosable error ("No local model provider is reachable...") instead of a generic failure                                                                                                 |

AGI Workforce's router does more here: an explicit, ordered, rate-limit-aware multi-provider fallback chain is a genuinely useful capability Goose's core doesn't appear to have built in (Goose leans on per-session provider selection + retry-on-the-same-provider). The cost is the duplication documented in §5/§1 finding 3 — the capability is real, but implemented twice within Desktop alone (streaming vs. non-streaming) and then a _third_ time independently in the CLI's own provider dispatch.

## 5. Code-Sharing / Reuse Comparison — Confirmed, Not Speculative

Goose: **one crate, two clients.** `goose-cli` constructs `Agent::new()` in-process (`crates/goose-cli/src/session/builder.rs:501`, `use goose::agents::{Agent, ...}`). `goose-server` (`goosed`) exposes the identical `goose::agents::Agent` over HTTP (`routes/agent.rs`, `routes/reply.rs`), and the Electron desktop client is a thin HTTP caller against `http://127.0.0.1:$GOOSE_PORT` (`ui/desktop/src/main.ts:890`, `AGENTS.md`: "UI: Electron app" / "Agent: crates/goose/src/agents/agent.rs"). There is exactly one implementation of the tool loop, retry, MCP client, and provider clients in the entire workspace.

AGI Workforce: **confirmed, via `Cargo.toml` inspection, that `apps/cli` and `apps/desktop/src-tauri` share exactly one path dependency** — `agiworkforce-sandbox-policy` (`apps/cli/Cargo.toml:42`, `apps/desktop/src-tauri/Cargo.toml:31`). Every other harness subsystem is separately implemented:

- **Agent loop**: `apps/cli/src/agent/{chat,mod,executor,history,prompt,tools}.rs` (~4,359 lines) vs. `apps/desktop/src-tauri/src/core/agi/*` (24 files: `core.rs`, `executor.rs`, `orchestrator.rs`, `planner.rs`, `memory*.rs`, `checkpoint*.rs`, `executors/` with 16 domain executors, etc.)
- **MCP client**: `apps/cli/src/mcp/*` (~5,695 lines) vs. `apps/desktop/src-tauri/src/core/mcp/*` (~11,460 lines)
- **LLM provider clients**: `apps/cli/src/provider.rs` + `features/providers` + `models/provider_dispatch.rs` vs. `apps/desktop/src-tauri/src/core/llm/providers/*`

This is not automatically wrong — the two loops serve genuinely different domains (CLI: interactive coding-task ReAct loop with file/shell/MCP tools and Task-tool-style subagents, directly analogous to Goose's own `agent.rs` + `subagent_handler.rs`; Desktop: plan-then-execute computer-use/workflow automation gated behind OS accessibility permissions, with cross-agent resource locking that a single-user coding CLI doesn't need). Domain-justified divergence at the _orchestration_ layer is defensible. But **MCP transport/protocol code and provider HTTP clients have no domain-specific reason to differ** between a CLI and a desktop app talking to the same provider APIs — that portion is pure, unjustified duplication, and the repo has already flagged the identical shape of problem once: `docs/agent-context/known-flaws.md` `EXEC-POLICY-DUP-01` records "two divergent exec-policy... engines" between `apps/cli/src/exec_policy.rs` and `crates/agiworkforce-execpolicy`, with the explicit risk that "command-safety rules can silently diverge." The MCP-client and provider-client splits are the same architectural failure mode recurring in a different subsystem.

## 6. Safety / Permission-Gating Comparison

Goose's `GooseMode` (`goose-provider-types/src/goose_mode.rs`) has four variants — `Auto` (default), `Approve` (ask every call), `SmartApprove` (ask only for sensitive calls, via `detect_read_only_tools` in `permission_judge.rs`), `Chat` (no tool calls at all, checked inline at `agent.rs:2107`). Per-call confirmation uses a `ToolConfirmationRouter` (`tool_confirmation_router.rs`) with a `register`/`deliver` oneshot-channel pattern, including stale-entry pruning on cancellation — a small, well-tested unit (5 tests covering out-of-order delivery, dropped receivers, and stale-entry cleanup).

AGI Workforce's `AgentMode` (`apps/desktop/src-tauri/src/sys/commands/tool_confirmation.rs:69-74`) also has four variants — `Safe`/`Plan` (read-only allowlist, shared logic), `Build` (all tools, destructive ones need confirmation), `Autopilot` (all tools, auto-approved) — functionally a close parallel to Goose's four modes, plus a documented `ModeTransitionPayload` with a recomputed integrity hash (`:792-868`) guarding the Autopilot transition specifically, which is more defensive than anything observed in Goose's mode-switching (`update_goose_mode` at `agent.rs:2777` is a plain field write + persist, no integrity envelope). This is a point in AGI Workforce's favor.

The gap is not in the mode enum design — it's in how the _selection of which engine runs at all_ is wired at the boundary, which is exactly what finding #2 in §1 demonstrates: `resolve_request_flags` (`send_message_setup.rs:72-99`) trusts a client-supplied boolean (`enable_agent_mode`) to decide between `spawn_streaming_chat` (plain completion) and `spawn_streaming_agent` (full `AgentOrchestrator`, requiring OS automation permissions) when an explicit model is selected — and until the recent fix, the frontend was sending that boolean derived from an unrelated permission-style enum. Goose has no equivalent ambiguity because there is only one engine (`Agent::reply()`); `GooseMode` only ever changes approval behavior _inside_ that one loop, so a similar flag-mapping bug could at worst mis-set the approval mode, not silently swap which subsystem (and which OS permission requirements) handles the turn.

## 7. Recommendations, Ranked by Impact

1. **Consolidate the MCP client into one crate shared by `apps/cli` and `apps/desktop`.** This is the least domain-justified duplication found (§3, §5) — transport/protocol/OAuth mechanics are identical regardless of surface. Extract from whichever of `core/mcp/*` or `cli/src/mcp/*` is more complete into a new `crates/agiworkforce-mcp-client`, following the same pattern already used for `agiworkforce-sandbox-policy`.
2. **Delete the duplicate retry/fallback logic in `llm_router.rs`.** Extract the shared candidate-filter → availability-check → rate-limit-skip → fallback loop (`route_with_retry` line 1333, `send_message_streaming_with_retry` line 2091) into one function parameterized over "invoke" (returning either a value or a stream), matching Goose's single `retry_operation` blanket impl in `goose-provider-types/retry.rs`. `known-flaws.md`'s `LOCAL-CHAT-NOINVOKE-01` already shows this pair gets edited in lockstep — a single implementation removes the double-edit risk outright.
3. **Add a typed boundary between "tool-confirmation posture" and "which execution engine runs this turn."** The `enable_agent_mode` bug (§1 finding #2) happened because both concepts were representable as an untyped boolean at the IPC boundary. Introduce a request-level enum (e.g., `ExecutionEngine::{Chat, ComputerUseAgent}`) that the frontend cannot construct from an `AgentMode`/`AgentControl` value without an explicit, named conversion — mirroring how Goose keeps `GooseMode` scoped strictly to in-loop approval behavior.
4. **Consider whether Desktop's `core/agi` plan-then-execute engine needs its own retry manager**, analogous to Goose's `agents/retry.rs` (success-check-driven retry with `on_failure` hooks), rather than relying solely on provider-level fallback in `llm_router.rs` — recipe/goal-level retry (e.g., "re-plan if the last 3 steps failed") is currently implicit in `consecutive_failures`-style checks in `core.rs` rather than a first-class, reusable component.
5. **Port AGI Workforce's absolute wall-clock timeout (`core/agi/core.rs:721`) into the CLI's `AgentSession` loop and, if not already present, into Goose's `agent.rs` loop as a suggested upstream contribution** — this is a real strength worth generalizing rather than a gap to close.
