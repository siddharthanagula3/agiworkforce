# Build vs Buy: OSS Adoption Plan for Desktop

Status: Proposed (1 item evaluated and rejected — see below)
Owner: Platform lead
Last updated: 2026-07-03

Goal: speed up the remaining path to production by replacing hand-rolled code with mature, maintained open-source crates where the swap is safe and the time-ROI is high. Ranked by time-to-value, not by theoretical architectural purity.

**Correction (2026-07-03, same day):** the `ollama-rs` recommendation below was evaluated empirically and **rejected** — see item 1. Left in place with the correction rather than deleted, because the reasoning for _why_ it doesn't fit is itself useful: it's a concrete example of a plausible-looking swap that breaks on contact with real constraints (a `reqwest` major-version split, missing tool-call-correlation fields, degraded streaming error handling). Treat every row below the same way — as a hypothesis to verify against source before adopting, not a decision already made.

## Why these four, ranked this way

**1. `ollama-rs` — EVALUATED AND REJECTED, do not adopt.** A background agent did the actual migration attempt (not just a docs read) and found four independent, source-verified blockers: (a) `ollama-rs` 0.3.5 has **no `/api/version` or health-check equivalent at all** — grepped, zero hits — so it wouldn't even have fixed today's bug, which is already fixed at the settings-save layer anyway (`llm.rs` `llm_configure_provider`); (b) it pins `reqwest = "^0.12.28"` while this workspace is on `reqwest 0.13` — different major versions are different types in Rust, so our proxy/CA-cert-configured HTTP client (`http_client_factory::create_http_client`) cannot be reused, meaning adoption would mean duplicating client construction for a second reqwest version or silently dropping enterprise proxy/CA support for remote Ollama hosts; (c) its `ChatMessage`/`ToolCall` types have no `tool_call_id`/`id` fields, breaking multi-tool-call correlation AGI Workforce needs; (d) its streaming API collapses all transport/parse errors to `Result<_, ()>`, regressing the classified-error handling (`sse_parser.rs`) already hardened this session. **What shipped instead**: a 36-line, zero-new-dependency hardening of `is_available()` to validate `base_url` before use (commit `7eb81366a`) — smaller than the proposed swap and with none of its risk. This is the correct outcome of evaluating a "do first" recommendation seriously rather than rubber-stamping it — apply the same rigor to the remaining three rows before adopting anything.

**2. `tauri-plugin-store` (do second).** The corrupted-settings bug from today's session (a bad `ollamaUrl` value that a localStorage edit couldn't fix because the Rust-side value took precedence, or vice versa — the sync direction itself was unclear) is a structural problem: two independent stores for the same data, kept in sync by application code, will drift. The official plugin gives JS and Rust the _same_ store file — no sync code to get wrong. This is worth doing before you ship more settings surface area, not after.

**3. `rmcp` (scope it, don't skip it, don't rush it).** This is the biggest number on this page: **24,410 lines** of hand-rolled MCP protocol implementation, including a 2,270-line hand-written transport layer. MCP is a fast-moving spec with subtle framing/capability-negotiation edge cases; the official SDK is maintained by the people who write the spec. You almost certainly have (or will have) protocol-compliance bugs in your hand-rolled version that the SDK already handles. This is NOT a "do it this week" item given the size — but it's the one place on this list where "we don't have time to build this properly ourselves" is the strongest argument _for_ adopting the OSS library, not against it. Recommend: scope a migration that keeps your existing business logic (connector management, OAuth, extension registry, tool-execution wiring — the AGI-Workforce-specific parts) and replaces only the protocol/transport layer (`transport.rs`, `protocol.rs`, the low-level parts of `session.rs`) with `rmcp`. Don't attempt this alongside other production-push work; it's its own tracked initiative.

**Real comparable data point (read directly from the local Goose clone, not estimated):** Goose's MCP CLIENT layer — `agents/mcp_client.rs` (1,447 lines) + `agents/extension_manager.rs` (3,035) + `agents/extension.rs` (1,004) + `mcp_utils.rs` (108) + `config/extensions.rs` (667) = **6,261 lines** — does everything AGI Workforce's 24,410-line `core/mcp/` + `sys/commands/mcp*.rs` does (connection management, tool/resource/prompt discovery, extension lifecycle, OAuth), built entirely on `rmcp` for protocol/transport. Goose needed **zero lines** for the equivalent of AGI Workforce's 2,270-line `transport.rs` — `rmcp`'s `ClientHandler`/`RunningService`/`ServiceExt` traits (`crates/goose/src/agents/mcp_client.rs:9-25`) provide it. That's roughly a 4x code-size difference for equivalent functionality, with the single highest-bug-risk layer (hand-written JSON-RPC framing) eliminated entirely rather than shrunk. This doesn't change the "scope it, don't rush it" priority, but it's real evidence the payoff is real, not theoretical.

**4. `rig-core` (evaluate for v2, not now).** This would be the highest-leverage move on paper — it's a whole harness (multi-provider, type-safe tool calling, MCP client built in) that overlaps heavily with what `core/llm/` + `core/agi/` hand-build today. But adopting it now means a rewrite of your core routing and agent-loop logic under production time pressure, which is a bigger risk than the time it might save. Flag it as the thing to seriously evaluate once the immediate production push is done and you have room to do the migration properly, not as something to reach for this week.

## What this does NOT include

This list is deliberately narrow — it's the highest-confidence, evidence-backed swaps found while debugging today's chat-send bug, not an exhaustive audit. It does not cover apps/cli's separate agent implementation (which appears to duplicate logic in `core/agi/` rather than sharing it — a real finding, but a refactor/consolidation decision, not a library swap), nor the web/mobile/extension surfaces.
