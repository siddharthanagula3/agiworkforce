## Architecture Decisions

### 1. AsyncLocalStorage singleton, not per-module instance

The `_storage` constant is a module-level singleton. This is the correct pattern because Node's AsyncLocalStorage creates one propagation tree per instance — multiple instances would break cross-module context reads (e.g., `getAgentContext()` called from a different package than where `runWithContext()` ran). The singleton is unexported; callers interact only through `getAgentContext()` and `runWithContext()`.

### 2. Discriminated `AgentOrigin` union, not a flat flags field

The `AgentOrigin` union (`tauri-command | background-agent | dispatch`) makes it a type error to read `commandName` on a dispatch origin or `messageId` on a tauri-command origin. This prevents a class of "wrong field checked" bugs that arise when flags like `isFromDispatch: boolean` are added over time. New variants can be added without touching existing code.

### 3. `invokingRequestId`: sparse-edge semantics

`invokingRequestId` is non-null **only on the first terminal API event** for a given spawn or resume. Subsequent events from the same chain carry null. This matches the reference implementation at `agentContext.ts:163-178` in `~/Desktop/reference/src/utils/`. Downstream code uses non-null invokingRequestId as a conversation boundary marker — a consistent sentinel rather than a monotonically-increasing counter.

`deriveChildContext()` sets `invokingRequestId` to the parent's `requestId` (exactly once), then child-of-child contexts carry null again. This preserves the sparse-edge invariant across multi-level agent hierarchies.

### 4. Rust `tokio::task_local!` for Rust-side isolation

`task_local!` is the standard Tokio analog of `AsyncLocalStorage`. Each call to `COMMAND_CTX.scope(ctx, future).await` binds `ctx` to the lifetime of `future` within that tokio task. Any code reached via `.await` within `future` can call `COMMAND_CTX.with(|ctx| ...)` without receiving context from a different concurrent task.

Three `try_get_*` helpers (`try_get_request_id`, `try_get_conversation_id`, `try_get_command_name`) return `Option<_>` via `COMMAND_CTX.try_with(...)`. The `try_with` API returns `Err` when called outside any scope — avoiding a panic on legacy command paths that aren't yet wired.

### 5. IPC boundary is explicit, not transparent

The two stores (TS `AsyncLocalStorage` and Rust `task_local!`) are completely independent. Values do NOT flow across the IPC boundary automatically. Context values that Rust needs must be passed as explicit fields in the Tauri command's request payload (e.g., `conversation_id: Option<String>`), and values that TS needs from Rust must be returned in the command response. This is the correct design: transparent cross-boundary propagation would require serialising and deserialising the context on every IPC hop, coupling the two type systems.

## Edge Cases Handled

### Context propagation through Promise chains

Verified in tests: context survives `await Promise.resolve()`, multiple sequential awaits, and `.then()` chains without async/await syntax. Node's `AsyncLocalStorage` achieves this via the async-hooks mechanism — each Promise continuation carries a reference to the store at the time of `.then()` registration.

### Concurrent isolation

The stress test fires 1,000 `runWithContext()` chains simultaneously with random `setTimeout` delays (up to 5ms) to force genuine interleaving. Each chain reads back its own context and asserts exact match. Zero contamination observed across all 1,000 chains. This covers the primary use case: 1,483 Tauri commands that may be in-flight simultaneously during heavy agentic sessions.

### Memory release after chain completion

After `runWithContext` resolves, `getAgentContext()` returns null (verified in the basic contract test). The 10K memory test fires 10,000 chains sequentially, each creating a context object, and verifies the test runner does not OOM. Because AsyncLocalStorage does not retain a reference to the context after the async chain settles, the objects become GC-eligible immediately on resolution.

The "no reference cycles" constraint is documented in the module header: callers must not store `AgentContext` references in long-lived data structures, because the closure captured by `runWithContext()` holds the context alive until all `.then()` callbacks settle.

### Worker thread re-establishment

Worker threads created via `new Worker()` do NOT inherit `AsyncLocalStorage` from the spawning thread — this is a Node.js design decision. The `reestablishContextInWorker()` helper documents the correct pattern: serialise the context object from the spawning thread (via `JSON.stringify`), pass it via `workerData`, and call `runWithContext()` inside the worker before doing any async work. The helper itself is a thin wrapper over `runWithContext()` — its value is documentation, not new mechanism.

### React server components (apps/web)

`apps/web` uses Next.js 14 app router. RSC render functions run in Node.js per-request, and each request gets its own async execution context. Middleware that needs to propagate `AgentContext` across RSC boundaries must call `runWithContext()` at the request entry point (typically in a Next.js middleware or route handler) before rendering. The same `agentContext.ts` module is used — no changes are needed to the module itself, only to the middleware wiring.

### Rust nested scopes

The Rust test `nested_scopes_are_independent` documents a known difference from the TS side: `tokio::task_local!` scopes do NOT stack like `AsyncLocalStorage` does. When `COMMAND_CTX.scope(inner, future).await` is called inside an outer scope, the outer context is NOT automatically restored after the inner scope exits — because tokio's task-local is task-level, not scope-stack. The TS side restores the previous context when a nested `run()` exits (AsyncLocalStorage is a proper scope-stack). This difference is documented in the Rust test with an explicit assertion and comment.

Practical implication: Rust code should avoid calling `COMMAND_CTX.scope()` inside an existing scope within the same task. For sub-operations that need their own scope, prefer spawning a new task (`tokio::spawn`), which guarantees isolation by design (child tasks do not inherit task-local values from the parent).

## Integration with Task 1.3 (appStateStore)

The `AgentContext.planTier` field is typed as `AppState['auth']['planTier']` — the canonical `PlanTier` union from `AppStateStore.ts`. This means any code that reads `getAgentContext()!.planTier` gets the same type guarantees as reading from `appStateStore.getState().auth.planTier`. The context is populated at command invocation time by reading from the store, so callers don't need a separate store read inside async chains.

## Open Items

1. **Wire-up in call sites**: The new `COMMAND_CTX.scope(ctx, future)` wrapper is not yet called from any of the 153 existing command handlers in `sys/commands/`. Adoption can be incremental — the `try_with` API returns `None` for un-wired commands rather than panicking, so existing commands continue to work. A follow-on task should add `COMMAND_CTX.scope()` calls to the highest-throughput commands first (chat_send_message, chat_stream_message, etc.).

2. **TS invocation helper**: A convenience wrapper `withTauriCommandContext(commandName, conversationId, planTier, fn)` could be added to `apps/desktop/src/` to make it easy for frontend code to establish contexts before calling `invoke()`. This is a convenience not a correctness requirement.

3. **Propagation to web middleware**: `apps/web` middleware does not yet call `runWithContext()` per request. This is required for RSC chains to get context. Tracked as a follow-on task for the web surface.
