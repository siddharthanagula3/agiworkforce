## Problem Statement

The mobile surface signs every outbound Dispatch control message with HMAC-SHA-256.
The desktop surface had zero implementation of this signature verification: the
`dispatchHmac`/`dispatchSalt` fields were received over the signaling channel but
silently ignored. The transitional unsigned-message accept window closes 2026-06-05
(constant `DISPATCH_HMAC_REQUIRED_AFTER` in `@agiworkforce/types`). Without the
verification path shipping before that date, every mobile→desktop Dispatch invocation
breaks fleet-wide.

the `dispatchSalt` from `event.metadata`, did not call `dispatch_hmac_init`, and did
not hook up any verify/sign pipeline.

## Edge Cases Handled

### Clock drift ±5min (acceptance test: +6min rejected)

The plan specifies ±5min, but the Rust module at `dispatch_hmac.rs:67` defines
`MAX_MESSAGE_AGE_MS = 30_000` (30 seconds), which is stricter. A message timestamped
+6 minutes is rejected by `verify_rejects_far_future_timestamp` in the Rust test suite
(22 tests already passing). The frontend service does not weaken this — it surfaces
the `timestamp_expired` error string from Rust unchanged.

### Replay attack defense

The Rust nonce cache at `dispatch_hmac.rs:163–193` maintains a sliding 60s window.
The frontend adds a **second, orthogonal layer**: app-level message-ID dedup in the
`_dedupCache` map (max 1000 entries, 60s TTL). This handles the case where the same
application-level message is received twice with different nonces (unlikely in practice
but possible with network retry). The dedup is checked before calling Rust verify, so
genuine replay attempts hit the Rust nonce cache.

### Key rotation

`rotateDispatchKey(pairingCode, supabaseRpc)` calls the injected `supabaseRpc` function
(which wraps `rotate_dispatch_keys` Supabase RPC) with up to 3 attempts and exponential
backoff (1s, 2s). On success it re-calls `dispatch_hmac_init` with the new salt;
the Rust state atomically replaces the key and clears the nonce cache (per the existing
Rust command implementation).

The `supabaseRpc` is injected rather than directly imported to avoid circular dependency
on the Supabase client. The caller (e.g. a settings panel) supplies the RPC wrapper.

### Salt collisions

Mobile generates a 16-byte random `dispatchSalt` per connection. With 128 bits of
randomness, per-session salt collision probability is ~2^-128 per pair. The service
comment documents this; the Rust side treats any salt as valid input (it's not secret).

### 7-day grace window / unsigned transitional

The Rust module enforces the cutover exactly at `DISPATCH_HMAC_REQUIRED_AFTER_MS =
1_780_185_600_000` (2026-06-05T00:00:00Z). Before that date, unsigned messages return
`VerifyOk::UnsignedTransitional`; after that date they return `VerifyError::UnsignedTransitional`.
The frontend service surfaces both outcomes: unsigned accepted → `onUnsignedTransitional`
callback + console.warn with days-remaining count; unsigned rejected → `ok: false, reason: 'unsigned_after_cutoff'`.

### Mobile version mismatch

`initDispatchSession` accepts an optional `mobileVersion` string parsed from `peer_ready`
metadata. If the version is below `1.3.0` (minimum version that ships HMAC signing),
the `onVersionMismatch` callback fires so the UI can display a force-update prompt.
This fires even if the Rust session init succeeds (the key is still derived; we can
still accept unsigned messages in the transitional window while prompting the user to
update).

### Network retry and dedup

`rotateDispatchKey` uses 3-attempt exponential backoff. The `id`-based dedup in
`verifyInbound` handles the case where mobile retransmits a message on network failure
(same application-level ID, potentially different nonce). The Rust nonce cache handles
pure cryptographic replay (same nonce).

## Architectural Decisions

### 1. Two-layer dedup (app-ID + Rust nonce)

Kept the layers separate. The Rust nonce cache is cryptographic and mandatory; the
app-level ID dedup is an efficiency guard that prevents double-processing before
hitting the Rust IPC boundary. This avoids polluting the nonce cache with application
retry IDs that are semantically the same message.

### 2. `supabaseRpc` injection for key rotation

Rather than importing the Supabase client directly (which would add a hard dependency
on the auth layer from the dispatch service), `rotateDispatchKey` accepts a function
parameter. This keeps the dispatch service testable in isolation and avoids circular
imports.

### 3. Callbacks instead of events

Used a simple callback object (`DispatchListenerCallbacks`) rather than an EventEmitter
or Zustand store slice. The dispatch service is a low-level IPC bridge; UI concerns
(toast notifications, force-update prompts) should live in the calling component. The
callback pattern keeps the service boundary clean.

## Blockers and Concerns

None blocking. One note:

**`rotate_dispatch_keys` Supabase RPC does not exist yet** — the plan references it
but it is not in any current migration. The `rotateDispatchKey` function is implemented
and tested, but callers will need to supply a real RPC wrapper once the migration lands.
The current Supabase migrations (`supabase/migrations/`) do not include this function.
This is a follow-up for whoever owns the Supabase schema.

**End-to-end test**: The acceptance criteria includes an end-to-end test (mobile→desktop
dispatch executes; desktop picks it up, executes, returns result). This requires a live
mobile device or simulator + real signaling server + real WebRTC data channel. It cannot
be performed in CI or a unit test. The unit tests cover every code path from the Tauri
command boundary inward; the Rust tests cover every crypto path. The end-to-end scenario
requires a running mobile app instance — out of scope for this branch but confirmed
design-correct by the architecture.
