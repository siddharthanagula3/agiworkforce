## Findings

### QA-001 — Artifact panel toolbar controls overlap each other · **FIXED**

**Severity:** P1 (visible in any demo recording of an artifact)

**Observed.** With an HTML artifact open, the panel header rendered its controls
on top of one another: "Copy" overlapped "HTML", the publish globe icon
overlapped the copy icon, and the version chip "v1/1" overlapped "Publish". The
bar was unreadable and several buttons were partly unclickable.

**Measured before the fix:**

|                                  |           |
| -------------------------------- | --------- |
| Toolbar width                    | 399px     |
| Left group box                   | **47px**  |
| Left group content               | **245px** |
| Overlap painted over the buttons | **198px** |

**Root cause.** The header used **viewport** breakpoints (`sm:`) to decide what
to render inside a **fixed-width split panel**. The panel stays ~399px wide no
matter how large the window is, so at a 1600px viewport `sm:inline` happily
showed the "Copy" and "Publish" text labels, the "Open in new tab" button and
the "Fullscreen" button — none of which fit. The left group carried `min-w-0`
and `shrink-1` but `overflow: visible`, and its title span lacked `min-w-0`, so
`truncate` never engaged and the surplus content painted straight over the
button row.

This is why it reproduced at every window size: widening the window made it
_worse_, not better, because more labels became eligible to render.

**Fix** (`apps/web/features/chat/components/artifacts/ArtifactPreview.tsx`):

1. Made the header a container context (`@container`) — Tailwind v4 supports
   this natively, no plugin needed.
2. Converted all five viewport breakpoints in the header to container
   breakpoints: the Copy/Copied/Publish labels to `@[30rem]:inline`, and the
   Open-in-new-tab / Fullscreen buttons to `@[22rem]:flex`.
3. Added `overflow-hidden` to the left group. This is the load-bearing part —
   it guarantees the group can never paint outside its box for _any_ panel
   width or title length, independent of the breakpoint tuning.
4. Added `min-w-0` to the title span so it is the element that absorbs the
   shrink and actually ellipsises.
5. Hid the redundant `· HTML` type label below `@[26rem]` — the type icon and
   the artifact tab above already carry it.

**Verified after the fix, in the browser:** left group box 211px, content 211px,
`overlaps: false`, `overflow: hidden`. Toolbar reads cleanly as
`👁 <> │ T… │ ‹ v1/1 › │ copy download publish refresh close`. The title now has
real room because the freed space went back to it.

**Generalisable lesson.** Any component that lives inside a resizable or
fixed-width panel must size on container queries, not viewport breakpoints.
Worth grepping other panel-hosted components for `sm:`/`md:`/`lg:` usage.

### QA-002 — Interactive checklist loses all progress on refresh · **FIXED**

**Severity:** P1 (the control invites interaction, then silently discards it)

**Observed.** An assistant response containing steps renders as an interactive
checklist card. Ticking step 1 correctly moved the counter `0/3 → 1/3`, filled
the progress bar to 33%, and struck the line through. **Reloading the page reset
it to `0/3` / 0%.** Same on navigating away and back.

**Root cause.** `StepsCard.tsx:106` held the state in
`useState<Set<number>>(new Set())` and nothing else. There was no persistence of
any kind, so every mount started empty. Ticking a box is a user edit, not a
render detail — it has to outlive the component.

**Fix** (`apps/web/features/chat/components/cards/StepsCard.tsx`): persist to
`localStorage`, restored via a lazy `useState` initializer so the first paint
already shows the restored state and the bar never flashes 0% before filling.

Choosing the key was the interesting part. The card is handed only
`{ content: string }` — neither `MessageCardRenderer` nor `MessageFormatCard`
receives a message id, so there was no identity to persist against. Rather than
thread a new prop through three components, the key is derived from what is
already stable: **the conversation id from the URL plus an FNV-1a hash of the
card's own content**. Assistant messages are immutable once persisted, so that
pair is stable across reloads. All storage access is wrapped in `try/catch` —
private mode or a full quota must not break ticking a box.

**Verified in the browser:** ticked step 2, hard-reloaded, card restored to
`1/3` / "33% complete", with
`agi:steps-card:c54d025f-600d-43cf-9900-50a0c2a7bcf2:xavksi = [1]` in
localStorage — correctly scoped to the conversation.

**Known limit, recorded not hidden.** Two checklists with byte-identical content
in the _same_ conversation would share one entry. Threading a real message id
would remove that; it is noted in the code comment.

### QA-004 — A Max 15x subscriber is shown Free as "your current plan" and offered a $7 downgrade as an upgrade · **FIXED**

**Severity:** P0 (billing correctness, and the single worst thing that can appear
in a demo — the product misidentifying a paying customer's plan)

**Observed.** Signed in as a **MAX 15X** subscriber. Opened the account menu →
**Upgrade**. The dialog rendered:

- **Free**, with the button **"Your current plan"** — wrong; the account is Max 15x.
- **Basic — $7 USD/month**, with **"Upgrade to Basic"** — a _downgrade_, sold as
  an upgrade, to someone already on the top tier.

The same load also showed **"Loading workspaces…"** stuck in the account menu and
a greeting reading "Good afternoon" **without the name** — both symptoms of the
same thing: `/api/me` had not resolved.

**Root cause — a fix that did not reach all its consumers.** Commit
`04b6b8acb` ("fix(billing): stop a transient 401 reporting a paid plan as free")
diagnosed this precisely and added an `unauthenticated` flag to
`web-auth-store`, whose doc comment still reads:

> _"`/api/me` … clears `subscription` to null, sets `initialized`, and records no
> error, so every consumer that reads `subscription?.tier ?? 'free'` renders a
> confident 'Free' with an Upgrade button. A paying Max 15x customer whose token
> happened to be refreshing was told to buy the plan they already own."_

Two consumers were never updated:

1. **`apps/web/shared/stores/billing-policy.ts`** — the shared readiness helper
   tested `initialized && !isLoading && error === null`. The 401 path
   **deliberately records no error**, so this returned `true` on exactly the case
   the helper exists to exclude. Every consumer inherited the hole.
2. **`apps/web/features/chat/pages/WebChatPage.tsx:3820`** — still
   `subscription?.tier ?? 'free'`, with no readiness guard.

And `UpgradePlanDialog` had `currentTier = 'free'` as a **default parameter**, so
even passing `undefined` would have re-manufactured the wrong answer.

**Fix.**

- `billing-policy.ts`: added optional `unauthenticated` to the state shape and an
  early `if (state.unauthenticated === true) return false`. This closes the hole
  for **all** consumers at once rather than patching one screen.
- `WebChatPage.tsx`: `subscription?.tier ?? (billingPolicyReady ? 'free' : undefined)`
  — the Free fallback now applies only once the answer is trustworthy.
- `UpgradePlanDialog.tsx`: removed the `= 'free'` default so `undefined` survives
  as "unknown"; added `tierKnown`; `isCurrent` is false and no card claims to be
  the current plan while unknown; the compact two-card view (which needs a
  "current" anchor) falls back to the full ladder so the user chooses rather than
  the UI guessing.

**Verified in the browser.** After the fix, on a load where `/api/me` resolved
healthily, the account menu **no longer offers "Upgrade" at all** for this
top-tier account — it now goes straight from "Get help" to "Get apps and
extensions" — workspaces resolved to "Personal ✓", and the greeting carried the
name. That is the correct end state for a Max 15x subscriber.

**Regression check:** `UpgradePlanDialog.test.tsx` 4/4 pass; the billing-policy
consumer suites (pricing, ComposerFooter, billing-policy) 89/89 pass across 9
files.

**Worth a follow-up:** the whole class is "consumers that read
`subscription?.tier ?? 'free'` without a readiness guard". Grepping for that
exact pattern across surfaces would likely find more.

### QA-003 — Checklist card clips its description mid-sentence · **OPEN**

**Severity:** P3 (polish; visible in a demo)

The card's description is line-clamped to 2 lines and cuts mid-phrase:
_"…reach out to your manager or IT if you hit any…"_. The full text is reachable
via **Original response**, so nothing is lost — but the truncation lands on a
meaningless word. Clamping at a sentence boundary, or widening to 3 lines, would
read better. Not fixed: it is cosmetic and the escape hatch exists.
