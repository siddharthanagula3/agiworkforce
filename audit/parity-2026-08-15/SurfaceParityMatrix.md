# Surface Parity Matrix

Audited 2026-08-15 at commit `e15df56e3` (branch `compliance/dpdp`, tree clean). Synthesizes `gaps/domain-cross-surface.md`, `gaps/domain-composer.md`, `inventory/shared-packages.md`, and all ten per-surface/domain inventories into one capability × surface reference. This document does not introduce new findings — every cell cites the domain or inventory file that established it. Where the underlying documents disagree with each other in emphasis, this matrix takes the more recently re-verified source-level claim.

**Surfaces:** Web · Mobile · Desktop-Tauri · Desktop-Electron · Chrome extension · VS Code extension · CLI (included only where the evidence base has CLI-specific findings; the CLI is a Rust terminal agent with no chat UI, composer, or settings surface comparable to the other six, so most UI-shaped rows omit it rather than force a NOT_APPLICABLE column of no analytical value).

**Statuses:** COMPLETE · PARTIAL · BROKEN · MOCKED · DEAD · MISSING · NOT_APPLICABLE · NEEDS_VALIDATION.

**Reading the matrix — the document's central distinction:**

- **NOT_APPLICABLE** = a correct platform decision. The capability is architecturally inappropriate for that surface, and shipping it would be wrong, not merely absent. Always carries a one-line reason (a runtime constraint, a trust-boundary rule, or an explicit founder/architecture decision).
- **MISSING** = plausibly should exist there and doesn't. No architectural reason blocks it; it's an unbuilt or unported capability.
- **PARTIAL / BROKEN / MOCKED / DEAD** = built to some degree but not delivering the capability correctly today — see the cell's cited gap ID for the specific failure mode.
- **NEEDS_VALIDATION** = the evidence base could not close the question from static reading alone (a live-config dependency, an environment-specific runtime behavior, or a test suite whose current failures make the underlying logic unverifiable).

Two corrections this audit made to its own earlier findings are carried forward here rather than silently repeated: the web auth-route cluster (`/sign-in`, `/sign-up`, `/register`, `/auth/login`) is **not** duplicate implementations — every non-canonical URL is a documented `redirect()` alias for a named external caller (desktop's cloud-auth handoff, Clerk's own routing convention); see §3.13. And `agiworkforce.com` is confirmed live in production — nothing in this document should be read as implying otherwise.

## 1. Headline: four parallel chat implementations, one of them the product's primary surface

The single fact that shapes most of the rest of this matrix: `@agiworkforce/unified-chat` (`packages/ui/unified-chat`) is a real, substantial, ~75-component shared chat UI package — `ChatInterface.tsx` 1,063 lines, `MessageList.tsx` 393, `ChatInput.tsx` 1,422, `MessageBubble.tsx` 924 — and **Web's primary chat route does not use it.**

| Surface                                                        | Chat route                                                 | What renders                                                                                     | Uses `unified-chat`?                                                                                                                                                                                 |
| -------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Desktop (Tauri, and Electron in bundled-fallback mode)         | `App.tsx:1976` (unconditional)                             | `DesktopShellV3` → `ChatInterface`                                                               | **Yes, genuinely** — `DesktopShellV3.tsx:7-13` imports `ChatInterface`/`ChatInterfaceProps`/`ChatMessage`/`ChatRuntime` directly                                                                     |

| Chrome extension                                               | `side_panel.ts` (10,933 ln, vanilla DOM, zero React deps)  | Hand-rolled composer/message DOM; comment: "Mirrors `ChatInput.tsx`" (`side_panel.ts:9352-9354`) | **No** — manually re-derived by reading the shared component's source, not imported                                                                                                                  |

**Consequence, made concrete:** a fix landed in `unified-chat` (a markdown bug, an attachment-cap change, a paste-image handler) reaches Desktop and Web's secondary Work/Code mode — and nothing else. Web's primary surface, Mobile, and the Chrome extension each maintain an independent implementation that must be hand-ported. The Chrome extension's composer, which explicitly documents mirroring `ChatInput.tsx` by hand, is already missing six controls the shared component has (§5). Mobile and VS Code's non-adoption are the correct call given runtime constraints and are not filed as gaps anywhere in this audit; Web's non-adoption of its own team's shared package is (`CROSS-SURFACE-001`, P1).

## 4. Tauri vs. Electron: two apps, one TypeScript tree

This is the cross-surface fact most likely to be miscounted as "the desktop surface" in a casual reading of the product. It is not one app with two build targets — it is **two independently-shipping, separately-branded desktop products** that install side by side on the same machine, sharing a `src/` tree only by engineering convention.

|                    | Tauri shell (`src-tauri/`)                               | Electron shell (`electron/`)                                                                                                                                                                    |
| ------------------ | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| App ID             | `com.agiworkforce.desktop` ("AGI")                       | `com.agiworkforce.desktop.cloud` ("AGI Cloud")                                                                                                                                                  |
| Trust boundaries   | Local + BYOK + Managed Cloud (all three)                 | Managed Cloud **only**, permanently, founder-locked                                                                                                                                             |
| Default renderer   | `apps/desktop/src`, built native (WKWebView/WebView2)    | The **hosted web app**, `https://agiworkforce.com/chat`, loaded top-level in Chromium (`main.ts:14,510`)                                                                                        |
| Deep-link scheme   | `agiworkforce://`                                        | `agiworkforce-cloud://` (deliberately distinct so both installers coexist)                                                                                                                      |
| Release tags       | `v-desktop-*`                                            | `v-cloud-desktop-*` (never mixed)                                                                                                                                                               |
| Auto-update        | `@tauri-apps/plugin-updater`, real feed, minisign-signed | **No auto-update feed at all.** A manual "Download Installer" dialog opens a signed DMG in the OS browser; `desktopCloudUpdate.ts` explicitly documents "not an in-place electron-updater feed" |
| Platforms packaged | macOS + Windows + Linux (per `tauri.conf.json`/CI)       | **macOS only** — `electron-builder.yml` has no `win`/`linux`/`nsis`/`appImage` keys at all                                                                                                      |

**The consequential fact for parity analysis:** in its default, unconfigured state, the Electron shell **does not run `apps/desktop/src` at all.** It is a thin Chromium wrapper pointed at the same web app that ships to browsers. `apps/desktop/src` only becomes the Electron renderer when an operator sets `AGI_CLOUD_RENDERER=bundled` — an explicit escape hatch for webview/auth failures, not the normal path. This means:

- Every capability-matrix cell above marked "inherits Web" for Desktop-Electron is describing the _actual_ default-shipped behavior, not a fallback case.
- The `apps/desktop/src/lib/tauri-electron/*` bridge (8 files: core/window/deep-link/dialog/notification/process/shell/updater) exists purely to make the **bundled-fallback** renderer behave correctly when it _is_ used, replacing the ordinary web build's silent no-op Tauri stubs with real Electron IPC.
- **The entire 9-channel Electron IPC bridge (`agi:invoke-bridge`, `agi:window-control`, `agi:dialog`, `agi:notify`, `agi:relaunch`, `agi:check-update`, `agi:open-update-installer`, `agi:deep-link`) is unreachable in the default shipped configuration.** `preload.ts` is only attached to a `BrowserWindow` in the `!isRemote` branch; the default main window and the quick-ask panel both use `partition: REMOTE_SESSION_PARTITION` **with no `preload` key at all** (`main.ts:478`, `quickAsk.ts:39-45`). `window.agiHost` is `undefined` in the default build. Every one of the 9 channels is `BACKEND_ONLY`/dead-by-default, live only under the operator escape hatch. This is intentional-by-design (each `tauri-electron/*` shim correctly feature-detects `agiHost` and degrades, not a crash risk), but it means the security-reviewed, well-architected IPC bridge documented in the Electron codebase is not what a typical installed copy of "AGI Cloud" actually exercises.
- Deep links are the sharpest instance of the same pattern: `deliverDeepLink()` fires unconditionally on `open-url`/`second-instance` regardless of render mode and pushes via `webContents.send`, but in remote (default) mode there is no preload script, so nothing on the page can ever receive it — the OS still hands the app `agiworkforce-cloud://` URLs, which are then silently dropped. This is correct-by-design (the default renderer authenticates via an ordinary same-origin Clerk cookie session instead), but `CHANGELOG.md` separately lists allowlisting `agiworkforce-cloud://sso-callback` as a Clerk redirect URL as an **un-actioned ops TODO**, so even the bundled path's SSO return may not resolve in production Clerk config today (NEEDS_VALIDATION against the live dashboard).

**Security posture (Electron):** genuinely clean where it was checked — `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false` on every window with no exceptions; a real CSP with no `unsafe-inline`/`unsafe-eval`; origin-scoped, media-subtype-aware permission handling that narrows Electron's coarse `media` grant to audio-only even though the app has no camera feature; navigation allowlisting with `setWindowOpenHandler` always denying (external links open in the OS browser, never an embedded child window, which would break OAuth's user-agent check); `safeStorage`-backed secrets that refuse to store plaintext if OS encryption is unavailable. No security holes were found in this shell's main/preload code.

**Local↔Cloud toggle honesty inside the Electron shell (`CROSS-SURFACE-004`, P2):** `LocalCloudToggle.tsx` renders unconditionally in the shared sidebar even when running under Electron, and calls `appModeStore.setMode('local' | 'cloud')`. Selecting `'local'` inside the Electron-bundled renderer is silently coerced back to `'cloud'` by the store itself — the toggle doesn't visibly disable or hide the Local segment for a shell that structurally cannot honor it; it just no-ops the mode change. Not verified from static reading whether this specific path surfaces a toast on refusal (NEEDS_VALIDATION).

**Intentional divergence, not drift:** every capability the Electron shell permanently lacks relative to Tauri — Local mode, BYOK, filesystem access, shell execution, browser automation, computer use, local MCP — is a founder-locked decision (`apps/desktop/AGENTS.md`, "one Desktop surface, two shells," 2026-08-03/04) and verified to hold in code: `appModeStore.ts` force-coerces `mode` to `'cloud'` whenever `supportsLocalAppMode` is false, which it always is for the Electron build. `src/lib/tauri-electron/shell.ts`'s `Command.execute()` throws an honest error ("Shell commands are not available in the AGI cloud desktop app") rather than the web stub's fake success response — a deliberate honesty improvement over the browser fallback path. This is the correct design; it should not be read as an Electron capability gap anywhere in this matrix.

## 6. What's genuinely strong across surfaces — say so plainly

Consistent with this audit's standards, several patterns recur across surfaces and deserve to be named as strengths, not just background to the gaps above:

1. **The trust-boundary enforcement row is the strongest cross-surface story in the repo.** Genuinely COMPLETE on every surface that needs it — Web (N/A by nature), Mobile, Desktop-Tauri, Desktop-Electron (by permanent exclusion), and the Chrome extension all independently verified, with VS Code downgraded only to NEEDS*VALIDATION because its \_test suite*, not its logic, is currently blind (§2.3).
2. **`trust-boundaries`'s own history is the model case for exactly the kind of drift this document hunts for.** Desktop and Mobile each hand-maintained an egress allowlist that had already drifted apart (desktop missing `vercel.app`, mobile missing `clerk.dev`/`clerk.services` — a real potential Local-mode leak in each direction) before being reconciled into one shared, platform-free module now consumed by both at ~20-30 real call sites each. This is evidence the team has already executed this exact remediation once and it held — the same treatment this document recommends for composer parity, model-retirement logic, and the agent runtime, none of which have it yet.
3. **The Chrome extension is far more capable than its near-zero prior tracking (5 rows in `audit/ui-gaps.csv`) suggested.** A ~35,000-line hand-built MV3 application with real CDP-based browser automation, a fail-closed Managed-Cloud provenance gate enforced by a strict `.every()` over the transcript plus a sticky disqualification flag plus a passing egress-boundary lint, a job-application autofill+escalation engine with no equivalent in either benchmark, and 1,549/1,549 passing tests. Its real gaps (composer drift, rendering, response actions — §2.1, §3) should be read against that baseline, not as evidence the extension is thin.

5. **Desktop's Tauri↔Electron and Tauri IPC wiring gates are real, self-enforcing drift-prevention mechanisms** — a reachability walk from the actual entry point (not a lexical presence check), a "may only shrink" rule on the waiver allowlist, and a stale-allowlist check in the other direction so a waived entry that becomes reachable again fails the build until removed. This is the pattern the rest of this document's cross-surface drift findings (composer parity, model-retirement logic, the agent runtime) should eventually adopt.
6. **The chat/tool-loop backend is the most carefully engineered code path found anywhere in the evidence base**, with inline comments naming the exact bug class nearly every non-obvious decision closes — failover attribution, cancel-before-bill, missing-heartbeat, tool-permission bypass, connector-ceiling governance.
