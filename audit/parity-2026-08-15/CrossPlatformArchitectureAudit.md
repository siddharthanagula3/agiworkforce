## 1. Headline finding: four chat implementations, one shared package

**There is not one chat implementation in this repo. There are four, and the shared package is not what the web surface most users hit actually renders.**

`@agiworkforce/unified-chat` (`packages/ui/unified-chat`) is real and substantial — ~75 components, not a stub: `ChatInterface.tsx` 1,063 lines, `MessageList.tsx` 393, `ChatInput.tsx` 1,422, `MessageBubble.tsx` 924, plus composer toolbar, artifact panel, tool-call cards, command palette, project gallery, and settings-modal components. Desktop proves the abstraction works end-to-end: `apps/desktop/src/App.tsx:1976` mounts `DesktopShellV3` unconditionally, which imports `ChatInterface`, `ChatInterfaceProps`, `ChatMessage`, `ChatRuntime` directly from the package (`apps/desktop/src/features/v3/DesktopShellV3.tsx:7-13`). That is genuine, unconditional adoption — every user of the Tauri app renders the shared component.

Web is where the story splits:

| Route                                                    | What it renders                                                                                                                                             | Uses `unified-chat`?                                                                                                                                                         |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/`, `/chat`, `/chat/[sessionId]` (primary)              | `WebChatRoot` → `WebChatPage.tsx` (**4,407 lines**), its own `ChatMessageList` (1,593 ln), `MessageBubble` (**2,254 ln**), `ChatComposerNew` (**3,621 ln**) | No — 3 named imports only (`UsageWarningBanner`, `LocalByokHandoffDialog`, the `ChatMessage` type; `WebChatPage.tsx:17,168`), nothing that renders a message or composes one |
| `/agi-work`, `/chat/code`, `/chat/schedules` (secondary) | `WebShellV3` → `ChatInterface` from the package                                                                                                             | Yes                                                                                                                                                                          |

The primary surface's own `MessageBubble.tsx` is 2.4x the shared component's 924 lines; its own `ChatComposerNew.tsx` is 2.5x the shared `ChatInput.tsx`'s 1,422 lines. This is not a naming coincidence — it is a second, independently-maintained implementation of the same product surface, sitting beside the one the team already built and Desktop already ships on.

Mobile (`apps/mobile/src/features/chat/components/`: `MessageBubble.tsx` 1,124 ln, `ChatInput.tsx` 1,249 ln, `MessageList.tsx` 286 ln, `Composer/Composer.tsx` 140 ln) is a from-scratch React Native tree. This is **not** a gap — React Native cannot render a React-DOM component tree that pulls `react-dom`, and the codebase says so explicitly in a comment rather than pretending otherwise: `apps/mobile/src/lib/capabilities.tsx:6` — "React layer in `@agiworkforce/unified-chat` (it pulls react-dom)." The only cross-code-level connection between mobile and the shared package is the platform-neutral capability matrix in `@agiworkforce/types`, consumed by both sides independently.

The Chrome extension (`apps/extension/src/side_panel.ts`, **10,933 lines**, vanilla TS/DOM, zero `react` dependency in its `package.json`) hand-writes its composer and message rendering. It does not import the shared package — it manually re-derives behavior from reading the shared component's source, and says so in its own comment (`side_panel.ts:9352-9354`): "Mirrors `packages/ui/unified-chat/ChatInput.tsx`..." A comment that documents an intent to stay in sync is not a mechanism that keeps two things in sync, and the drift below shows the difference is not theoretical.

The VS Code extension plugs into `vscode.ChatParticipant`, a platform API — it correctly does not, and should not, ship its own chat UI.

**Consequence, not just structure:** a fix landed in `unified-chat` — a markdown-rendering bug, an attachment-cap change, a paste-image handler — reaches Desktop and web's secondary Work/Code mode. It does not reach web's primary surface, Mobile, or the Chrome extension, because none of those three import the code that changed.

## 2. Measured behavioral consequences of the drift

The composer domain audit (`gaps/domain-composer.md`) built a control-by-control matrix across all four independently-authored composers and found the drift is already costing shipped features, not just code hygiene:

| Control                                 | Web (primary)              | Shared pkg (Desktop + web-secondary)         | Mobile                            | Chrome ext                   |
| --------------------------------------- | -------------------------- | -------------------------------------------- | --------------------------------- | ---------------------------- |
| **Large-paste→attachment** (≥10k chars) | ❌                         | ❌                                           | ✅ `LARGE_PASTE_THRESHOLD=10_000` | ❌                           |
| **Attach from Library** (reuse)         | ❌                         | ❌                                           | ✅ `AddToChatSheet`               | ❌                           |
| **Image generation mode**               | ✅ full                    | ❌ (only a `/image` prompt-template command) | ✅ full (`mediaMode.ts`)          | ❌                           |
| **Video generation mode**               | ✅ full                    | ❌                                           | ✅ full                           | ❌                           |
| Skill `@mention` picker                 | ✅                         | ✅                                           | (sheet menu, by design)           | ❌                           |
| Research toggle                         | ✅                         | ✅                                           | ✅                                | ❌ (no dedicated toggle)     |
| Explicit web-search toggle              | ✅                         | ✅                                           | ✅                                | ⚠ not confirmed as distinct  |
| Code-execution toggle                   | ✅                         | ✅                                           | ✅                                | ❌                           |
| Writing-style picker                    | ✅                         | ✅                                           | ✅                                | ❌                           |
| Ask/Auto/Plan/Bypass agent-mode row     | ✅                         | ✅                                           | ✅ gated                          | ❌                           |
| Queue message while streaming           | ⚠ single-slot, cancel-only | ✅                                           | ❌ send button = Stop-only        | ⚠ persisted, no user control |

Four distinct capability-drift shapes are visible in this one table:

1. **Mobile is ahead, not behind, on paste-to-attachment and Library reuse** — the other three surfaces should port _mobile's_ implementation outward, not the reverse. This is worth stating plainly because "mobile lags" is the wrong prior; here it doesn't.
2. **Desktop's shared composer has no image/video generation mode at all**, despite Web and Mobile in the same codebase already shipping it — the shared package that Desktop exclusively depends on is missing a capability two of its three sibling surfaces already have.
3. **The Chrome extension is missing six controls** the shared component it claims to mirror already has (Skill @mentions, Research toggle, web-search toggle, code-execution toggle, writing-style picker, the agent-mode row). Two related concepts (project/folder scoping) are correctly and deliberately absent — the extension has no project model — but the other six are not desktop-only concepts; they are plausible-to-want-in-Chrome capabilities that simply never propagated because the component is hand-mirrored, not imported.
4. **The one piece of composer logic that _is_ correctly centralized proves the alternative works**: `packages/ui/unified-chat/src/lib/slashCommands.ts` is a pure, framework-neutral module — data plus a capability-filter function — imported by both web's local `ChatComposerNew.tsx` and the shared `ChatInput.tsx`. It is the existence proof that framework-neutral extraction is viable for this codebase's composer, not a hypothetical.

None of this is P0 — every surface degrades to a working composer, and web's primary composer (`ChatComposerNew.tsx`) carries a visible trail of prior `AUDIT-FIX CMP-3/10/15/16/27` hardening comments showing it has already been through a real "does this control do anything" pass, not neglected. But per the composer domain audit's own framing, the composer is the single most important interface in the product, and the drift is filed at P1 (`CROSS-SURFACE-001`/`COMPOSER-001`, `COMPOSER-004`) precisely because it is the highest-leverage place for four independent implementations to diverge next.

| Package                                                                | Typed only, or runtime-enforced?                                                                                                                                                                                                                                                                                                                                                                                           |

| `@agiworkforce/cloud-contracts`                                        | Runtime-enforced via real Zod schema validation at 109+40+28+18 call sites, and its module ownership is itself enforced by a CI guard (`scripts/check-cloud-contract-ownership.mjs`).                                                                                                                                                                                                                                      |
| `@agiworkforce/compliance`                                             | Partially runtime-enforced — mobile calls it for real; web bypasses it with a hand-restated duplicate (§3.5), so the "contract" is only actually shared by one of its two real consumers.                                                                                                                                                                                                                                  |
| `@agiworkforce/licensing`                                              | **Typed only.** Zero runtime callers in TS or the parallel Rust crate; self-documented as deliberately unwired.                                                                                                                                                                                                                                                                                                            |
| `@agiworkforce/model-registry` retirement data (`retired-models.json`) | **Typed/CI-time only.** Enforced as a commit/CI-time guard (`check-model-catalog-integrity.mjs`, `check-no-hardcoded-model-ids.mjs`) preventing reintroduction of retired IDs, but there is no shared _runtime_ function that migrates a persisted conversation's stored model ID when that model retires — each surface (web's `model-store.ts` at minimum) reimplements the "is this still current" check independently. |

The pattern that recurs across every "typed but not enforced" case above is the same: a real, well-designed contract exists, and the missing piece is not more schema, it is one more wiring step — a declared dependency, a CI job, a fixture-replay test — connecting the schema to a runtime path. This mirrors the composer finding in §2: the primitives are frequently good; the gap is almost always propagation.

## 5. `trust-boundaries`: the model case for fixing exactly this class of drift

`packages/contracts/trust-boundaries/src/egress-policy.ts` (92 lines) is the strongest evidence in this audit for what "duplicated implementations that drifted" looks like when caught and fixed, not just found. Its own header comment documents the defect it replaced, verbatim:

> "desktop and mobile each defined their own copy and the allowlists DRIFTED — desktop blocked `vercel.app` (mobile didn't); mobile blocked `clerk.dev` + `clerk.services` (desktop didn't). Each surface therefore failed to block some of our-cloud hosts the other blocked — a potential Local-mode leak."

The fix reconciled both into a safe union in one platform-free TS module (`PLATFORM-FREE: pure TypeScript, no DOM / Node / React-Native imports`), fail-closed by design ("an unknown or unreadable app mode is treated as Local and blocks our-cloud egress"). It is genuinely consumed, not aspirational: `apps/desktop/src/lib/egressGuard.ts` and `apps/mobile/lib/egressGuard.ts` both import it directly at an estimated 20-30 real call sites each (auth, streaming, attachments, billing, cloud persistence). Web is correctly absent as a consumer — web _is_ the cloud, so it has no local/cloud egress boundary to guard.

This is the pattern the rest of this document's recommendations (§9) ask to extend: the fix wasn't a bigger spec, it was moving one already-correct piece of logic to a single shared, platform-free module and deleting the two copies that had drifted apart.

**A second, independently-verified fail-closed enforcement point sits in Desktop's Rust layer**, not this TS package: `derive_cloud_sync_enabled(active_mode, storage_mode_is_cloud)` (`apps/desktop/src-tauri/src/sys/commands/chat/send_message_setup.rs:66-75`) forces sync `false` unconditionally whenever `active_mode == "local"`, regardless of the user's stored sync preference. Its doc comment names the threat directly: "a user with storage*mode='cloud' but active_mode='local' must never have that Local session's data touch the network." This function is \_reused*, not reimplemented, by the memory-sync and project-sync gates (`sys/commands/memory.rs:25`, `sys/commands/projects.rs:21`), so the boundary is consistent across chat, memory, and projects rather than three independently-driftable copies — and it carries explicit "TRUST-BOUNDARY" regression tests (`send_message_setup.rs:1119-1136,1242-1329,1559-1583`).

**The Chrome extension enforces a third, independent trust boundary in code**: its Managed-Cloud provenance gate (`conversation-history.ts:1465-1468` per the inventory) is fail-closed — absent-runtime means never-synced — and is backed by 1,549/1,549 passing tests, a message-policy matrix with its own coverage test, and zero `TODO`/`FIXME`/"coming soon" strings anywhere in `src/`. (One narrower, unrelated code path in the same extension — `shouldExecuteScheduledTask()` for legacy pre-origin-stamp scheduled tasks, `background/policy.ts:728-735` — is fail-_open_ by contrast with every other provenance gate in the codebase; this is a scheduling-policy nuance filed separately from the main provenance gate and does not change the classification of the primary boundary as fail-closed.)

The VS Code extension's equivalent boundary logic is real but currently **unverified**: a genuinely good security fix landed two days before this audit (`Config.model()` switched from merged workspace config to `getUserScoped()`, stopping a checked-out repo's `.vscode/settings.json` from silently moving a user's Local/BYOK/Managed-Cloud boundary), but the two test files exercising exactly this logic (`chatParticipant.test.ts`, `usageMeterTrustBoundary.test.ts`) mock only `.get()`, not the new `.inspect()` path — `Config.model()` silently falls back to `'auto'` inside the tests, producing 17 failing / 862 passing on `npx vitest run`. The trust boundary itself is not known to be broken; the safety net that would catch a _second_ regression in it is currently blind (`CROSS-SURFACE-006`, P1).

**Net assessment:** the Local/BYOK/Managed-Cloud boundary — the one invariant `CLAUDE.md` and `AGENTS.md` treat as non-negotiable across every surface — is the strongest cross-surface story in this repo, genuinely enforced in code on every surface that needs it (desktop TS, desktop Rust, mobile, Chrome), with the sole caveat that VS Code's regression coverage needs a same-day, low-risk test fix before further work in that area.

## 6. Design tokens and UI primitives: tokens reach further than components

The token layer and the component layer adopt at very different rates, and conflating them would overstate reuse:

- **`@agiworkforce/design-tokens`** (437-line `index.ts` emitting CSS custom properties + `chat.css`) reaches **5 of 6** app surfaces for real: web (`app/globals.css` imports `chat.css` directly), desktop (`src/styles/globals.css`), mobile (chat components/stores), the Chrome extension (`src/tokens.ts` calling `cssVarsToString(agiExtensionCssVars[...])` to emit real `:root`/`:host` variable blocks for both light and dark), and the VS Code extension (`webviewContent.ts`). This is genuine, non-decorative consumption from non-React, non-Tailwind surfaces, not just a nominal dependency.
- **`@agiworkforce/ui`** (55 shadcn/Radix-style component primitives) reaches only **2 of 6**: web (113-114 files) and desktop (54-55 files). Mobile (React Native), the Chrome extension (vanilla DOM, zero `.tsx` files, no `react` dependency), and the VS Code extension (webview built from an HTML template string) cannot render a React-DOM component tree — this is the identical structural constraint that keeps them off `unified-chat` (§1), applied one layer down the stack. There is no parallel RN or vanilla-DOM primitive set audited in this pass, so the component-reuse ceiling for those three surfaces is architectural, not a backlog item.

Both of the two surfaces that _do_ adopt `@agiworkforce/ui` heavily also routinely bypass the token system with inline hex literals: independently re-run in this synthesis pass, `grep -rEo "#[0-9a-fA-F]{6}\b" apps/desktop/src` and the equivalent for `apps/web/features`+`apps/web/shared` land in the same order of magnitude the design-system domain audit measured directly (desktop 322 raw hits, mostly legitimate — xterm theme colors, syntax-highlight presets, chart palettes; web 410 raw hits, but only 4 real violations once the actual `check-no-hex-colors.mjs` guard's exemptions are applied). The guard exists for web and mobile but **is not wired into CI for either** — only the Chrome extension's and VS Code extension's equivalent guards run in CI today, and the VS Code one is currently red on a `color-mix()` regex false positive (`DESIGN-SYSTEM-001`, a live, reproducible CI break on the audited commit, not a hypothetical). Desktop has no equivalent hex-color guard at all.

## 7. The agent runtime has no shared contract, anywhere

`packages/ai/agent-core` is named as if it should be the cross-surface agentic execution engine. It is not: `packages/ai/agent-core/src/` contains exactly two substantive files — `context.ts` (context-window budgeting/compaction) and `memory.ts` (memory-relevance scoring). A repo-wide grep for `tool.?loop|subagent|checkpoint.*resume|approval.*gate` across `packages/ai/*` turns up only incidental string matches inside provider wire-format/routing code, not an implementation. `packages/ai/provider-runtime`'s own `AGENTS.md` describes it as owning "AGI-owned tool-loop scaffolding," but its actual contents are streaming/retry/failover/gateway/watchdog modules — no loop control flow there either.

The real agent loop — planning, tool-call sequencing, checkpoint/resume, approval gates — lives independently inside each app's native layer: Desktop's Rust `core/agi/` (which carries its own separately-tracked `checkpoint_*` vs. `coding_checkpoint_*` duplication — two independently-built checkpoint systems where only the coding one shipped a UI, per `desktop-tauri.md` §2) and the CLI's Rust `src/agent/`. Unlike `packages/client/sync`'s cross-language cursor/settings contract (§8), **there is no fixture-replay or contract test verifying that two surfaces' agent loops apply the same approval-gate rules or checkpoint semantics.** If Desktop's agent loop and a future Web/Mobile agentic surface diverge on when a tool call requires approval, nothing in the repo's test suite catches it today.

This is not asserted as a currently-visible behavioral bug — no such bug was found by the source audit — but the absence of any shared contract for a capability this safety-relevant is itself the finding (`CROSS-SURFACE-014`, P2). The immediate, low-risk fix is naming: rename `agent-core` to something accurate (its recommendation suggests `@agiworkforce/context-memory`) so it stops reading as a shared runtime that doesn't exist, then scope a follow-up to identify which specific agentic-loop invariants are load-bearing enough to warrant extraction into a real cross-language contract test.

## 8. `packages/client/sync` and the Tauri/Electron relationship

### 8.1 Cross-device sync — the right pattern for a problem that can't have one shared binary

`packages/client/sync` (`cursor.ts`, `conversations.ts`, `messages.ts`, `memory.ts`, `projects.ts`, `settings.ts` — 717 lines total) is real, cursor-based delta-sync **apply logic**: bigint `server_version` comparisons explicitly guarded against the "9" vs "10" lexicographic-compare bug, three-way JSON settings merge with prototype-pollution-safe key filtering (`UNSAFE_OBJECT_KEYS`), last-observed-server-revision tiebreaking. It is honestly last-writer-wins-by-revision, not a CRDT — a defensible, stated choice for this problem, not an unstated shortcut.

Its own `src/index.ts:1-14` states the package exists specifically to "de-triplicate the apply rules that used to be hand-copied across mobile's `cloudSyncEngine.ts` (TS/Zustand) and desktop's `cloud_sync.rs` (Rust/SQLite)." Rust cannot import a TS module, so desktop's Rust side necessarily reimplements the same rules natively rather than depending on this package directly — but parity between the two is kept honest by a **shared golden-fixture replay suite** exercised on both the TS vitest tests and `cloud_sync.rs`'s `#[cfg(test)]` fixture-replay module (`src/__fixtures__/cursor-compare.json`, `pull-apply.json`, `push-body.json`). This is the right engineering pattern for a problem that genuinely cannot be solved by one shared binary, and it is the same pattern this document recommends (§9) for the currently-parity-test-free enterprise-licensing and agent-runtime cases. Web only consumes cursor mechanics for a pull-only artifact overlay — conversation/message persistence stays server-owned for web, which is architecturally correct since web has no local store to reconcile.

**One open verification question, not resolved in this pass**: does CI actually run _both_ the TS vitest suite and the Rust fixture-replay module whenever either side's fixtures or logic change, or could one drift silently ahead of the other without a failing build? This was not confirmed by locating and reading the specific CI workflow file (`CROSS-SURFACE-011`, P3) — flagged as an open question rather than asserted as broken.

### 8.2 Tauri and Electron: two shipping products sharing a source tree by convention, not a shared runtime

The Electron shell is not a second window onto the Tauri app — it is a separately-identified, separately-releasing product that happens to reuse the same `apps/desktop/src` TypeScript tree as one of three build targets:

|                  | Tauri shell                                          | Electron shell                                                                   |
| ---------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------- |
| App ID           | `com.agiworkforce.desktop` ("AGI")                   | `com.agiworkforce.desktop.cloud` ("AGI Cloud")                                   |
| Trust boundaries | Local + BYOK + Managed Cloud (all three)             | Managed Cloud **only**, permanently                                              |
| Default renderer | `apps/desktop/src` built native (WKWebView/WebView2) | The hosted web app `https://agiworkforce.com/chat`, loaded top-level in Chromium |
| Deep-link scheme | `agiworkforce://`                                    | `agiworkforce-cloud://` (deliberately distinct so both installers coexist)       |
| Release tags     | `v-desktop-*`                                        | `v-cloud-desktop-*` (never mixed)                                                |
| Auto-update      | Real `@tauri-apps/plugin-updater` feed               | No feed — manual "Download Installer" dialog only                                |

The critical, easy-to-miss consequence: **in its default configuration, the Electron shell does not run `apps/desktop/src` at all.** It is a thin Chromium wrapper pointed at the same web app that ships to browsers. `apps/desktop/src` only becomes the Electron renderer when an operator sets `AGI_CLOUD_RENDERER=bundled` — an explicit escape hatch for webview/auth failures, a founder-locked decision (2026-08-04). `src/lib/tauri-electron/*` (8 files) exists purely to make that fallback renderer behave correctly when it _is_ used, replacing the web build's silent no-op Tauri stubs with real Electron IPC.

**Chat is genuinely shared between Tauri-desktop and web's _secondary_ routes — but not web's primary chat surface.** The qualifier is essential and is easy to lose: both `apps/web/package.json` and `apps/desktop/package.json` depend on `@agiworkforce/unified-chat`, and `App.tsx:12-19` pulls `ChatHostBridge`, `useChatModelStore`, `useChatSettingsStore`, `useChatStore` straight from the package — so at the manifest level the dependency is real on both sides. **Desktop consumes it for its actual chat UI. Web consumes it only for `/agi-work` and `/chat/code`;** web's primary chat (`/`, `/chat`, `/chat/[sessionId]`) renders its own `WebChatPage.tsx` (4,407 lines) instead, per §1. Reading the dependency graph alone produces the misleadingly optimistic conclusion; only the import graph of the actually-rendered route settles it. Desktop's own `src/features/chat/` is now a thin, desktop-specific overlay of 8 files (CommandPalette, SearchModal, McpToolConfirmationPrompt, FolderAccessConsentDialog, ProjectSettingsDialog, KeyboardShortcutsOverlay, BrandedGreeting, ToolLabel) — not a parallel chat implementation. This was not always true: `apps/desktop/archive/features/chat/` holds 204 files of the superseded pre-migration chat UI, correctly excluded from `tsconfig`/Vite, zero live imports — a real, completed migration, correctly archived rather than left live and dead. It is the template for what should happen to the second, larger body of still-live-but-unmounted desktop UI discussed in §9.4.

**Electron's own IPC bridge is complete for the mode it serves and dead-by-default for the mode users get.** All 9 IPC channels (`agi:invoke-bridge`, `agi:open-external`, `agi:window-control`, `agi:dialog`, `agi:notify`, `agi:relaunch`, `agi:check-update`, `agi:open-update-installer`, `agi:deep-link`) are correctly authenticated (`isTrustedSender`, origin-pinned) and bidirectionally matched between `preload.ts` and `main.ts` — but `preload.ts` is only attached in the `!isRemote` branch. The default (`remote`) main window uses a session partition with no `preload` key at all, so `window.agiHost` is `undefined` and every one of the 9 channels is unreachable in the shipped default configuration. Each Electron-only shim correctly feature-detects `agiHost` and degrades rather than crashing, so this is not a defect — it is intentional per the architecture — but it means the audited IPC surface is "COMPLETE for `AGI_CLOUD_RENDERER=bundled`; unreachable for the primary shipped configuration," a distinction worth stating precisely rather than reporting bare "COMPLETE."

**Local/BYOK/Managed-Cloud enforcement in the Electron shell holds by construction, not by convention**: `appModeStore.ts` force-coerces `mode` to `'cloud'` whenever `supportsLocalAppMode` is false, which it always is under Electron (`isTauri` false). Terminal, browser automation, and MCP components exist in the shared renderer tree but are gated behind `privacyMode === 'local'`, which the Electron build can never satisfy — confirmed unreachable, not merely hidden. The one honesty gap here is UX, not security: `LocalCloudToggle.tsx` renders unconditionally and silently no-ops a `setMode('local')` attempt rather than disabling or hiding the Local segment (`CROSS-SURFACE-004`, P2) — the toggle is visible but inert, the same "control that looks live but doesn't do what it says" anti-pattern this audit's benchmark research documents users complaining about in ChatGPT and Claude's own surfaces (§10).

## 9. Recommended target architecture and migration sequence

The evidence above points to one structural principle, repeated at every layer: **the good pattern already exists somewhere in this repo — this is not a green-field design problem.** `slashCommands.ts` proves framework-neutral composer extraction works. `trust-boundaries` proves reconciling two drifted platform copies into one shared module works. `packages/client/sync` proves a fixture-replay contract test is the right tool when a shared binary is impossible across a language boundary. `wiring-allowlist.json` proves a shrink-only allowlist gate is the right tool for tracked, intentional debt. The recommendation in every case below is: apply a pattern this codebase has already validated once, to the place it hasn't reached yet.

### What should be shared (and isn't yet)

1. **Composer paste/attachment/media-mode logic**, extracted as pure, framework-neutral modules under `packages/ui/unified-chat/src/lib/` (mirroring `slashCommands.ts`), consumed by web's primary composer, the shared `ChatInput.tsx`, and given the Chrome extension a real, tested port instead of a comment-only mirror.
2. **Model-retirement resolution** (`resolveModelForConversation(storedModelId, catalog) → { current, replacement?, uiCopy }`) as one pure function in `@agiworkforce/model-registry`, replacing the three independent per-surface reimplementations.
3. **Article 50 provenance marker generation and validation**, once `serialiseClaim`'s nesting bug is fixed and `@agiworkforce/compliance` becomes a declared web dependency — with a cross-surface fixture-replay test (mirroring `sync`'s pattern) asserting a marker generated on one surface validates on another.
4. **A parity contract for the agent runtime's safety-relevant invariants** (approval-gate trigger conditions, checkpoint data shape) between Desktop's and the CLI's independent Rust implementations — not necessarily a shared binary, but a fixture-replay test in `sync`'s style, once the specific load-bearing invariants are identified.
5. **Enterprise licensing verification**, if and when it is ever wired into an enforcement path: a shared fixture set (signed containers + expected verify results) replayed against both the TS package and the Rust crate, before either becomes load-bearing — closing the one place this repo built the `sync` pattern's problem shape without building the `sync` pattern's solution.

### What is correctly platform-specific (do not force into a shared package)

- Mobile's independent RN chat components (React Native cannot run React-DOM).
- The VS Code extension's native `vscode.ChatParticipant` integration (the platform owns this surface).
- `@agiworkforce/data-layer` (server-side backend abstraction, web-only by architecture) and `@agiworkforce/local-llm` (mobile's on-device inference tier selector, with no Rust equivalent to unify against).
- Desktop's Rust-native local-LLM handling, browser automation, and MCP stack — Tauri-only concerns with no `apps/web` equivalent, correctly unshared because web has no Local mode to serve.
- The Electron shell's IPC bridge — correctly minimal (9 channels) and scoped to the one thing it actually needs (bundled-renderer fallback), not a candidate for expansion toward Tauri's 1,268-command surface.

### Migration sequence, ordered by risk

Consolidating a 4,407-line primary surface onto a shared component is not a small change, and the sequence below is ordered so that no step requires the largest, riskiest move first.

1. **Lowest risk, immediate**: fix the two currently-red or currently-blind safety nets that cost nothing to fix and gate real risk — the VS Code trust-boundary test mocks (`CROSS-SURFACE-006`, a two-file test-only change) and the VS Code `color-mix()` regex false positive (`DESIGN-SYSTEM-001`, currently blocking the next real release tag). Neither touches product code.
2. **Low risk, mechanical**: extend the `wiring-allowlist.json` / shrink-only-allowlist pattern to the two places this document identifies as needing exactly that mechanism but not yet having it — a hex-literal ESLint rule scoped to `apps/desktop/src` and `apps/web/features`+`shared`, allowlisted at today's count and shrink-only from there; and an allowlist-diff CI check that fails when `unified-chat`'s exported composer-feature list grows without a corresponding `side_panel.ts` acknowledgment, so the extension's drift stops being caught by manual comparison.
3. **Medium risk, additive-only**: port mobile's already-shipped, already-tested large-paste and Library-reuse logic outward to web, desktop, and the extension as framework-neutral functions. This is purely additive — no existing behavior on any of the four surfaces regresses, and it is the single highest-value slice in the composer domain because one function closes the largest surface-count gap found.
4. **Medium risk, one surface at a time**: close Desktop's composer capability gap (image/video generation mode) by adding it to `AttachmentMenu.tsx`/`ChatInputToolbar.tsx`, modeled on mobile's `mediaMode.ts` — the smallest existing reference implementation, already pure TS. This raises the shared package's floor before any consolidation work asks web's primary surface to depend on it, so Desktop and web-secondary do not regress capability the day web-primary migrates.
5. **Higher risk, scoped and reversible**: give the Chrome extension a real, tested port of the composer logic extracted in step 3, closing the six-control gap (§2) without requiring a React runtime — the extension stays vanilla DOM/TS, it just stops re-deriving behavior from source-reading.
6. **Highest risk, sequenced last and explicitly tracked**: migrate `WebChatPage.tsx`'s message list and composer to render via `@agiworkforce/unified-chat`'s `MessageList`/`ChatInput`, moving any web-primary-only behavior the shared package genuinely lacks into the package as an optional prop/slot rather than forking again. This should be tracked as a single, explicit migration item with its own shrink-only allowlist (mirroring `wiring-allowlist.json`'s "may only shrink" rule) so the legacy web components cannot silently regrow features the shared package already has while the migration is in flight. This step is sequenced last because it is the only one in this list that touches the highest-traffic route in the product; every step before it either reduces the size of this migration (by closing the shared package's own capability gaps first) or de-risks the mechanism (by proving the allowlist/fixture-replay pattern on smaller surfaces first).

Each step above is independently shippable and independently reversible except the last, which is why the last is last. Nothing in this sequence requires a big-bang rewrite — the composer domain audit's own recommendation makes the same point explicitly: "Do not attempt a big-bang unification."

## 10. What not to copy from the benchmark

`research/cross-cutting-and-complaints.md` documents live, unresolved cross-surface parity failures at both incumbents as of the research date: OpenAI's unified desktop app reportedly shipping without a working Chat mode on some versions, and a reported Claude-Chrome sidebar bug that can lose an entire conversation because it wasn't stored in chat history. Neither vendor had a public resolution timestamp at research time. The lesson is not "match their bar" — this repo's own chat-availability track record across surfaces is already better than that — it is that **cross-surface parity bugs are hard to keep out even for well-resourced incumbents, which is exactly why the mechanical drift-prevention patterns already proven in this repo** (`wiring-allowlist.json`'s reachability walk, `trust-boundaries`' historical remediation, `sync`'s fixture-replay) **are worth extending to the areas that don't have them yet** — composer parity, model retirement, the agent runtime — **rather than relying on manual vigilance to hold.**

The same research documents ChatGPT's own effort/reasoning control rendered as three inconsistent widgets across three of its own surfaces (a checkmarked dropdown on macOS, a pair of unrelated toggles on web, an unlabeled slider in the Chrome extension) — the exact "one concept, N incompatible widgets" failure this audit's own composer matrix shows this repo is not yet fully immune to (mobile's raw effort slider vs. the catalog-driven chip UI everywhere else is the one place this repo still risks the same anti-pattern, already tracked separately as `GAP-142`). Desktop's silently-inert `LocalCloudToggle` under Electron (`CROSS-SURFACE-004`) is the same "a control that looks live but doesn't do what it says" class of defect the benchmark's own users complain about, just in a different feature — worth fixing on the same principle, not because a competitor does it better, but because this repo's own documented standard ("no fake availability badges," "finish what you start") already forbids it.

## 11. What's genuinely strong — say so plainly

1. **`packages/contracts/trust-boundaries` is the model case for exactly the class of drift this audit hunts for**, already executed once and holding (§5).
2. **`packages/client/sync`'s cross-language fixture-replay strategy** is the right pattern for a problem that cannot be solved with one shared binary, and should be extended to `packages/contracts/licensing` before that package is ever wired into an enforcement path (§8, §9).
3. **`packages/contracts/types/src/capabilities.ts`** is a well-designed, non-decorative platform-capability layer that the rest of the codebase is correctly instructed to consume instead of ad hoc platform-string branching (§4).
4. **Desktop's Tauri↔Electron wiring gates** (`check-wiring.sh`'s reachability walk, `wiring-allowlist.json`'s shrink-only rule) are a real, self-enforcing drift-prevention mechanism — a reachability walk from the actual entry point, not a lexical presence check — and the pattern this document recommends extending to composer parity and model retirement (§9).
5. **The Chrome extension is far more capable than its prior tracking (5 rows in `audit/ui-gaps.csv`) suggested**: a ~35,000-line hand-built MV3 application with real CDP-based browser automation, a fail-closed Managed-Cloud provenance gate, and 1,549/1,549 passing tests. Its composer drift (§2) is real and should be read against that baseline, not as evidence the extension is thin.
6. **Mobile is the most mature surface in the monorepo by its own inventory**, and the cross-surface-relevant pieces checked here corroborate it: real trust-boundary enforcement inside the send path, physically separate local/cloud memory MMKV namespaces with tombstone-based delete propagation and CAS versioning (`stores/memory/cloudMemoryStore.ts`, namespace `'memory-store-cloud'`), and the honest engineering discipline of shipping a real `<FeatureUnavailable/>` fallback for every gated capability rather than a blank screen.
7. **The one piece of composer logic that is genuinely shared today** (`slashCommands.ts`) and **the one piece of platform-boundary logic that was drifted and got fixed** (`trust-boundaries`) are not exceptions to this audit's findings — they are the existence proof that this repo's own engineers already know how to solve this exact class of problem, twice. The recommendation of this document is to do it a third, fourth, and fifth time, not to invent a new method.
