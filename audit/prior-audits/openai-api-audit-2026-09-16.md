# OpenAI API audit and plan

Compiled 2026-09-16. This document is an audit and a plan only. It changes no code, config, prompt, schema or test, and nothing in it has been executed or measured at runtime. It was compiled from four read-only evidence files gathered the same day and held in this session's scratchpad: `openai-docs-2026-09-16.md` (current official documentation extract from developers.openai.com), `openai-runtime-map-2026-09-16.md` (every OpenAI and OpenAI-compatible call path in the repository), `openai-quality-levers-2026-09-16.md` (latency, prompting, retries, caching, cost and observability trace of the web chat path), and `openai-turn-anatomy-2026-09-16.md` (per-send hidden model calls, data loads, context assembly, router signals and after-response work). Where an input marked a fact UNKNOWN or NOT CONFIRMED, that mark is carried forward here unchanged.

# 1. Executive Summary

**Current OpenAI architecture.** One TypeScript adapter, `packages/ai/providers/openai/src/index.ts`, is the only code in the repository that can call both `sdk.responses.create` (`index.ts:276`) and `sdk.chat.completions.create` (`index.ts:347`). It selects Responses by default for every catalog-known, capability-bearing OpenAI chat model on a native `api.openai.com` route (`shouldUseOpenAIResponsesApi`, `index.ts:206`; `modelMetadataSupportsResponses`, `index.ts:185-204`). Every client surface (web, mobile, Chrome extension, VS Code extension, CLI, Electron desktop) reaches that adapter through one ingress, `apps/web/app/api/llm/v1/chat/completions/route.ts`, and every provider's stream is re-serialized back onto an OpenAI Chat-Completions-shaped SSE wire by `OpenAIWireAssembler` (`packages/ai/provider-protocol/src/openai-wire-compat.ts:359-889`). Sixteen other provider packages speak the OpenAI-compatible Chat Completions protocol to non-OpenAI hosts and are not OpenAI integrations. Two independent second implementations exist in Rust: `apps/desktop/src-tauri/src/core/llm/provider_adapter.rs:266-391` picks Responses on a narrower rule, and `apps/cli` never constructs a Responses request at all (`apps/cli/src/models/streaming.rs:210-251`).

**Main quality issue.** There is no schema-enforced structured output anywhere on the request path. `ChatRequest` has no `responseFormat` field (`packages/contracts/types/src/provider-adapter.ts:156-178`), neither translator emits `response_format` or `text.format`, and the public gateway schema explicitly rejects `response_format.type === 'json_schema'` as unenforceable (`apps/web/app/api/llm/v1/chat/completions/lib/request-processor.ts:331-344`). Every internal JSON producer is prompt-engineered free text parsed best-effort (`json-object-mode.ts:3-7,30-51`; `packages/ai/agent-core/src/memory.ts:174-183,224-259`). OpenAI documents `text.format` with `strict: true` as the mechanism that guarantees schema adherence (https://developers.openai.com/api/docs/guides/structured-outputs).

**Main latency issue.** Work that could overlap or move off the critical path does not. Context compaction is a blocking model call inside `processRequest` (`request-processor.ts:3921`), two independent database-bound memory lookups run in sequence rather than together (`request-processor.ts:2460-2481` then `:2483-2509`), a first-balance credit path writes then re-reads (`request-processor.ts:3509-3529`), and billing settlement plus assistant-message persistence both complete before the client's terminal `[DONE]` frame is enqueued (`stream-transform.ts:1065-1117`).

**Main reliability issue.** The OpenAI SDK client is constructed with no `maxRetries` and no `timeout` (`index.ts:222-229`), and `ProviderAdapterConfig` has no field that could carry either (`provider-adapter.ts:419-425`), so the raw SDK defaults apply unobserved. The repository's own backoff state machine, `withRetry` (`packages/ai/provider-runtime/src/retry.ts:77-200`), has no caller outside its own package. The only live recovery is cross-provider rotation (`managed-failover.ts`), and it is reachable only before the first byte (`route.ts:1003-1006`). OpenAI's guidance is to honour `Retry-After` and otherwise use exponential backoff with jitter (https://developers.openai.com/api/docs/guides/error-codes).

**Main cost issue.** Every turn resends the entire thread from the client (`useChatStream.ts:545-551`, turn anatomy §3) against a system prefix whose cacheable position is not guaranteed: required-tool nudges are unshifted last and therefore land ahead of the composed cacheable preamble (`request-processor.ts:3748-3756,3773-3779,3891-3900`). On GPT-5.6 and later a cached read costs 0.1x the uncached input rate (https://developers.openai.com/api/docs/guides/prompt-caching), so a displaced prefix is a direct, per-turn, ten-times overcharge on the largest stable token block in the request.

**Responses API status.** Native OpenAI traffic from `apps/web` already runs on Responses by default and is correct. The gaps are not "migrate to Responses"; they are three specific ones. `apps/cli` BYOK against `api.openai.com` speaks Chat Completions only (`streaming.rs:210-218`). The desktop Tauri rule is `provider == "openai" && model_type == "reasoning"` (`models_config.rs:730-736`), a different shape from the TypeScript capability rule. And the Responses features that justify the API (`previous_response_id`, `store`, `reasoning.context`, `text.format`, `context_management`, `prompt_cache_options`, `text.verbosity`) are plumbed or documented but unused (`translate-responses.ts:248,293-294`; `index.ts:101`).

**Highest-value change.** Restore the cache-stable system prefix to position zero in the message array and set `prompt_cache_options.ttl: "30m"` on native GPT-5.6-and-later routes. It is a small, provider-neutral change with no user-visible effect, it applies to every turn, and it converts the single largest repeated token block in each request from full input price to 0.1x cached price where OpenAI's cache can actually see it.

OpenAI documents `input_image` with `detail` of `low`/`high`/`auto`/`original`, up to 512 MB per request and 1,500 images, and `input_file` with a 50 MB per-file and 50 MB combined limit (https://developers.openai.com/api/docs/guides/images-vision, https://developers.openai.com/api/docs/guides/file-inputs). Neither translator ever sets an image `detail` field, although the registry declares `imageInput.detailValues` per model (quality levers §9).

# 6. Quality Findings

**Q1. No schema-enforced structured output exists, and the gateway is honest about it.** `ChatRequest` has no `responseFormat` field (`provider-adapter.ts:156-178`), neither `translate.ts` nor `translate-responses.ts` emits `response_format` or `text.format`, and `request-processor.ts:331-344` rejects `json_schema` with an explicit message that returning unvalidated output for a schema request "would be silently wrong". The refusal is correct given the implementation. The implementation is the gap. OpenAI documents `text.format` with `strict:true` and SDK `parse()` helpers including `zodTextFormat()` for Zod schemas (https://developers.openai.com/api/docs/guides/structured-outputs), and the repository already uses Zod for its own request schema.

**Q2. Three internal JSON producers all degrade to non-model fallbacks without a single retry.** `extractJsonObject` (`json-object-mode.ts:30-51`) strips fences and parses, returning `{ok:false}` on failure. `parseModelMemoryFacts` (`memory.ts:224-259`) falls back to the regex extractor. Title generation falls back to a 60-character truncation (`generate-title.ts:296-319`). A transient malformed reply and a model that fundamentally cannot follow the instruction are treated identically.

**Q3. The cacheable system prefix is not guaranteed to be first.** `composeManagedSystemPreamble` (`request-processor.ts:1049-1069`) deliberately builds a stable prefix followed by `SYSTEM_PROMPT_CACHE_BOUNDARY` (`system-prompt-cache-boundary.ts:3`) and a dynamic tail, and `dynamicSystemMessageRefs` partitions by reference identity so a turn-varying semantic-search result never lands inside the stable half (`request-processor.ts:3691-3707`). That machinery is well built. But required-tool nudges are unshifted last (`:3748-3756,3773-3779,3891-3900`), and each `unshift` displaces everything already present, so on a turn with nudges the first message in the array is a nudge, not the stable preamble. Cache eligibility on OpenAI is prefix-based, so a displaced prefix is a cache miss on the largest stable block in the request.

**Q4. Prompt-cache options documented for GPT-5.6 and later are unset.** `derivePromptCacheKey` sends a stable `prompt_cache_key` on both wires (`translate.ts:228-243,289`; `translate-responses.ts:30,278,297`), which is correct. But `prompt_cache_options.ttl: "30m"` is never set. On GPT-5.6 and later a cached prefix "remains eligible for reuse for 30 minutes after its most recent write or reuse" when the TTL is set; the default is 5 to 10 minutes of inactivity (https://developers.openai.com/api/docs/guides/prompt-caching). A multi-turn conversation with human-length pauses between sends falls outside the default window routinely.

**Q5. `reasoning.context` is unread, and reasoning is dropped rather than replayed.** `translate-responses.ts:106-108` drops thinking blocks from replayed history with a comment stating that reasoning is server-side per `previous_response_id`. Since `previous_response_id` is never populated (`index.ts:270-274` passes no `previousResponseId`), reasoning is simply lost between turns. The registry models this precisely: the 5.6 entries carry a `persistentReasoning` block naming `reasoning.context` values `auto`, `all_turns` and `current_turn` plus ZDR-safe `reasoning.encrypted_content` (`models.curation.json:844-1183`), and nothing reads it. OpenAI documents that stateless requests now include `encrypted_content` by default and that replaying the complete `output` array preserves reasoning items and assistant `phase` values (https://developers.openai.com/api/docs/guides/reasoning).

**Q6. `text.verbosity` is never set.** A repository-wide grep for `verbosity` across `packages/ai` outside tests returns nothing (quality levers §2). The only output-length lever in use is `max_output_tokens` (`translate-responses.ts:288`), which truncates rather than shapes.

**Q7. Reasoning effort is silently dropped on OpenAI Chat Completions tool turns.** `translate.ts:313` omits `reasoning_effort` when `provider === 'openai'` and tools are present. The Responses path has no such carve-out (`translate-responses.ts:216-244`). This is a deliberate compatibility measure, but it means the same requested effort produces different behaviour depending on which branch the model lands in, and nothing surfaces that to the caller.

**Q8. Registry-declared capabilities have no readers.** `ultraMode`, `proMode`, `persistentReasoning`, and `toolCalling.programmatic` are all modelled in `models.curation.json` for the 5.6 family with no caller anywhere in `apps/web` or `packages/ai/providers/openai` (quality levers §2). `imageInput.detailValues` is likewise declared with no code that sets an image `detail` field. A registry that describes capabilities the request builder cannot express will drift.

**Q9. Token counting is a heuristic where an exact endpoint exists.** `estimateTokens` (`classify.ts:75-88`) uses chars-per-token constants of 3.8 for OpenAI, 3.5 for Anthropic and 4.0 for Google, times a per-model drift factor, plus a flat 800 tokens per multimodal part (`context-window.ts:15-31`). This feeds the compaction trigger, the context-overflow guard and usage-aware routing. OpenAI documents `POST /v1/responses/input_tokens` returning an exact `input_tokens` count for the same input shape (https://developers.openai.com/api/docs/guides/token-counting). A heuristic that over-estimates triggers an avoidable compaction call; one that under-estimates produces a 400.

# 7. Latency Findings

**L1. Context compaction blocks the provider call.** `compactContextWindow` is awaited as the last phase of `processRequest` (`request-processor.ts:3921`), so on any turn that needs a trim, a full model round-trip on a cheap route completes before the user-visible request is even dispatched (turn anatomy §1). Its output is capped at 500 output tokens over up to 24,000 source characters (`context-compaction.ts:29-32`). OpenAI's alternative is server-side `context_management: [{type:"compaction", compact_threshold}]`, which prunes context inside the same request and emits a `response.compaction.compacting` stream event (https://developers.openai.com/api/docs/guides/compaction). That is OpenAI-only, so it can only ever be an optimisation on the native route, never a replacement for the portable path.

**L2. Two independent memory lookups run in sequence.** `enrichPastChatContext` (`request-processor.ts:2460-2481`) is fully awaited before `enrichManagedMemoryContext` (`:2483-2509`) begins. Neither consumes the other's output; both read from the same `scopedDbPromise`. They are not combined into one `Promise.all`. Worse for diagnosis, the first is not wrapped in any `timePhase` call, so its cost is invisible in the `phase.*_ms` span attributes.

**L3. The first-balance credit path writes then re-reads.** `request-processor.ts:3509-3529` calls `SubscriptionService.allocateCreditsForPeriod` and then re-reads the balance, two sequential round-trips where an allocation returning the new balance would need one. This only fires on a first-ever balance, so the blast radius is new accounts.

**L4. Three separate Upstash round-trips before any work begins.** IP rate limit (`auth-gate.ts:123`), per-user rate limit (`:213`), and the turn-slot concurrency counter (`turn-slot.ts:105-146`) are three unbatched Redis calls per turn (turn anatomy §2).

**L5. Settlement and persistence delay the terminal frame.** `settleStreamBilling` (`stream-transform.ts:1065-1098`) and `persistAssistantTurnSnapshot` (`:1110-1114`) are both awaited before `data: [DONE]` is enqueued (`:1116-1117`). The agentic path has the same shape (`managed-agent-stream.ts:161,201,358`). Everything after `close()` is correctly deferred, including usage analytics and citation-redirect resolution (`:1119-1161`). The two awaited steps are the ones on the user's clock.

**L6. TTFT is instrumented but the deadline stack is coarse.** `firstTokenTimestampMs` is marked on the first non-empty content delta and logged as `llm_ttft_observed` with an SLO target of 2,500 ms and a breach threshold of 5,000 ms (`stream-transform.ts:633-667,52-53`). `PROVIDER_FIRST_TOKEN_DEADLINE_MS` is 25,000 ms and `TURN_FIRST_TOKEN_BUDGET_MS` is 40,000 ms (`deadline-policy.ts:12-14`). There is a ten-times gap between the SLO the telemetry measures and the deadline the code enforces.

**L7. The non-streaming branch's provider call is untimed.** `route.ts:1121-1194` calls `withProviderDeadlines` directly at `:1145-1163` with no `timePhase` wrapper, so a non-streaming turn's provider time never appears in the phase breakdown that every streaming turn produces.

**L8. Buffering is platform default.** `stream-transform.ts` and `sse-heartbeat.ts` use standard Web Streams `controller.enqueue` with no custom high-water mark or pause and resume logic. Heartbeats are injected every 15,000 ms on the research, tool-loop and durable branches (`route.ts:615,997,836-838`). Whether the standard single-turn streaming path wraps with the same heartbeat is UNKNOWN; the trace did not reach far enough into `buildAdapterStreamResponse` to confirm it.

**L9. Orchestration overhead is already partly optimised, and that work should not be undone.** The subscription lookup is started before the CSRF check and awaited two steps later (`auth-gate.ts:204-208,218-221`). Policy and spend gates run in one `Promise.all` (`route.ts:384-401`). Five routing inputs are fetched together (`request-processor.ts:2780-2798`). Ownership and moderation run as two legs of one `Promise.all` (`:2341-2343`). Attachment hydration overlaps the memory-policy read (`:2373-2383`).

# 8. Reliability Findings

**R1. No SDK retry or timeout surface exists.** `new OpenAI({...})` at `index.ts:222-229` passes only `apiKey`, `baseURL`, `organization`, `project` and `fetch`. `ProviderAdapterConfig` (`provider-adapter.ts:419-425`) has no `maxRetries` and no `timeout` field, so no caller could set them. The SDK's own defaults apply, unmodified and outside this application's instrumentation. The mitigating factor is real: `armProviderDeadlines` (`provider-deadlines.ts:68-119`) aborts the adapter's `AbortSignal`, which does cancel the SDK's HTTP request rather than abandoning it.

**R2. The same-route retry loop is dead code.** `withRetry` (`packages/ai/provider-runtime/src/retry.ts:77-200`) implements `DEFAULT_MAX_RETRIES = 10`, `BASE_DELAY_MS = 500`, `MAX_BACKOFF_MS = 32000`, `MAX_OVERLOAD_RETRIES = 3`, and `computeDelay` honours a provider's `Retry-After` verbatim when present (`:202-214`). A repository-wide grep for callers outside `provider-runtime` returns nothing. Its `FLOOR_OUTPUT_TOKENS = 3000` context-overflow shrink logic (`:10,143-147`) is therefore also unexercised; the live context-overflow behaviour is a terminal 400 to the user (`upstream-error-copy.ts`). OpenAI's guidance for 429 and 503 is to follow `Retry-After` when present and otherwise use exponential backoff with jitter (https://developers.openai.com/api/docs/guides/error-codes).

**R3. Cross-provider rotation is the only live recovery and it is pre-first-byte only.** `managed-failover.ts` rotates on nine categories (`:96-111`) and never on `billing_exhausted`, `safety` or `content_blocked` (`:136-140`), with a narrow Auto-only, once-per-turn billing exception (`:166-174`). Rotation happens on the first-chunk peek, so a rotated attempt has by construction delivered nothing (`route.ts:1003-1006`). A mid-stream OpenAI failure is terminal for the turn. The telemetry already distinguishes the two cases (`llm_stream_threw_mid_stream` at `stream-transform.ts:946`, `llm_stream_error_mid_stream` at `:1041`, `llm_stream_error_presented` at `:814`).

**R4. Rotation correctness is good and should not be weakened.** Tool state pins the provider once tool-call ids are minted (`managed-failover.ts:292-298`), with the AGI Work planning turn explicitly exempted so the first rotation does not exhaust the whole ladder (`:285-291`). A rejected credential skips every remaining route on that provider (`:411-416,450-456`). A grounded request gets at most one same-provider attempt (`MAX_SAME_PROVIDER_RETRIES_FOR_GROUNDED_REQUEST`, `retry.ts:22`). Free-lane rotation stays in the free lane (`:532-595`). One reservation spans every attempt and is settled once by whichever model served (`:52-57`).

**R5. Cancellation has two independent mechanisms and one gap.** The client's `AbortSignal` is threaded into both loops and into individual tool executions (`tool-loop.ts:1806,1979,3382`), so an abort can interrupt a tool call in flight. Cooperative cancellation for detached durable runs sets `cancellation_requested_at` and is polled at loop checkpoints (`runs/[runId]/route.ts:67-90`, `cloud-agent-run-service.ts:967-995`); it does not interrupt a tool call already executing. OpenAI's own cancel endpoint applies only to background responses (https://developers.openai.com/api/docs/guides/background), which this repository does not use.

**R6. Stream resume is poll-based replay, not SSE reconnect.** The durable path journals events and the client polls `?after=<seq>` every 2.5 seconds (`runs/[runId]/route.ts:39-63`, `useChatStream.ts:781`). The plain chat path has no stream-resume code at all (UNKNOWN whether any exists outside the paths traced). OpenAI documents `GET /v1/responses/{id}?stream=true&starting_after={sequence_number}` for background responses, which is a narrower mechanism and OpenAI-only.

**R7. The stream idle watchdog runs with defaults and a no-op warning hook.** Both wire calls wrap their stream with `withStreamIdleWatchdog` and pass no options and no hooks (`index.ts:281-298,351-353`), so the 90-second idle timeout and 45-second warning defaults apply (`watchdog.ts:1,3`) and `onHalfTimeWarning` never fires even though its timer does. A 90-second inter-chunk gap throws from inside the provider package, well before the 240,000 ms app-level stream deadline.

**R8. Error taxonomy is duplicated three times.** The main table maps every `ClassifiedError.category` to a fixed status, type, code and message (`upstream-error-copy.ts:79-309`). The audio transcription route has its own status-code switch that never reuses it (`transcriptions/route.ts:238-248`). The client maintains a third hand-written list, `MODEL_SWITCH_WORTHY_STREAM_ERROR_CODES` (`ChatMessageList.tsx:114-121`), deciding whether to offer "Switch model". The three drift independently, and codes that are terminal server-side, such as `content_filter` and `context_length_exceeded`, are not excluded from the generic client-side Retry affordance.

**R9. The transcription route is a structurally weaker integration.** A raw `fetch` with a hardcoded `'openai'` provider gate (`:412`), `Bearer OPENAI_API_KEY` (`:559`), `AbortSignal.timeout(60_000)` (`:561`), one attempt, no retry, no failover, no breaker. On error the reservation is released and the error rethrown (`:565-566`). This is recorded as a standing founder-blocked issue, AGI-14 (`ACTIVE_ISSUES.md:501-528`).

**R10. Breaker configuration is sound.** OpenAI is an `api_key` credential class: degrade at 7 consecutive failures, open at 12, 30-minute window, 10-minute reset (`breaker-profiles.ts:34-53`). The read path fails open by design so a breaker that cannot see its own store never becomes the outage (`route-breaker.ts:68-72`). Unfunded credentials and policy exclusions are deliberately separate checks that stay excluded even in half-open (`route-health-store.ts:544-557`).

**R11. No idempotency header is sent, correctly.** `packages/ai/provider-runtime/src/idempotency.ts:1-17` records that as of 2026-09-05 neither OpenAI nor Anthropic documents an idempotency header, and the docs extract confirms no idempotency-key mechanism is mentioned on the error-codes page (https://developers.openai.com/api/docs/guides/error-codes). Idempotency is enforced in-application instead.

# 9. Cost Findings

Ranked by likely impact.

**C1. Cache-prefix displacement.** Covered as Q3. Every turn with a required-tool nudge pays full input price on the stable system block. Cached reads are 0.1x the uncached input rate on GPT-5.6 and later, and the minimum cacheable prefix is 1,024 tokens on those models (https://developers.openai.com/api/docs/guides/prompt-caching). The composed preamble plus custom instructions plausibly clears that floor on most turns, though no measurement was taken.

**C2. Missing cache TTL.** Covered as Q4. Without `prompt_cache_options.ttl: "30m"`, the eligible window is 5 to 10 minutes of inactivity. Conversational pauses routinely exceed that, so the second turn of a resumed conversation re-bills the whole prefix.

**C3. Full-history resend with no server-side state.** The client resends every earlier message, tool result and attachment reference on every turn and the server does not diff against what it persisted (`useChatStream.ts:545-551`, turn anatomy §3). Adopting `previous_response_id` would not reduce token cost, because chained prior-turn input tokens are still billed as input tokens (https://developers.openai.com/api/docs/guides/conversation-state). It would reduce payload size, upload latency and cache-invalidation risk, and it would restore reasoning carry-over. Framing it as a token saving would be wrong.

**C4. The double assistant-message write.** The assistant message is persisted server-side before `[DONE]` (`stream-transform.ts:1110-1114`) and again by the client afterwards (`useChatStream.ts:1918-1928`, plus the error, cancel, interactive-card and tool-approval variants at `:3628,3686,3795,4069,4183`). Both write the same row id with `on conflict (id) do update`, so this is not a duplicate-row defect. It is two HTTP round-trips and two database writes per turn. The client round-trip is not purely redundant: it also triggers artifact indexing and, for a first user message, title generation (`messages/route.ts:152-198`), so it cannot simply be deleted.

**C5. Hidden model calls.** Per send, the harness can make up to three model calls beyond the answer. Context compaction blocks the turn and bills through its own reservation with no `quotaFeature` tag (`context-compaction.ts:172-214`). Title generation runs once per conversation through Next `after()` with `quotaFeature: 'conversation_title'` (`generate-title.ts:224,373-382`). Model-backed memory extraction is on by default and runs through `after()` with `quotaFeature: 'memory_extraction'` (`model-memory-extraction.ts:64-71,139`). Only title generation is cached (`exact-response-cache-service.ts:23-25`). Several plausible hidden calls were checked and confirmed not to be model calls at all: routing classification, tool-intent detection, moderation, search-query rewriting and past-chat retrieval are all regex or SQL (turn anatomy §1).

**C6. Reasoning-effort defaults on cheap utility calls.** The 5.6 family defaults to `defaultEffort: "medium"` (`models.curation.json:844-1183`), reached whenever no explicit per-turn signal is present (`translate-responses.ts:223-231`, fallback `medium` at `:203`). Reasoning tokens are billed as output tokens and occupy context even though they are not returned (https://developers.openai.com/api/docs/guides/reasoning). Title generation, memory extraction and compaction have no need of them.

**C7. OpenAI hosted `web_search` per-call surcharge is unmetered.** A dedicated per-call COGS ledger exists for Google grounding (`grounding-cost.ts:1-40`, posting to `cogs-ledger-service.ts`). No equivalent exists for OpenAI's hosted `web_search`, which OpenAI bills at $10.00 per 1k calls on reasoning models plus search-content tokens at model rates (https://developers.openai.com/api/docs/pricing). Token usage from the same turn is captured normally; only the per-call surcharge is unaccounted. The same gap would apply to `file_search` at $2.50 per 1k calls and to Code Interpreter at $0.03 to $1.92 per 20-minute session if either were adopted.

**C8. `service_tier: 'flex'` is unreachable.** The knob is plumbed end to end (`index.ts:99,273,343-345`) and `provider-adapter-service.ts:340-347` never passes it. OpenAI documents that the response body reports the tier actually used, which may differ from the one requested (https://developers.openai.com/api/docs/guides/models), so adopting it needs a read-back path as well as a write path.

**C9. Cache accounting is already captured correctly.** Both wire paths read `cached_tokens`, cache-write tokens and reasoning tokens from OpenAI's own usage object into one accumulator (`stream.ts:99-145`, `stream-responses.ts:512-529`, `adapter-usage.ts:19-43`), and the per-turn ledger carries `costSource` of `provider_reported` or `estimated` (`managed-usage-accounting-service.ts:25-53`). This is not a gap.

# 10. Agent and Tool Findings

**A1. The payload-policy call is applied to the wrong branch.** `resolveOpenAIResponsesPayloadPolicy` is invoked at `index.ts:328-341` from the Chat Completions branch with `api: 'openai-completions'`, and every behaviour inside it is gated on `isOpenAIResponsesApi`, which matches only `'openai-responses'` and `'openai-codex-responses'` (`openai-responses-payload-policy.ts:67,171-173`). Store handling, prompt-cache stripping and disabled-reasoning stripping are therefore all no-ops at that call site, and the function is never called from the real Responses branch (`index.ts:268-317`). This is either vestigial wiring or a defect. It is flagged UNKNOWN pending maintainer intent, not asserted as a bug.

**A2. Native `code_interpreter` has no stream translation and its generated-file helpers have no callers.** `translateOpenAIResponsesStream` has item guards only for function calls and web search (`stream-responses.ts:48,61`), so a native code-interpreter call's status and output items produce no distinct `StreamChunk`. The package ships `buildOpenAIContainerGeneratedFileBundles` and `extractOpenAIContainerFileCitations` specifically to recover generated files and container-file citations (`generated-files.ts`, re-exported at `index.ts:70-77`), and neither has a caller anywhere in `apps/web`. The path is reachable: `resolveTurnCodeExecutionTools` falls back to the native tool when E2B is disabled or the turn is non-streaming (`execution-tools.ts:235-244`), and `live-voice-tools.ts:58` attaches it unconditionally for voice. E2B has its own wired generated-files path (`apps/web/lib/e2b/generated-files.ts`).

**A3. Hosted web search is correctly gated.** `substituteGatedWebSearchTool` swaps OpenAI's native `web_search` for the app's function tool when the account's policy would not auto-approve a search, because a provider-native search runs inside the provider's turn and never reaches the tool loop where it could be gated (`route.ts:682-691`). Four tool shapes are explicitly classified: `generic-function`, `openai-hosted`, `anthropic-server`, `google-builtin` (`required-search.ts:43-85`). This is good design. Whether the substitution changes the query the model ends up issuing was not traced and is UNKNOWN.

**A4. Responses-only tools are the right ones to have skipped so far.** `file_search`, native `image_generation`, OpenAI's computer tool and hosted remote MCP have zero matches anywhere in `packages/ai` or `apps/web`. Each has an app-owned equivalent that works across providers. `tool_search` and programmatic tool calling are newer additions (`tool_search` requires `gpt-5.4` or later, https://developers.openai.com/api/docs/guides/tools) and the registry already models programmatic calling for `gpt-5.6-terra` with no reader.

**A5. Continuation resends the whole transcript in both loops.** The standard loop appends `function_call_output` items and resends (`translate-responses.ts:95-102`); the deep-work loop does the same at the `ContentBlock` level (`cloud-code-agent-loop.ts:462-563`). Neither uses server-side conversation state. That is the portable choice and should remain the default.

**A6. Parallelism differs between the two loops, deliberately in one and not in the other.** The standard loop runs read-only and parallel-safe tools concurrently with a cap of 4 and then mutating tools strictly serially (`tool-loop.ts:3434-3447`), mirroring a documented split (`:33-34`). The deep-work loop runs every tool sequentially in a plain `for` loop (`cloud-code-agent-loop.ts:463-561`) with no parallel branch at all. For a read-heavy deep-work step that is avoidable serial latency. OpenAI's `parallel_tool_calls` defaults to allowing multiple simultaneous calls (https://developers.openai.com/api/docs/guides/function-calling), and neither translator sets it explicitly.

**A7. Side-effect protection on retry is solid.** `toolInvocationIdempotencyKey` is scoped by request, step, tool-call id and resume round, and `runToolCallOnce` prevents re-execution across a retried HTTP request (`tool-loop.ts:3405-3426`). `cloudCodeToolRetrySafety` classifies only `read_file` and `list_files` as retry-safe (`cloud-code-agent-loop.ts:49-53`). The durable wrapper keys each provider and tool call to a Workflow step by `operationKey` (`cloud-code-turn-workflow.ts:74-124`).

**A8. The tool loop parses assembled wire bytes rather than canonical chunks.** `collectProviderStream` reads `data:` lines and `event.choices[0].delta.content` and `.tool_calls` plus `x_` extension fields (`tool-loop.ts:1386-1644,1457,1465-1497`). This means the loop maintains SSE handling in parallel with `OpenAIWireAssembler`, a duplication the tests already name explicitly: `tool-loop-openai-passthrough.test.ts:214` describes emitting an `x_stream_error` marker because "tool-loop hand-rolls its own SSE, so the base-path marker does not cover it without this". Any change to the wire shape must be made in two places.

**A9. Mid-turn steering and async tool calling are not used and are not portable.** `response.steer` over WebSocket is `gpt-6-astra` only, and GPT-5.6 and earlier do not support it (https://developers.openai.com/api/docs/guides/steering). The changelog also names async tool calling and mid-conversation reasoning-effort changes for Astra (https://developers.openai.com/api/docs/changelog, Sep 3 2026), neither independently explored. These are future options, not present gaps.

# 11. Multimodal Findings

**M1. Files never reach OpenAI as files.** `textDocumentParts` wraps already-extracted text as a synthetic `text/plain` file block (`chat-attachment-hydration.ts:106-117`), so a PDF, Office document or notebook arrives as extracted text, not source bytes. On Responses that becomes `input_file` with `file_data` (`translate-responses.ts:53-58`); on Chat Completions there is no file part at all and the same text is inlined as a plain text part (`translate.ts:53-68`). The Chat Completions comment records why: throwing there used to break every `.txt` and `.csv` attachment on OpenRouter and every compatible vendor sharing that translator.

**M2. Native PDF handling is available and unused.** OpenAI documents `input_file` accepting `file_id`, `file_url` or `file_data`, with a PDF-only `detail` parameter and a 50 MB per-file and combined limit (https://developers.openai.com/api/docs/guides/file-inputs). The repository instead does its own extraction with `MAX_PDF_TEXT_CHARS = 200_000`, `MAX_TEXT_PAGES = 250`, `MAX_IMAGE_PAGES = 10` and `MAX_IMAGE_BYTES = 8 MiB` (`pdf-attachment-content.ts:8-31`), and falls back to page images when there is no text layer (`chat-attachment-hydration.ts:466-479`). The app-owned path is provider-neutral and should stay the default; native `input_file` is worth evaluating only as a native-route quality option for scanned or layout-heavy PDFs, and only if the extraction is measurably losing information.

**M3. Image `detail` is never set.** Both translators emit an image part with no `detail` field (`translate-responses.ts:47-52`, `translate.ts:46-51`), while the registry declares per-model `detailValues` such as `[low, high, original, auto]`. `detail: "low"` is a documented cost and latency lever for screenshots and thumbnails.

**M4. App attachment limits are stricter than OpenAI's and that is fine.** The app allows 20 files and 18 MiB total per request with 4 parallel fetches (`chat-attachment-hydration.ts:26-30`). OpenAI allows up to 512 MB per request and 1,500 images (https://developers.openai.com/api/docs/guides/images-vision). The app limit is a deliberate product and cost boundary, not a defect.

**M5. Unsupported modalities fail loudly and rotate correctly.** `unsupported_input` is documented as never retryable on the same route but failover-eligible (`provider-runtime/src/errors.ts:44-55`), is listed in `FAILOVER_ELIGIBLE_CATEGORIES` (`managed-failover.ts:110`), and surfaces a message naming the specific file once rotation is exhausted (`upstream-error-copy.ts:216-222`).

**M6. Audio is out of scope here.** Pointer only: the transcription route is a separate, weaker integration covered at R9, and voice runs on a `gpt-live-1` WebRTC session with per-session-minute billing (`models.curation.json:3241-3271`, `sessionPerMinuteCost: 0.05`). OpenAI marks audio in Responses as "Coming soon" (https://developers.openai.com/api/docs/guides/migrate-to-responses), so no Responses-side audio work is proposed.

# 12. Proposed Changes

Each change is tagged NO USER-VISIBLE CHANGE, MINOR BEHAVIOR CHANGE or INTENTIONAL PRODUCT CHANGE.

### Change 1. Put the cacheable prefix first

- **Current behavior.** Required-tool nudges are unshifted after the composed preamble and therefore precede it in the final array (`request-processor.ts:3748-3756,3773-3779,3891-3900`).
- **Proposed implementation.** Insert nudges after the composed preamble block rather than at index 0, using the same reference-identity tracking that already partitions dynamic content (`dynamicSystemMessageRefs`, `:3691-3707`). Add an assertion in the composer that the stable prefix is at index 0 when present.
- **Files and areas.** `apps/web/app/api/llm/v1/chat/completions/lib/request-processor.ts`.
- **Expected benefit.** The largest stable token block becomes cache-eligible on every turn with nudges. Cached reads are 0.1x uncached input on GPT-5.6 and later.
- **Tradeoff.** Nudges sit slightly further from the conversation, which may marginally weaken their pull on the model.
- **Behavior impact.** NO USER-VISIBLE CHANGE.
- **Impact HIGH. Effort SMALL. Risk LOW.**
- **Validation.** A unit test asserting index 0 is the stable preamble for a turn with search, places and execution nudges all active, plus an assertion that the `prompt_cache_key` is unchanged across two turns that differ only in nudges.

### Change 2. Set `prompt_cache_options.ttl` on native GPT-5.6 and later routes

- **Current behavior.** `prompt_cache_key` is sent on both wires; no TTL is set (`translate.ts:289`, `translate-responses.ts:297`).
- **Proposed implementation.** Add a registry-gated `prompt_cache_options: {ttl: "30m"}` to the Responses params when the resolved model's catalog entry declares `cachePolicy.minCacheLifeMin >= 30`, which `gpt-6-astra` already does (`models.curation.json:761-836`).
- **Files and areas.** `packages/ai/providers/openai/src/translate-responses.ts`, model registry capability read.
- **Expected benefit.** Cache eligibility survives human-length pauses between turns.
- **Tradeoff.** None documented; TTL is an OpenAI-side retention window, not a client cost.
- **Behavior impact.** NO USER-VISIBLE CHANGE.
- **Impact HIGH. Effort SMALL. Risk LOW.**
- **Validation.** Extend `prompt-cache-key.test.ts` to assert the field is present for a 5.6-family model and absent for a model whose registry entry does not declare the longer cache life.

### Change 3. Give `ChatRequest` a provider-neutral structured-output field

- **Current behavior.** No `responseFormat` on `ChatRequest` (`provider-adapter.ts:156-178`); the gateway rejects `json_schema` (`request-processor.ts:331-344`); JSON is prompt-engineered and parsed best-effort (`json-object-mode.ts`).
- **Proposed implementation.** Add an optional `responseFormat: {type:'json_schema', name, schema, strict}` to `ChatRequest`. In the OpenAI Responses translator map it to `text.format`. In the Chat Completions translator map it to `response_format` where the vendor's compat metadata says it is supported, and otherwise fall back to the existing directive-plus-parse behaviour so nothing regresses for compatible vendors. Lift the gateway refusal only for providers whose adapter reports real enforcement.
- **Files and areas.** `packages/contracts/types/src/provider-adapter.ts`, `packages/ai/providers/openai/src/translate-responses.ts` and `translate.ts`, `apps/web/app/api/llm/v1/chat/completions/lib/request-processor.ts`, `json-object-mode.ts`.
- **Expected benefit.** Real schema enforcement on the native route; the public gateway can stop refusing a documented parameter.
- **Tradeoff.** A per-provider capability matrix to maintain, and a behaviour difference between enforcing and non-enforcing routes that the error copy must explain.
- **Behavior impact.** INTENTIONAL PRODUCT CHANGE for the public API surface; NO USER-VISIBLE CHANGE for chat.
- **Impact HIGH. Effort MEDIUM. Risk MEDIUM.**
- **Validation.** Adapter unit tests asserting `text.format` shape and `strict:true`; a gateway contract test asserting `json_schema` is accepted for enforcing providers and still refused with the existing message for others; golden tests on the three internal JSON producers.

### Change 4. Add one bounded same-route retry that honours `Retry-After`

- **Current behavior.** `withRetry` has no live caller; the only recovery is cross-provider rotation, pre-first-byte only (`retry.ts:77-200`, `route.ts:1003-1006`).
- **Proposed implementation.** Before consulting `failover.next`, attempt at most one same-route retry for `rate_limit`, `server_overload` and `server_error`, delayed by the provider's `Retry-After` when present and otherwise by a jittered backoff, and only when the first-token deadline has enough remaining budget under `nestedDeadlineMs` (`deadline-policy.ts:73-81`). Reuse `computeDelay` from `retry.ts:202-214` rather than writing a second one. Preserve every existing never-rotate rule unchanged.
- **Files and areas.** `apps/web/app/api/llm/v1/chat/completions/lib/managed-failover.ts` and the three `route.ts` call sites, `packages/ai/provider-runtime/src/retry.ts`.
- **Expected benefit.** A transient single-provider blip resolves on the same route instead of rotating to a different model, which is both cheaper and better for continuity and the prompt cache.
- **Tradeoff.** Adds up to one `Retry-After` delay to the worst case before rotation begins.
- **Behavior impact.** MINOR BEHAVIOR CHANGE. Slower worst-case failure, fewer unnecessary model switches.
- **Impact HIGH. Effort MEDIUM. Risk MEDIUM.**
- **Validation.** Injection tests that return 429 with and without `Retry-After`, asserting one retry then rotation, and asserting no retry for `billing_exhausted`, `safety` or `content_blocked`.

### Change 5. Add `timeout` and `maxRetries` to `ProviderAdapterConfig`

- **Current behavior.** Neither field exists on the contract type (`provider-adapter.ts:419-425`); the OpenAI client is built without them (`index.ts:222-229`).
- **Proposed implementation.** Add both as optional fields, set `maxRetries: 0` explicitly for OpenAI so the application's own retry policy is the only one in play, and set `timeout` from the armed stream deadline so the SDK and the `AbortController` agree.
- **Files and areas.** `packages/contracts/types/src/provider-adapter.ts`, every provider package's client construction, `apps/web/lib/services/provider-adapter-service.ts`.
- **Expected benefit.** One retry policy instead of two invisible ones stacked.
- **Tradeoff.** Explicitly disabling SDK retries removes a safety net that currently, unobserved, sometimes helps.
- **Behavior impact.** NO USER-VISIBLE CHANGE.
- **Impact MEDIUM. Effort SMALL. Risk LOW.**
- **Validation.** A unit test asserting the constructed client carries the expected options; a deadline test asserting the SDK timeout never exceeds the armed abort deadline.

### Change 6. Overlap the two memory lookups and time both

- **Current behavior.** `enrichPastChatContext` awaited before `enrichManagedMemoryContext`, the first untimed (`request-processor.ts:2460-2509`).
- **Proposed implementation.** Start both, `Promise.all` them, and apply their results in the existing deterministic order so the final message array is byte-identical. Wrap the first in a new `pastChatRecall` phase.
- **Files and areas.** `apps/web/app/api/llm/v1/chat/completions/lib/request-processor.ts`, `lib/turn-phases.ts`.
- **Expected benefit.** One database round-trip removed from the critical path, and the previously invisible one becomes measurable.
- **Tradeoff.** Two concurrent queries against the same scoped connection; the gain is bounded by that connection's own concurrency.
- **Behavior impact.** NO USER-VISIBLE CHANGE.
- **Impact MEDIUM. Effort SMALL. Risk LOW.**
- **Validation.** A test asserting the composed message array is identical before and after for a fixture with both sources populated, plus the new phase attribute appearing on the span.

### Change 7. Lower the effort floor on utility calls and cache compaction

- **Current behavior.** Compaction, title and memory extraction inherit `defaultEffort: "medium"`; only title results are cached (`exact-response-cache-service.ts:23-25`).
- **Proposed implementation.** Pass an explicit effort of `none` or `low` for the three utility call types where the model family supports it, and add `'context-compaction'` to `CACHE_TTL_SECONDS_BY_CALL_TYPE`. Note that `gpt-6-astra` does not support `none`, so the existing downgrade rules in `resolveOpenAIReasoningEffortForModel` (`openai-reasoning-effort.ts:90-115`) must be the mechanism, not a hardcoded string.

# 15. Product and Infrastructure Decisions

These need a decision before the engineering work that depends on them can start. None is an engineering recommendation.

1. **Quality versus cost target per workload.** §5 recommends cheaper models and lower reasoning effort for several workloads. Someone must set the acceptable quality floor per workload, because the registry's current profile ceilings (`routing-policies.json:5-16`) encode an implicit answer that has not been restated recently.
2. **TTFT target.** The telemetry SLO is 2,500 ms with a 5,000 ms breach threshold, while the enforced first-token deadline is 25,000 ms (`stream-transform.ts:52-53`, `deadline-policy.ts:14`). Either the SLO is aspirational or the deadline is too loose. Pick one number and derive the other.
3. **Native web search versus cross-provider search.** Hosted `web_search` gives better grounding on OpenAI only, costs $10.00 per 1k calls on reasoning models plus search-content tokens, and cannot be gated by the app's tool-approval policy (`route.ts:682-687`). The generic Perplexity-backed tool is uniform and gateable. The current substitution rule is a reasonable compromise; confirming it is a product decision, not an engineering one.
4. **Provider-hosted conversation state, `store`, and ZDR.** Adopting `previous_response_id` means OpenAI retains responses for 30 days unless `store:false`, and ZDR organizations get `store:false` enforced automatically (https://developers.openai.com/api/docs/guides/conversation-state). `docs/architecture/provider-routing.md:11-19` currently records "No claim unless the account contract says so" for OpenAI ZDR, with local and BYOK defaults keeping `store:false`. Whether managed-cloud turns may opt into provider-held state is a privacy decision.
5. **Data residency.** The changelog notes regional processing via a prefixed domain since Aug 21 2026 (https://developers.openai.com/api/docs/changelog). The router already carries `zeroDataRetentionOnly` and a user-level US-only preference (`request-processor.ts:1619-1634`). Whether to adopt regional endpoints is an infrastructure decision.
6. **Agent duration and tool cost caps.** Current budgets are 100 steps and 120 tool calls per AGI Work turn (`tool-loop.ts:285-286`, `tool-turn-governor.ts:16-17`), a 240,000 ms tool-loop budget and an 800,000 ms workflow invocation limit (`deadline-policy.ts:5,16`). There is no per-turn dollar cap on hosted tool surcharges. Change 10 would make one measurable; whether to enforce one is a product decision.
7. **Fallback and downgrade policy.** Change 4 proposes one same-route retry before rotation, which trades a slower worst case for fewer model switches. Whether a user prefers a slightly slower correct model over a faster different one is a product judgment.
8. **Background job behaviour.** Whether scheduled agents and deep-work runs should use OpenAI `background: true` with `sequence_number` resume, or stay entirely on the existing durable Workflow transport, is an infrastructure decision. The durable transport is provider-neutral and already works; OpenAI's mechanism is narrower but removes a failure surface.
9. **Rust CLI adopting Responses.** Change 12 is ready to implement and blocked only on whether BYOK CLI users should get different wire behaviour than they have today.
10. **Public gateway structured-output contract.** Change 3 would let the gateway accept `json_schema` for enforcing providers while continuing to refuse it for others. A public API that accepts a parameter conditionally is a contract decision, and `apps/web/app/api-docs/page.tsx:17-100` would need updating with it.

# 16. Things Already Done Correctly

These should not be rewritten.

- **Responses eligibility is capability-driven, not name-driven.** `modelMetadataSupportsResponses` reads catalog metadata and requires streaming plus at least one real capability (`packages/ai/providers/openai/src/index.ts:185-204`), and `shouldUseOpenAIResponsesApi` requires a native route first (`:206`). Unknown models fail closed to Chat Completions.
- **The Responses stream translator is thorough.** `stream-responses.ts` maps text deltas, both reasoning-text event families to `thinking-delta` (`:443-448`), URL citations to `citation-delta` (`:449-476`), web-search lifecycle to server-tool chunks (`:301-340,481-501`), and the full usage object including `cached_tokens` and `reasoning_tokens` (`:512-529`).
- **One canonical stream vocabulary and one client wire.** `StreamChunk` (`packages/contracts/types/src/provider-adapter.ts:362-375`) and `OpenAIWireAssembler` (`openai-wire-compat.ts:359-889`) mean every provider reaches every client in one shape, with rich content carried as `x_` extensions rather than lost.
- **The cache-boundary partition is built on reference identity, not ordering luck.** `dynamicSystemMessageRefs` tracks the exact message objects that vary per turn (`request-processor.ts:2474,2501,3059,3068,3189`) and `:3691-3707` partitions by that set, so a semantic-search result can never silently land inside the stable prefix regardless of unshift order.
- **Prompt cache keys are stable and derived, not invented.** `derivePromptCacheKey` hashes only the stable prefix (`translate.ts:228-243`) and both wires send it.
- **Model-switch cost is priced into routing.** `task-family-continuity.ts:1-40` pins a session to its current model absent a failure signal and escalates only upward, explicitly to protect the prompt-cache prefix, backed by `model-switch-cache.ts`.
- **Failover refuses to shop refusals around.** `billing_exhausted`, `safety` and `content_blocked` never rotate (`managed-failover.ts:136-140`), with a documented narrow Auto-only billing exception (`:166-174`).
- **A rejected credential is not replayed per candidate.** `CredentialFailoverState` skips every remaining route on that provider (`managed-failover.ts:411-416,450-456`).
- **Tool state pins the provider, with the right exemption.** `toolStateBindsProvider` (`:292-298`) and the planning-turn exemption (`:285-291`).
- **`Retry-After` is preserved onto the thrown error.** `providerUpstreamError` (`adapter-errors.ts:40-71`) exists because a bare `Error` used to lose the header and rotation happened with zero backoff.
- **Deadlines nest instead of stacking.** `nestedDeadlineMs` clamps a child deadline to the parent's remaining budget with a 1,000 ms floor (`deadline-policy.ts:56,73-81`), and `armProviderDeadlines` only arms a first-token timer when it is strictly tighter than the stream timer (`provider-deadlines.ts:101-104`).
- **Durable writes are bounded and fail visibly.** `createBoundedDurableWriter` races every write against a 10,000 ms deadline and marks itself unreadable once rather than retrying forever (`durable-stream-write.ts:16-56`).
- **Breaker reads fail open by design.** `route-breaker.ts:68-72` documents why an unreadable store must not become the outage, and unfunded and policy-excluded credentials stay excluded even in half-open (`route-health-store.ts:544-557`).
- **Compacted history is fenced as untrusted.** `fenceUntrustedContent` with `COMPACTED_HISTORY_TAG` (`context-compaction.ts:37-38,60-73`) prevents an injected directive inside a dropped span from being laundered into a system-authored summary.
- **Idempotency is honest.** `packages/ai/provider-runtime/src/idempotency.ts:1-17` records that no provider documents an idempotency header and enforces dedupe in-application instead, rather than sending a header that claims a guarantee nobody made.
- **Tool side effects survive retries.** `toolInvocationIdempotencyKey` and `runToolCallOnce` (`tool-loop.ts:3405-3426`); one reservation spans an attempt chain and settles once (`managed-failover.ts:52-57`).
- **Read-only and mutating tools are split.** `mapWithConcurrency` with a cap of 4 then a strict serial pass (`tool-loop.ts:3434-3447`).
- **Checkpoints are written before the frame that announces them.** All four shapes (`tool-loop.ts:4704,3682,4632,4037-4048`), so a resume never has less state than the client was shown.
- **Route switches are disclosed.** `X-AGI-Resolved-Model` and fallback-reason headers (`route.ts:728-738`), a route-switch row in the activity timeline (`useChatStream.ts:1423-1461`), and a persisted `movedFromModel`/`movedReason` pair so a reload still explains it (`:1204-1208`).
- **Degraded capabilities are disclosed in-band.** When Deep Research or code execution was requested but could not attach, the capability preamble instructs the model to say so (`capability-preamble.ts:246-266`).
- **Container-file citations already have real adaptation code.** `generated-files.ts:1-38` converts OpenAI `container_file_citation` annotations into the app's normalized generated-file model before storage, gated by the documented rule at `docs/architecture/provider-routing.md:33`. It needs a caller, not a rewrite.
- **Persistence is normalized, not raw provider objects.** `persistAssistantTurn` writes the app's own schema with a metadata blob for citations, search results and generated files (`assistant-turn-persistence.ts:138-227`).
- **Observability follows OpenTelemetry GenAI conventions.** `chat.turn` span with `phase.*_ms` attributes (`phase-timer.ts:20-30`), a per-call `gen_ai.stream.start` span with `gen_ai.request.model` and related attributes (`adapter-factory.ts:82-95`), and structured events distinguishing pre-first-byte from mid-stream failures.
- **Provider-routing documentation matches the code.** `docs/architecture/provider-routing.md:11-19,29-33` accurately records the capability matrix and the enforcement rules. One reading to keep straight: the SDK-decision row at `docs/architecture/byok-provider-strategy.md:179` names file search, remote MCP and computer use among the native tools the official SDK should carry, and none of the three is implemented anywhere yet; the row is a transport decision, not a claim that they ship.

# 17. Final Prioritized Plan

The smallest ordered set of tasks with the largest gain.

1. **Instrument what is invisible.** Wrap `enrichPastChatContext` in a phase and wrap the non-streaming provider call in `timePhase` (`request-processor.ts:2460-2481`, `route.ts:1145-1163`). Land the latency and cost comparison scripts. Without this, every later claim is an argument rather than a measurement. Impact HIGH on decision quality, Effort SMALL, Risk LOW.
2. **Make the cacheable prefix actually cacheable.** Change 1 and Change 2 together. One ordering fix and one request field, both provider-neutral in shape and OpenAI-gated in effect, applying to every turn against a documented 0.1x cached input rate. Impact HIGH, Effort SMALL, Risk LOW.
3. **Settle the retry story.** Change 5 then Change 4, in that order, so there is exactly one retry policy and it honours `Retry-After`. This converts the most common transient failure from a model switch into a successful turn on the intended model, which also protects the cache work in step 2. Impact HIGH, Effort MEDIUM, Risk MEDIUM.
