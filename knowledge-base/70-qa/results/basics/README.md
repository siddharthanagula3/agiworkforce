## Start a run

1. Name the run with its task ID, OS, mode and UTC timestamp. Under this directory create a fresh folder such as `runs/M-2/android-emulator/cloud-subscribed/20261123T011200Z/`. Make a fresh copy per attempt. Preserve earlier observations.
2. Record installed version, package source, candidate commit if known, OS, viewport, appearance, language, network, route, model shown and a nonsensitive alias for the account. For an entitled case, check plan and allowance in the app. For a gated case, read the published plan and waitlist display and record the expected route. If actual eligibility is unknown, leave it unresolved.
3. Prepare only synthetic data. Use [fixtures](fixtures/). Copy code-bench into a disposable run folder outside the evidence archive, then initialize and commit that unmodified copy with the normal Git CLI. Use a fresh copy for each independent failing-test task. From the unmodified copy, the unittest fails because add(17,19) returns −2. The expected result after repair is 36. For Chrome, serve only the fixtures folder on 127.0.0.1, for example `python3 -m http.server 8765 --bind 127.0.0.1 --directory fixtures` from this directory; grant host access only through the extension’s normal controls, if offered. If the extension rejects loopback, use an authorized public test fixture origin; record the actual environment. Never open the fixtures server on a public interface.
4. Start a recording of the actual app window or device before interaction. macOS offers the system screen recording picker. Simulator offers Record Screen; Android supports the emulator's recording controls. On Linux/Windows use the host's recorder. Record the actual editor, terminal or Chrome surface. Screen recordings must show tap/click or the visible result of each action, readable output and the final settled state. If supported and authorized, include only device/application audio for voice evaluation. Label gaps around sign-in and prompting; exclude entry of passwords, keys, verification codes, billing details and unrelated private records. Confirm the recorder actually produced a playable file with motion, sound when needed, correct surface and first/last frames. Record failure or blocker if recording consent/tools are unavailable.
5. For **every step**, save a named screenshot, e.g. `01-start.png`, `02-first-words.png`, `03-settled.png`, `04-reopened.png`. Include the success, failure and declined-permission cases that apply. Measure send-to-first-visible-words from the video timestamp, note actual milliseconds and observe pauses in the stream. Record input, expected output, actual output and final state. A read-only status page can corroborate a run; account mutation or direct API calls cannot stand in for it.
6. Exercise both light/dark at two usable widths on responsive Web and Electron, resize the editor and side panel, use narrow/wide terminal widths, and check phone portrait/landscape and font scaling. Confirm readability, reachability, focus, clipping and scroll. In the relevant tasks try offline/reconnect, app background/restart, reload while working, cancellation, accidental navigation and a long paste. For persistence, use an independent fresh app view and reload after completion; exclude cached local-only success. Use the same synthetic prompts on an authorized Claude or ChatGPT surface; record both versions/tiers, timings, side-by-side outcome, and material differences. Do not infer parity from code or a doc. Mark a missing comparator or inaccessible device as blocked for that criterion, and continue the others.
7. Note supporting media with exact relative paths or video timecodes. Report the observed symptom in plain words. Use `pass` only when all applicable criteria in the plan are verified. Use `fail` for an observed product defect, `blocked` for an unavailable account/device/permission/comparator, `partial` for incomplete observations, and `unrun` otherwise. A documented plan limit can pass only if the actual UI explains a clear Upgrade or waitlist path and avoids charging a denied turn. Report counts of passed, failed, partial, blocked and unrun separately. Denominator for readiness is all required cells. Do not report an empirical pass rate until cells have been executed, or turn no runs into 0% product performance.
8. Keep Local offline during Local-only proof. BYOK uses only a founder-authorized test key and visible destination. Keep all tests isolated from unrelated accounts and production files. For deletion provide founder with the exact disposable object and its consequence; leave that step pending until authorized. For a third-party publish, paid transaction, account invitation, hosted PR or new grant, obtain the plan's required account/target authorization. Do not make purchases to test checkout guards. No user workspaces are reset to replay these tests.

## Fixtures and prerequisites

- `route-brief.pdf` contains the synthetic station Cedar Bay, code VELA-74 and total five. `tiles.png` contains one red circle, blue square and green triangle. Use these files, or capture a picture of the synthetic tiles for M-4. A camera that returns a static virtual placeholder can prove UI flow only; distinguish observation of a real photo/file.
- `fixture-a.html` and `fixture-b.html` contain different stations/codes, a native expandable section, test form, synthetic sensitive field, mock purchase controls with a visible counter-message, and inert local-only actions. Neither page sends information or processes purchases.
- Provide access to a fresh eligible Free account and an already-entitled subscribed account with available Cloud credit, plus an intentionally exhausted test account. Use normal sign-in and plan screens. Only founder-approved test credentials or access codes may be used. Do not consume a production allowance to create a quota error. Use unique synthetic tags for all chats, files, schedules and projects.
- Verify a real iOS simulator, Android emulator, both physical phones, and available disk/memory for the chosen Local model. macOS has xcrun, adb and ffmpeg on PATH; their installation does not prove device access. A Mac terminal cannot stand in for a native Windows shell. Use an actual authorized Windows and Linux host or full VM for those cells.
- Google Chrome and macOS Terminal are installed. A local AGI CLI executable and an AGI Cloud macOS app bundle are present. Verify the distributed executable/signature with the user-visible version and actual install. An editor VSIX is present in Downloads; a VS Code bundle was not located by Spotlight on initial inventory. This is an availability lead only; use an available signed distribution and record its identity. Owner-granted access is still needed for any missing account, test key, signing/test build, comparison app, disposable remote repository or real phone.
- Record what changed after the baseline only in a separate rerun directory. Keep the whole pre-fix baseline. Before a release, record one continuous full script per required app/mode, recheck production after the owner releases and obtain the owner's viewing confirmation.
